# AI 能量判準的重新校準

**日期**：2026-08-07
**前置**：`src/specs/feel.ts` 檔頭「調完之後必須一起回頭看的東西」列了一筆欠帳
——「`steer.ts` 的 `brakeCornerRatio`、`unloadMargin`、`speedRecoverMargin`、
`extendPitchAngle` 的兩個增益，全是照**舊包絡**調出來的。持續迴旋率動了
+87% 之後那些值已經對不上這台飛機。」這一份結掉那筆帳。

---

## 1. 問題

### 1.1 欠帳的內容

2026-08-07 的手感重調（`GAME_FEEL`）讓出貨的 P-51D 爬升率變成史實的
2.2 倍、持續迴旋率 1.9 倍。而 `steer.ts` 的五個能量判準是 2026-08-05 照
**舊包絡**掃出來的。

### 1.2 但「來歷過期」不等於「值是錯的」

先量現況。`ai-manoeuvre`（1v1、300 秒、六種開局）的六場最差值：

```
指標            門檻    2026-08-05    現在（手感重調後）
belowStall      1%       0.083%        0.083%
safetyShare     5%       1.83%         0.75%   ← 變好
longestExtend   55 s     42.50 s       48.25 s ← 略退，仍有 12% 餘裕
steepShare      15%      9.66%         4.08%   ← 變好
offNose         85%      64.36%        67.19%  ← 略退，仍有 21% 餘裕
```

**沒有任何一條接近門檻。** 原因是這五個判準全部寫成**比值**，分母是飛機
自己的氣動性能：`stallMargin` = TAS ÷ 失速速度、`cornerRatio` = TAS ÷ 角落
速度。`lift` ×1.3 讓 CLmax 變大時兩個分母同步下移，比值自動跟著走 ——
這一層當初就是設計成不受手感倍率影響的。

**所以這一份的目的不是修 bug，是問「飛機肌肉大了 87%，這些門檻還能不能
再推，換到更強的攻擊性或更好的能量保存」。**

## 2. 量測

兩張表，同一組設定跑兩遍。

- **行為品質**：`ai-manoeuvre` 六場的**最差值**（P-51 對 P-51，TAS 200
  起始，300 秒）
- **戰鬥效能**：`ai-duel-matrix` 的高能量開局與共速共高（P-51 對 Bf 109，
  200 秒），記勝負、傷害交換、藍方花掉的比能量

單場 300 秒對決約 1.8 秒，掃描很便宜，所以掃得夠密。

**兩個平台是這一份唯一的結構性證據。**

行為品質那個平台（1.6~2.5 相同）說明：六場 1v1 裡 AI **從來沒有快到 1.6
倍角落速度以上**，那六場是同機種、TAS 200 起始，衝不到那個速度，所以這條
減速規則在那裡一次都沒觸發。

戰鬥效能那個平台（1.70~2.5 相同）說明：高能量開局裡規則**確實會觸發**，
而 1.70 是它剛好停止觸發的邊界。跨過那個邊界之後，同一場由「200 秒打不完、
藍方自己挨 428」變成「156 秒擊落、毫髮無傷」，能量還少花 600 m。

**六個連續取值逐位元相同，不是抽樣，是規則不再觸發這件事本身。**

1.20 那一格 `longestExtend` 56.50 秒破 55 秒門檻 —— 往下調是死路，與
2026-08-05「掃過 1.05–1.6：放低沒有幫助」一致。

### 2.2 `unloadMargin`（現值 1.15）—— 仍然是混沌

戰鬥效能：

```

1.02    逾時 紅 239 : 藍   0  花 6691   紅  94 : 藍 137

1.20    逾時 紅 180 : 藍   0  花 6051   紅 407 : 藍   0
1.30    藍勝 182s 紅1000 : 藍 0 花 6060  紅 151 : 藍  62
1.40    逾時 紅 278 : 藍   0  花 4408   紅 124 : 藍   0
```

行為品質七格全部在門檻內：`safetyShare` 0.58~2.25%、`longestExtend`
36.00~48.75 s、`steepShare` 4.08~7.24%，**沒有任何方向性**。

相鄰格之間傷害差 3~5 倍、勝負翻號，而行為品質毫無對應變化 —— 這正是
2026-08-05 那次掃描的結論（「相鄰值之間連勝負都會翻號 —— 沒有可辨識的
最佳點」）。**兩次獨立掃描、不同的飛行包絡，得到同一個結論。**

1.30 那格擊落看起來很好，但 1.20 與 1.40 都比 1.15 差 —— 那是抽樣不是趨勢。

### 2.3 `speedRecoverMargin`（現值 1.25）—— 沒有影響力

戰鬥效能四格（1.10 / 1.25 / 1.40 / 1.55）**逐位元完全相同**：
高能量開局一律「逾時 紅 561 : 藍 428、花 6627 m」，共速共高一律
「紅 305 : 藍 0」。

行為品質幾乎相同，唯一的差別是 1.55 的 `safetyShare` 由 0.75% 升到 1.75%
（往壞的方向），`offNose` 在 64.11~67.19% 之間無方向性跳動。

它的註解本來就寫過「責任在 `unload` 不在這一項，這一項降到 1.25 是順帶
收斂」。**在現行包絡下連那個順帶效果都沒有了。**

### 2.4 `pitchSpeedGain`（現值 4 × `extendPitch`）—— 現值就在好位置，且有懸崖

```
        高能量開局                  共速共高          longestExtend  steepShare
2×EP    逾時 紅 206 : 藍   0        紅 121 : 藍   0     39.00 s       8.24%
3×EP    逾時 紅  43 : 藍   0        紅 986 : 藍 461     48.50 s       4.41%
4×EP    逾時 紅 561 : 藍 428        紅 305 : 藍   0     48.25 s       4.08%  ← 現值
5×EP    逾時 紅 224 : 藍   0        紅 712 : 藍   0     48.00 s       5.91%
6×EP    逾時 紅   0 : 藍 151        紅 115 : 藍   0     96.25 s ✗     6.91%
```

6 倍是明確的懸崖：`longestExtend` 由 48 秒暴衝到 96.25 秒（破 55 秒門檻），
而且高能量開局的傷害交換**翻號**（藍方單方面挨打）。現值離懸崖有兩格。

中間幾格同樣是混沌（3×EP 在共速共高讓藍方挨 461，5×EP 讓紅方挨 712）。

### 2.5 `pitchAltitudeGain`（現值 2 × `extendPitch`）—— 量不到

兩張表都沒訊號（1~4 倍在戰鬥效能上逐位元相同）。改用 task #136 的六場
撞地場景（真實 AI、三機、腳本射手、180 秒），掃 0 / 1 / 2 / 3 / 4 / 6 倍：

```
所有六個取值，六個場景，全部逐位元相同：

400 尾追  撞地接管 0.00%  最低 2687     400 橫越  0.00%  2556
800 尾追  撞地接管 0.00%  最低 3953     800 橫越  0.00%   398
1000尾追  撞地接管 0.00%  最低  309     1000橫越  0.00%  3940
```

**連 0 倍（完全關掉）都一樣。**

原因：`extendPitchAngle` 只在 `extend` 意圖下執行，而 #136 量過那兩場低空
的意圖分布是 `approach` 60% / `engage` 30% / `merge` / `defend` ——
**`extend` 一次都沒出現**。這個旋鈕在目前所有可用的場景裡都碰不到。

它現有的註解說「掃它得不到訊號」，理由是「六場開局裡只有 1000 m 的三場
短暫進入那個範圍」。實測給出更銳利的理由：**不是進不去那個高度，是進去的
時候不在 `extend`。**

## 3. 設計

### 3.1 `brakeCornerRatio`：1.6 → 1.8

**規則本身保留。** 它的物理仍然成立 —— 轉彎半徑正比於 V²，超過角落速度
再快也不會轉得更好，只會繞更大圈。變的只是「多快算太快」這條線在新包絡下
畫錯位置了：飛機轉彎能力 +87% 之後，踩煞車丟掉的能量比換到的轉彎率值錢。

**為什麼取 1.8 而不是平台起點 1.70**：留 0.1 的餘裕。1.70 是實測邊界，
貼著邊界放等於別處動一下就又踩回懸崖 —— 而 1.60 到 1.65 那兩格
（藍方挨 428 / 333）就是懸崖的樣子。

**為什麼取 1.8 而不是 2.5**：數值上等價（1.70~2.50 逐位元相同），但把死區
拉大沒有好處。未來加進真的轉不贏的機種、或再調手感時，1.8 比 2.5 更快
重新活過來。

**這個改動精準地只作用在能量戰**：六場 1v1 的行為品質在 1.6 與 1.8 之間
逐位元相同（那六場衝不到那個速度），變的只有高能量開局 —— 而那正是這條
規則唯一會觸發的地方。

### 3.2 另外四個不動，但把發現寫進註解

| 旋鈕 | 處置 | 要寫進註解的 |
|---|---|---|
| `unloadMargin` | 不動 | 新的七格掃描表，附在舊表旁邊。**兩次獨立掃描、不同包絡、同一個結論**比一次有力得多 |
| `speedRecoverMargin` | 不動也不刪 | 四格逐位元相同 —— 它在現行包絡下沒有影響力。留著是因為它是安全網，包絡再變時會活過來 |
| `pitchSpeedGain` | 不動 | 五格掃描表，特別標出 6×EP 的懸崖（`longestExtend` 48 → 96 秒、傷害交換翻號） |
| `pitchAltitudeGain` | 不動 | 「量不到」的**真正理由**（不在 `extend`），以及要量它需要什麼場景 |

**為什麼不動混沌的那些**：這個專案在 `unloadMargin` 上已經吃過一次「拿抽樣
當趨勢」的虧，它現有的註解就是那次的記錄。這次的掃描重現了同一個現象，
結論因此更強而不是更弱。

### 3.3 為什麼只有 `brakeCornerRatio` 算數

現行的預設設定（`unloadMargin` 1.15、`brakeCornerRatio` 1.6、`pitchSpeedGain`
4×EP）在高能量開局是「紅 561 : 藍 428」—— 藍方挨了 428。而**三個旋鈕的
單軸擾動都能改善它**（1.10 → 藍方 0、1.40 → 藍方 0、2×EP → 藍方 0）。

若只看「改善了沒」，會誤以為三個都該調。分野在**證據的形狀**：

- `unloadMargin` 與 `pitchSpeedGain` 的鄰格**互相矛盾**（往上往下都可能
  變好也可能變壞），那是混沌的簽名
- `brakeCornerRatio` 的 1.70~2.50 是**六個連續取值逐位元相同**，那不可能
  是抽樣 —— 它是「規則不再觸發」這件事本身

**平台是結構，單點是抽樣。** 這一份只採信平台。

## 4. 不做的

- **不動 `feel.ts` 的任何倍率。** 這一份是 AI 判準的校準，不是手感重調。
- **不刪 `speedRecoverMargin` 或它的分支。** 沒有影響力不等於錯；它是失速
  的第一道政策層，包絡再變時會重新生效。刪掉會讓下一次的人重寫它。
- **不為 `pitchAltitudeGain` 造新場景。** 要量它需要一個「AI 在低空且處於
  `extend`」的場景，而那個場景目前不存在。造一個是另一份的事，這一份把
  需求記下來就好。
- **不動 `extendPitch`（25°）、`speedRecoverPitch`（20°）、`maxOffsetAngle`
  （20°）。** 它們不在 `feel.ts` 點名的欠帳裡。

## 5. 驗收

### 5.1 主判準

`ai-duel-matrix` L4-C（今天剛依裁定改寫成「活得下來且交換有利」）在
`brakeCornerRatio = 1.8` 下必須**更好**：由「逾時 200 s、紅 561 : 藍 428、
藍方剩 57%」變成「藍勝 156 s、紅 1000 : 藍 0、藍方剩 100%」。

### 5.2 護欄

`ai-manoeuvre` 六場的五條指標不得退化。預期**逐位元不變**
（1.6 與 1.8 在那六場相同），所以任何變化都值得追查。

### 5.3 回歸

- 全套 `npx vitest run --exclude "**/perf-gate**" --exclude "**/rematch**"`
- `perf-gate` 與 `rematch` 單獨複測（並行下會假紅）

### 5.4 事先講好的否決條件

以下任何一條成立，**`brakeCornerRatio` 退回 1.6**，只留註解回填：

- `ai-manoeuvre` 任何一條護欄變紅
- L4-C 在新判準下變差（沒擊落、或藍方剩餘 hp 低於現在的 57%）
- 其他測試出現紅燈而根因指向這個改動

**護欄重新定值是專案負責人的決定，不是實作者的。** 紅了先量、先報告、先問。
