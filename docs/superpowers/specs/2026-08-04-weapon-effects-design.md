# M7 武器特效 —— 槍焰、命中火花、入海水柱

**日期**：2026-08-04
**前置**：M2（武器、彈道、命中判定）、M5（20v20）、M6（編隊）

---

## 1. 目標與範圍

補上三個 M2 當時被砍掉的視覺回饋：

| 特效 | 觸發 | 一句話 |
|---|---|---|
| 槍焰 | 某一管槍擊發 | 槍口一閃 |
| 命中火花 | 彈丸打中飛機 | 沿**被打中那個面的法線**噴開的一小撮火星 |
| 入海水柱 | 彈丸打到海面 | 一根白色水柱抽起後落下 |

**全部按真實比例，不加螢幕尺寸下限。** 這一條是專案負責人裁決，理由見 §8。

### 1.1 一併補上的缺漏

彈丸目前**完全不理海面** —— 它只會活滿 `PROJECTILE_LIFETIME`（1.2 s）然後消失，中間可以穿過水面繼續飛。水柱這個特效需要一個入海事件，而那個事件本來就該存在：水面下的彈丸打不到任何東西（飛機在 `y <= 0` 就墜毀退場了）。

所以本里程碑順便補上「入海即回收」。§4 證明它**不可能改變任何命中結果**。

## 2. 架構：三個特效不共用一套機制

這是本 spec 最主要的判斷。三者的**錨點**不同，硬套同一套會有一個做得很差。

### 2.1 槍焰 —— 每管的計時器，位置在渲染時重算

`World.fire()` 在某一管 `shots > 0` 的那一步，把該管的計時器設成 `FLASH_SECONDS`；每個物理步遞減。渲染層讀計時器，槍口的世界位置由**內插後**的機體姿態重算：

```
槍口 = mount.position 套上 visual.quaternion，再加 visual.position
```

**【為什麼不用事件】** 事件會帶著**物理子步**的位置，而畫面上的飛機畫在**內插後**的位置（`Visual.position` / `Visual.quaternion`，`alpha ∈ [0,1)`）。兩者差一個子步的位移 —— 200 m/s 下是 0.83 m。槍焰會相對機身前後抖動接近一個機身長度。重算則永遠焊在槍口上。

**【它同時解決取樣不匹配】** 物理 240 Hz、畫面可能只有 60 Hz。一管 M2 是 800 rpm = 每 75 ms 一發，落在哪一個子步不確定；用事件的話，一幀跑 4 個子步而只在最後一步排空，就會漏掉前 3 步的擊發。計時器沒有這個問題 —— 它是一個**狀態**而不是一個瞬間。

**【計時器住在 World 而不是渲染層】** 它記的是「這一管距離上次擊發多久」，那是物理事實不是畫面參數。渲染層決定它長什麼樣子。與 `cooldowns`（射速時鐘）住在同一個地方，同一個理由。

### 2.2 命中火花與入海水柱 —— 事件緩衝，每個子步排空

火花一噴出就與飛機脫鉤，水柱則錨在海面上的一個定點 —— 兩者都**沒有可以重算的錨點**，只能用事件。

`World` 持兩個定長 SoA 緩衝：

```ts
interface HitEvents  { x, y, z, nx, ny, nz: Float32Array; count: number }
interface SplashEvents { x, z: Float32Array; count: number }
```

`resolveHits()` 追加，**主迴圈的子步回呼**裡排空。

**【為什麼是子步回呼而不是幀尾】** `main.ts:210` 已經為 `hitsDealt` 寫過這個理由：「`World.step` 在每個物理步開頭把它歸零，而一幀可能跑好幾步。若在幀尾才讀，最後一步沒命中就整幀不閃」。新的事件走同一個位置、同一個理由。排空之後緩衝清空，所以容量只需要覆蓋**一個子步**。

**【為什麼是兩個緩衝而不是一個帶 kind 旗標的】** 消費者不同（火花池 vs 水柱池），資料也不同（火花要法線，水柱只要水平座標）。合成一個會讓兩個消費者都得先過濾一次，而過濾的成本正好等於分開存的成本。

### 2.3 為什麼不用回呼

`World` 目前完全不知道渲染層存在。注入回呼會讓每一個 headless 測試都得準備一個樁，而 `World` 有 288 組矩陣測試在 node 裡跑。事件緩衝維持這條界線。

## 3. 命中法線

### 3.1 從 slab 測試取出來

`segmentBox` 是標準的 slab 測試：三個軸各求一次進入／離開參數，`tMin` 取最大。**最後抬高 `tMin` 的那一軸就是入射面所在的軸**，而從低面還是高面進去由方向分量的正負決定：

```
d > 0（沿 +axis 前進）→ 從低面進入 → 法線 = −axis
d < 0                  → 從高面進入 → 法線 = +axis
```

實作上只要在 `if (t0 > tMin) tMin = t0` 那一格順便記下軸與正負號。**這是六次迴圈裡多兩個賦值**，不是新的計算。

### 3.2 三件容易寫錯的事

**【法線要取與 `t` 同一個盒】** `hitAircraft` 對每個命中盒各跑一次 `segmentBox`，`t` 取最近、倍率取最高（M2 spec 的裁決：命中盒是巢狀的，倍率取最近的話座艙的 ×2.5 永遠選不到）。法線必須跟著 **`t`** 走，不能跟著倍率走 —— 跟著倍率會拿到內層盒的面，而外層盒才是彈丸真正先碰到的表面。

**【機體座標要轉世界】** 盒子定義在機體座標系，法線也是。噴出來的火星在世界座標飛，所以要套上機體姿態。

**【起點落在盒內時沒有入射面】** `tMin` 保持 0，三個軸都沒有抬高過它。這時候沒有「入射面」這個東西。備援：**用 −彈丸方向**（迎面噴回去）。

`HitResult` 因此多三個欄位：`nx, ny, nz`（機體座標的單位向量），起點在盒內時三者為 0，呼叫端據此走備援。

## 4. 入海偵測與回收

### 4.1 判準

`Projectiles` 已經同時保有線段起點（`sx, sy, sz`）與終點（`x, y, z`）—— 那是 M2 為了「一步走 3.7 m 不能用點判定」而存在的。入海就是這條線段跨過 `y = 0`：

```
sy > 0 且 y <= 0  →  入海
交點參數 t = sy / (sy − y)
撞擊點 = (sx + t·(x − sx), 0, sz + t·(z − sz))
```

判定放在 `resolveHits()` 既有的彈丸迴圈裡，**排在飛機命中之後**：同一步裡先撞到飛機的彈丸不該再生一根水柱。

### 4.2 海面高度取 0

與 `World` 預設的 `SEA_LEVEL` 墜毀判定（`position.y <= 0`）同一個數字。**兩者是同一個事實**，若未來有地形高度，必須一起改 —— 分開的話會出現「飛機撞地了但彈丸還在地下飛」。

### 4.3 它不可能改變任何命中結果

彈丸沒有重力（`Projectiles.step` 只積分等速），所以垂直速度分量恆定：**往下穿過水面的彈丸不可能再上來**。而水面下沒有可以打的目標 —— 飛機在 `y <= 0` 就墜毀退場了。

所以「入海即回收」只會讓存活彈丸變少，不會少算任何一次命中。這一條要有測試守著（§12）。

## 5. 槍焰

### 5.1 狀態

`Combatant` 增加 `muzzleFlash: Float32Array`（長度 = 該機的掛架數）。`World.fire()` 在 `shots > 0` 時設為 `FLASH_SECONDS`，`World.step` 每步對所有掛架遞減至 0。

**【換機種要一起重建】** `C` 鍵會換機種，而兩台的掛架數不同（P-51D 六挺、Bf 109 三挺）。`World` 換 spec 的那條路徑已經在重建 `cooldowns` 與 `hitRadius` —— `muzzleFlash` 必須加進**同一個地方**。漏掉的話陣列長度與掛架數對不上，多出來的那幾格會變成永遠不熄的槍焰。

### 5.2 外觀

一個 `InstancedMesh`，容量 = 架數 × `MAX_MOUNTS`（8）。每個實例對應一個掛架：

**【`MAX_MOUNTS` 必須有測試守著】** 它是一個容量上界，而不是一個描述。某天有人加一台九挺槍的飛機，第九挺的槍焰會**靜靜地畫不出來**。測試要斷言「所有機種的掛架數都 ≤ `MAX_MOUNTS`」—— 與 `createFlights` 檢查 `index === 陣列位置` 是同一類的守門。

- 位置：內插姿態下的槍口
- 朝向：`mountDirection`（既有函數，匯聚幾何已經算好）套上內插姿態
- 縮放：`計時器 / FLASH_SECONDS`，為 0 時縮成 0（畫不出東西，不必另外剔除 —— `tracers.ts` 的做法）
- 幾何：短錐，長 ~0.6 m、底半徑 ~0.12 m，加法混合的橘白色

**【為什麼是錐而不是廣告板】** 廣告板恆面向相機，從正側面看槍焰會是一個圓片而不是一條噴出來的火舌。錐狀在世界座標裡有方向，從哪個角度看都對。這與 `tracers.ts` 選世界空間幾何而不是線段是同一個判斷。

### 5.3 `FLASH_SECONDS = 0.03 s`

**兩個界夾出來的**：

- **下界 16.7 ms**：60 fps 的一幀。閃得比一幀短就會被抽樣漏掉 —— 有時看得到有時看不到，那比沒有更糟。30 ms 橫跨 1.8 幀，保證每次擊發至少畫到一幀。
- **上界 67 ms**：全場最快的一管是 Bf 109 的 MG 131（900 rpm）。工作週期 30/67 = **45%**，讀起來是**閃爍**；若取到 60 ms 以上就變成一盞常亮的燈，那是錯的視覺。

P-51D 的 M2 是 800 rpm = 75 ms 一發，工作週期 40%，同樣落在閃爍區間。

## 6. 命中火花

### 6.1 發射

每個命中事件噴 `SPARKS_PER_HIT = 8` 顆，方向落在法線周圍 `SPARK_CONE = 35°` 的錐內，初速 `SPARK_SPEED = 25 m/s`。

**【方向必須是決定性的，不能用 `Math.random()`】** 與 `battle/setup.ts` 的 `altitudeOffset` 避開亂數同一個理由：亂數要嘛需要一顆種子與一個 PRNG，要嘛就毀掉可測試性。這裡用**粒子索引的雜湊**：

```ts
function sparkDirection(nx, ny, nz, index, out: Vector3): void
```

純函數、決定性、可以斷言「輸出恆為單位向量」「與法線的夾角恆 ≤ SPARK_CONE」。

### 6.2 運動

```
v ← v · exp(−DRAG · dt) + g · dt      DRAG = 6 s⁻¹、g = −9.80665 m/s²
p ← p + v · dt
壽命 SPARK_LIFE = 0.2 s，透明度隨剩餘壽命線性淡出
```

**【在渲染幀率積分，不在物理步】** 火花是純裝飾，不參與任何判定，也不需要決定性。放進物理步只會讓 240 Hz 白算四倍。

**【阻尼 6 s⁻¹ 從哪來】** 時間常數 1/6 = 0.17 s，與壽命 0.2 s 同量級 —— 火星在死掉之前速度掉到約 1/e，看起來是「噴出去然後慢下來」而不是「等速飛走然後消失」。

### 6.3 外觀

沿速度方向拉長的細段（與曳光彈同一種幾何與同一個理由），長 `0.3 m`、半徑 `0.02 m`。池子 512 顆，**環形緩衝、滿了覆蓋最舊的**。

**【為什麼是覆蓋最舊而不是丟棄新的】** 最舊的正好是最淡的那一顆，覆蓋看不出來；丟棄新的則會在密集命中時整批不見 —— 而那正是最該看到火花的時候。

### 6.4 距離剔除

超過 `SPARK_CULL = 800 m` 的命中事件**不發射**。推導見 §8：0.3 m 的火星在 800 m 上是 0.64 px，次像素，看不見。剔除在**渲染層的 `emit()`** 裡做，因為只有那一層知道相機在哪裡 —— `World` 不需要知道有相機這回事。

## 7. 入海水柱

### 7.1 外觀與運動

白色圓柱 `InstancedMesh`，池子 256 格、環形緩衝。

```
高 SPLASH_HEIGHT = 4 m、半徑 SPLASH_RADIUS = 0.25 m
壽命 SPLASH_LIFE = 0.5 s
高度縮放：前 30% 的壽命抽到滿高，之後線性落回 0
透明度：後 50% 的壽命線性淡出
```

底部固定在 `y = 0`（幾何以底面為原點，只縮放 Y）。

### 7.2 不需要距離剔除

彈丸壽命 1.2 s × 最快初速 887 m/s = **最多飛 1,064 m**。所以射手離水柱恆在 1 km 之內，而相機通常就在射手附近。4 m 的水柱在 1 km 上是 6.8 px —— 一定讀得到。

### 7.3 它天然稀有

同一條算式的另一面：在 4,000 m 高度**平射**的子彈永遠碰不到海面。水柱只在低空纏鬥時出現 —— 而那正是它有意義的時候。這不是缺陷，是自己就收斂的設計。

## 8. 可見距離與尺寸（總表）

`tracers.ts` 已經定過角解析度：1920 px 寬、65° 視野 → 每像素 **5.9 × 10⁻⁴ rad**。一個像素對應的世界長度是 `5.9e-4 × 距離`：

| 距離 | 1 px = | 槍焰 0.6 m | 火星 0.3 m | 水柱 4 m | 曳光 14 m |
|---|---|---|---|---|---|
| 100 m | 0.059 m | 10 px | 5.1 px | 68 px | 237 px |
| 300 m | 0.18 m | 3.4 px | 1.7 px | 23 px | 79 px |
| 800 m | 0.47 m | 1.3 px | **0.64 px** | 8.5 px | 30 px |
| 1,000 m | 0.59 m | **1.0 px** | 0.51 px | 6.8 px | 24 px |
| 4,000 m | 2.36 m | 0.25 px | 0.13 px | 1.7 px | 5.9 px |

### 8.1 為什麼不加螢幕尺寸下限

專案負責人裁決：三個特效**全部按真實比例**。

先前曾考慮把槍焰當成「戰場資訊」（公里級距離仍讀得出誰在開火）並為它加一個螢幕像素下限，做法在本專案有先例 —— `contacts.ts` 的目標框就有 `BOX_MIN = 9 px` 的下限。**推翻它的理由是：那個訊號已經有人扛了。**

看上表最後一欄：一條曳光彈在 1 km 上仍有 **24 px 長**。線狀物在遠距離比點狀物耐看得多 —— 粗細只有 0.4 px，但長度撐住了可讀性。「誰在對誰開火」這件事曳光彈已經回答了，槍焰再去扛同一件事是**兩個訊號回答同一個問題**，而本專案在 M6 才因為類似的問題吃過虧（兩個對「誰在威脅誰」的答案）。

定案：

> **曳光彈是遠距離的開火訊號，槍焰是近距離的裝飾。**

所以槍焰有效範圍約 300 m 之內、火花約 300 m 之內、水柱約 2 km 之內。這是接受的設計結果，不是缺陷。

## 9. 渲染層的共同紀律

三個特效各是**一個** `InstancedMesh`，也就是總共 3 個 draw call。沿用 `tracers.ts` 已經立下的四條：

1. 整池共用一份幾何與一份實例矩陣緩衝，建立時就配足容量，之後每幀只寫入不重配
2. 空槽位縮放到 0 —— 畫不出東西，也不必另外剔除
3. `frustumCulled = false` —— 包圍球是建立時算的（全部在原點），開著的話相機一離開原點附近整批會一起消失
4. 熱路徑零配置：模組私有的暫存，索引迴圈

**【為什麼不共用一個 InstancedMesh】** 三者的幾何不同（錐、細段、圓柱）。`InstancedMesh` 一個實例只能換變換矩陣，換不了幾何。

## 11. 效能

### 11.1 熱路徑被動到兩次

`resolveHits` 是 20v20 效能閘門量的東西，本里程碑對它做了兩件事：

- **法線抽取**：六次 slab 迴圈裡多兩個賦值，加上命中時一次四元數旋轉（只在真的命中時發生，不是每個候選）
- **入海判定**：每個存活彈丸多一次比較（`sy > 0 && y <= 0`）

前者近乎免費，後者是 4,000 次比較/步。**20v20 閘門必須重測並重新推導**，規則與 M6 §11 相同：獨立量三次、預算取觀測上界之上的整百、門檻取預算的三倍。M6 的實測是 208.7 / 216.1 / 245.1 µs，預算 300、門檻 900。

**【入海回收會讓它變快，不是變慢】** 存活彈丸變少 → 粗篩的視窗更稀疏。但 `bench/multi-load.ts` 每步把彈丸池補滿到 `PROJECTILE_CAPACITY`，所以**閘門量到的負載是合成的、不受影響** —— 這一點 M6 已經確認過。

### 11.2 渲染側不在閘門內

`bench/multi.bench.ts` 是 headless 的 `World.step`，不含渲染。三個粒子系統的成本由**瀏覽器人工驗收**把關：40 架齊射時 FPS 與 draw call 不得明顯劣化（M5 的基準是 238–483 FPS、30 個 draw call；本里程碑加 3 個 draw call）。

## 12. 測試策略

判斷一律抽成純函數再測 —— 繪製函數與 `main.ts` 都進不了單元測試。這是 `edgeIndicatorPosition`、`minimapSymbol`、`countdownLabel`、`contactColor` 都用過的做法。

| 測試 | 守什麼 |
|---|---|
| `hit-normal`：六個面各射一次 | 法線的軸與正負號正確、已轉到世界座標 |
| `hit-normal`：巢狀盒 | 法線來自**最近的** `t` 那個盒，不是倍率最高的那個 |
| `hit-normal`：起點在盒內 | 回報「無法線」（三分量為 0），呼叫端走備援 |
| `sea-impact`：線段跨過 y = 0 | 交點的內插正確、彈丸被回收 |
| `sea-impact`：**入海回收不改變任何命中** | 開／關兩種設定下，20v20 的命中與傷害逐位元相同 |
| `sparkDirection` | 恆為單位向量、與法線夾角 ≤ 錐角、同索引恆給同方向 |
| 火花步進 | 粒子會死、不產生 NaN、環形緩衝覆蓋最舊的 |
| 水柱曲線 | 高度先漲後落、透明度單調遞減、壽命結束縮成 0 |
| 三個 `InstancedMesh` | 1 個 draw call、容量預配、空槽縮成 0（照 `tracers.test.ts` 四條） |
| `MAX_MOUNTS` | 所有機種的掛架數都 ≤ 它 —— 否則多出來的槍焰靜靜地不畫 |
| 換機種 | `muzzleFlash` 陣列跟著重建，長度等於新機種的掛架數 |
| 20v20 整合 | 兩個事件緩衝從未溢位 |
| 20v20 效能閘門 | 重新校準（§11.1） |

**不寫「看起來好不好看」的測試。** 那是人工驗收。

## 13. 驗收條件

### 13.1 自動

1. 六個面的入射法線都正確，且已轉到世界座標
2. 法線取自最近的 `t` 那個命中盒
3. 起點在盒內時回報無法線
4. 彈丸跨過 `y = 0` 時被回收，交點內插正確
5. **入海回收不改變任何一次命中或傷害**（逐位元）
6. `sparkDirection` 恆為單位向量、恆在錐內、決定性
7. 火花與水柱不產生 NaN，壽命結束都縮成 0
8. 三個特效各只有一個 `InstancedMesh`
9. 20v20 跑滿 150 秒，兩個事件緩衝從未溢位
10. 20v20 效能閘門重新校準後全綠，且連跑三次不飄

### 13.2 人工（專案負責人執行）

11. 開火時槍口有短促的閃，是**閃爍**不是常亮的燈
12. 槍焰焊在槍口上，不隨機動抖動
13. 打中敵機時看得到火花**從被打中的那個面**噴開
14. 低空對海射擊時看得到白色水柱抽起又落下
15. 40 架齊射時畫面不吵、FPS 與 draw call 沒有明顯劣化

## 15. 風險

| 風險 | 對策 |
|---|---|
| **法線取錯盒** —— 巢狀命中盒下拿到內層的面 | 專屬測試（§12）。這與 M2「倍率取最近導致座艙 ×2.5 是死碼」是同一類缺陷 |
| **入海回收悄悄改變命中** | §4.3 有證明，且有逐位元的回歸測試 |
| **槍焰工作週期太高變成常亮** | §5.3 的上界推導；人工驗收條件 11 |
| **40 架齊射時畫面太吵** | 三個特效都按真實比例、無螢幕下限，遠距離自然消失；人工驗收條件 15 |
| **效能閘門在錯的區間重測** | 與 M6 §11 同一條規則：獨立量三次，且若新預算更低就必須跟著調低 |
| **火花在低幀率下跳格** | 它在渲染幀率積分，dt 就是幀時間；壽命 0.2 s 在 30 fps 下仍有 6 幀 |

## 16. 明確不做（記錄在案）

| 項目 | 理由 |
|---|---|
| 擊落的爆炸火焰與殘骸模型 | M5、M6 已延後，不變 |
| 動態光源（槍焰照亮機身） | 40 架會有幾百個光源，而本專案的場景用的是無光照材質 |
| 硝煙、彈殼拋出 | YAGNI。三個特效已經回答了「我在開火」「我打中了」「我打偏了」 |
| 彈著點在機身上留彈孔 | 需要貼圖或幾何修改，與程序化機體幾何衝突 |
| 命中的音效 | 本專案目前完全沒有音訊子系統 |
| 水面漣漪與泡沫 | 水柱已經回答「彈著在這裡」；漣漪要改海面著色器 |
