# 甜蜜區偏置的射擊讓位 —— 設計

**日期**：2026-08-16
**狀態**：待專案負責人審
**動到的層**：`src/ai/steer.ts`（單一消費點）

---

## 1. 問題

### 1.1 人工回報（2026-08-16）

> 用 Bf 109 按 I 讓 AI 代飛,正前方約 150 m 有一台敵機（預瞄點幾乎跟敵機連在一起）,
> 預瞄點在我的下方約 15 度,我的飛機並沒有向下瞄準他。敵機在我面前爬升、預瞄點縮到
> 5 度,我機也沒有向下瞄準。

### 1.2 靜態根因

`steerCommand` 算完瞄準方向後,倒數第二層是甜蜜區偏置（最後一層是撞地底限）：

```ts
if (intent !== 'rally') applyPitchBias(sit.sweetPitch, out.aimWorld)
```

`applyPitchBias` 把命令的**航跡角**整個加一個角度,水平方位不動。

`sit.sweetPitch` 由 `doctrine.ts` 的 `sweetSpotPitch(self.spec, target.spec, altitude, tas)`
算出。它的輸入只有**機種對、高度、空速**三項 —— **不看距離、不看瞄準誤差、不看有沒有
射擊解**。

109 對 P-51（套 `GAME_FEEL`）的實測值：

| 高度 | 350 km/h | 400 | 450 | 500 以上 |
|---|---|---|---|---|
| 2000 m | +4.8° | +10° | +10° | +10° |
| 4000 m | 0° | +3.8° | +7.9° | **+10°** |

正號 = 抬頭。方向本身正確：109 的甜蜜區在 350 km/h 附近,飛太快時該用高度換迴旋率。
**問題不在方向,在於它沒有讓位機制。**

### 1.3 平衡點：偏置 ÷ 拉桿係數

命令的航跡角 = −(下瞄角 × `pullCeiling`) + `sweetPitch`。

500 km/h 時 `pullCeiling = 1.00`,所以**下瞄角要超過 10° 命令才是負的**。低於 10° 的
下瞄需求被完全吃掉,甚至反向。

`test/tools/nose-bias.probe.ts` 複現（109 交 AI、敵機 150 m 正前方爬升 10°）：

```
開局：預瞄點在下方 15°、500 km/h        開局：預瞄點在下方 5°、500 km/h
   t   偏置  拉桿  預瞄點在機首下方         t   偏置  拉桿  預瞄點在機首下方
 0.00 10.0°  1.00        13.7°           0.00 10.0°  1.00         3.1°
 2.50 10.0°  1.00         9.4°           2.00 10.0°  1.00        11.8°
 6.00 10.0°  1.00        10.0°  ← 收斂    6.00 10.0°  1.00         9.9°  ← 同一點
```

**兩個開局收斂到同一個平衡：預瞄點永遠停在機首下方 10°。**

對照組 320 km/h（偏置 = 0）同樣幾何下 AI 正常低頭追擊,一路壓到 −45° —— 機制確認。

### 1.4 後果比「瞄不準」嚴重

`DEFAULT_FIRE.trackingCone = 3°`（`shouldFire` 的第四條）。平衡點是 10°。

**那個態勢下 AI 結構上永遠開不了火。**

2026-08-15 人工回報過「命中產出下降」,當時歸因為「會閃躲所以打不到」。**那個歸因不
完整** —— 這一條是獨立的、與閃躲無關的成因。

### 1.5 這個值當初就沒定下來

`sweetSpotMaxPitch = 10 * DEG` 的註解寫著「**Task 7 掃描定值**,候選 5°／10°／15°／20°。
起手值取 10°」。翻 2026-08-11 spec §7.2：

> **掃了,但掃不出來** —— 0 / 5° / 10° / 15° / 20° 五個值對每一個判準都非單調,現有
> 測試組沒有一個指標解析得出這個尺度的改動。唯一一致的訊號是 20° 的 `fireShare` 與
> `onNose` 同時低於關閉基準 —— **偏太多會開始放掉射擊解**,與設計預期相符,所以 20° 排除。

**當時就看到這個失效模式了**,只是在 20° 才顯著到能被 20v20 的統計指標看見。10° 在
統計上被洗掉,但在單挑近戰是致命的。

## 2. 目標與非目標

**目標**

1. AI 在**射擊機會已經到手**時,甜蜜區偏置不得阻止它把機首帶上預瞄點。
2. 遠距離（還在進場、還在找位置）時,這一層維持現有強度 —— 不是把功能廢掉。
3. 連續,沒有翻轉點。

**非目標**

- 不改 `sweetSpotPitch` 本身的方向或大小算式。
- 不改 `sweetSpotMaxPitch`（那是護欄重新定值,專案負責人的決定,而且 §1.5 已證實掃不出來）。
- 不碰 `defendPitchBias`（破防路徑另有一層,不在本輪範圍）。
- 不碰 `pullCeiling` / `unloadPull`。

## 3. 三個做法與取捨

| | 做法 | 否決／採用理由 |
|---|---|---|
| 甲 | 調小 `sweetSpotMaxPitch` | **否決。** 平衡點 = 偏置 ÷ 拉桿係數,**任何非零上界都有一個平衡偏移**。改成 3° 時平衡點就是 3°,剛好等於開火錐,還是卡在邊緣。而且它同時削弱這一層在遠距離真正有用的地方。治標。 |
| 乙 | **有射擊解時讓位** | **採用。** 見 §4。 |
| 丙 | 只在 `extend` 意圖生效 | **否決。** 等於刪掉這個功能 —— `extend` 已經有 `extendPitchAngle` 在做低頭換速度,兩者重複。用一個近戰個案廢掉一份審過的設計,代價不成比例。 |

---

## 4. 採用的做法

### 4.1 原則

這個 codebase 已經寫死的優先序原則,在 `applyFloor` 的註解裡：

> 底限的優先序最高,必須有最後決定權 ——「想低頭換速度」不能贏過「快撞海了」

同一句話換個對象：**「我想把仗帶到我的甜蜜區」不能贏過「射擊解已經到手了」。**

甜蜜區偏置的用途是**把仗帶到哪裡打**,那是進場與脫離時的事。咬住了就不該再想。

### 4.2 閘門**不能**掛在瞄準誤差上 —— 回授鎖死

直覺寫法是「瞄準誤差小於 N 度就把偏置收掉」。**那會鎖死。**

平衡點是 10°。閘門若設在 5°,系統永遠停在 10° —— 進不了 5°,閘門永遠不開,偏置永遠
滿的。**閘門必須比平衡點更寬才會收斂**,而平衡點隨高度、空速、`pullCeiling` 飄,那個
門檻就得跟著飄。脆弱。

**閘門要掛在偏置控制不到的量上。**

### 4.3 掛在哪：`basis.interceptTime`

`shouldFire` 的四個條件裡,前三條都與機首無關：

1. 有彈道攔截解,且彈丸活得夠久（`interceptTime` vs `PROJECTILE_LIFETIME`）
2. 距離不能太近（`minRange`）
3. 視線角速度不能太大（`losRate`）

只有第四條看機首。**取第一條當閘門的自變數,沒有回授迴路。**

只取第一條、不取另外兩條的理由：
- `interceptTime` 直接回答「我的子彈現在飛得到那裡嗎」,那正是「射擊機會」的定義。
- 另外兩條會多帶兩個常數,而 §1.5 已證實現有測試組解析不出這個尺度 —— 多的常數定不了值。YAGNI。

### 4.4 形狀：連續斜坡,不是開關

這個檔案已經有三次「裸門檻造成極限環」的教訓寫在註解裡（`extendPitchAngle` 在 1000 m
線上震盪 40 秒、`unloadPull` 的抖動、`geometryGate` 在門檻上翻來翻去）。結論寫在
`extendPitchAngle`：**連續函數沒有翻轉點**。

```
sweetYield(t) =
  t === NO_INTERCEPT        → 1     沒有射擊解,沒有東西要讓
  sweetYieldTime <= 0       → 1     這一層關閉（消融用）
  t >= sweetYieldTime       → 1     子彈飛不到,等於沒有機會
  否則                       → t / sweetYieldTime      線性
```

`sweetYieldTime` 的起手值取 `PROJECTILE_LIFETIME = 1.2`。**與 `shouldFire` 的第一條用
同一個數字,不新增第二套尺度** —— 那是 `applyFloor` 與 `extendPitchAngle` 共用
`clearanceScale` 的同一個手法。

### 4.5 實際效果（109 vs P-51、4000 m、500 km/h,實測 `interceptTime`）

| 距離 | `interceptTime` | 讓位係數 | 偏置由 10° 變成 | 平衡偏移 vs 開火錐 3° |
|---|---|---|---|---|
| 100 m | 0.142 s | 0.12 | **1.2°** | 過 |
| 150 m | 0.213 s | 0.18 | **1.8°** | 過（人工回報的那一格） |
| 300 m | 0.426 s | 0.35 | 3.5° | 略高於錐 |
| 600 m | 0.851 s | 0.71 | 7.1° | — |
| 800 m | 1.135 s | 0.95 | 9.5° | — |
| 1000 m | 1.418 s | 1.00 | 10.0° | —（`shouldFire` 第一條本來就已經擋掉） |

人工回報的 150 m 由 10° 降到 1.8°,低於開火錐,問題解除。遠距離幾乎不動,功能保留。

**300 m 那一格的平衡偏移 3.5° 仍略高於開火錐** —— 這是刻意的取捨,見 §7.1。

## 5. 介面

### 5.1 新增純函數（`src/ai/steer.ts`）

```ts
export function sweetYield(interceptTime: number, cfg: SteerConfig = DEFAULT_STEER): number
```

回傳 0..1。放在 `steer.ts` 而不是 `doctrine.ts` 的理由：**它表達的是「這一層什麼時候
該讓位」,是轉向層的優先序仲裁規則**,與 `applyFloor`／`floorPitchAngle`／
`shrinkTowardNose` 同一族,不是打法政策。消費點也在這裡。放進 `doctrine.ts` 會多一條
`steer → doctrine` 的相依邊,而 `steer.ts` 已經 import 了 `NO_INTERCEPT`。

### 5.2 新增設定欄位（`SteerConfig`）

```ts
/**
 * 甜蜜區偏置的讓位時間尺度,秒。彈道飛行時間短於它時偏置按比例收掉。
 * 0 = 這一層關閉（消融用）。
 */
sweetYieldTime: number
```

`DEFAULT_STEER.sweetYieldTime = PROJECTILE_LIFETIME`（需在 `steer.ts` 新增一條
`import { PROJECTILE_LIFETIME } from '../world/Projectiles'`,讓兩個數字不會漂開）。

### 5.3 消費點（唯一,`steerCommand`）

```ts
- if (intent !== 'rally') applyPitchBias(sit.sweetPitch, out.aimWorld)
+ if (intent !== 'rally') {
+   applyPitchBias(sit.sweetPitch * sweetYield(basis.interceptTime, cfg), out.aimWorld)
+ }
```

`basis` 已經是 `steerCommand` 的參數,不必改簽名。

## 6. 測試策略

### 6.1 純函數單元測試（`test/unit/steer.test.ts` 或既有對應檔）

| 案例 | 期望 |
|---|---|
| `NO_INTERCEPT` | 恰好 1 |
| `t >= sweetYieldTime` | 恰好 1 |
| `t = 0` | 恰好 0 |
| `t = sweetYieldTime / 2` | 恰好 0.5 |
| `sweetYieldTime = 0` | 恰好 1（關閉） |
| 單調不減 | 掃 0..2 s,後一格 ≥ 前一格 |
| 值域 | 掃 −1..3 s,結果一律在 [0, 1] |

### 6.2 主判準：人工回報的場景（新測試檔）

把 `nose-bias.probe.ts` 的場景收斂成護欄：109 交 AI、敵機正前方 150 m、預瞄點在下方
15°、我機 500 km/h、敵機爬升 10°,跑 6 秒。

**判準：最後一秒的「預瞄點在機首下方」中位數必須小於 `DEFAULT_FIRE.trackingCone`。**

錨在既有常數上,不是照著改完的現況畫靶（2026-08-13 spec §7.5 的第三次教訓）。意思很短：
**AI 必須能把機首帶到扣得下扳機的位置。**

**同時要有一條會失敗的對照**：把 `sweetYieldTime` 設成 0（關閉這一層）跑同一場,斷言它
**大於** 開火錐。那條讓「這個缺陷是真的」可證偽 —— 若關閉與開啟沒有差別,代表判準沒有
量到這一層。

### 6.3 遠距離不得被改壞

同一支測試加一場 800 m 開局,斷言 `sweetYield` 在該格 > 0.9 —— 釘住「遠距離幾乎不動」
這個設計意圖。

### 6.4 全套回歸

跑完整測試組,逐條與 `main`／改動前比較。**任何護欄的重新定值都是專案負責人的決定**,
不由本輪自行放寬。

### 6.5 Playwright 驗收

現有 e2e 不覆蓋這條路徑,本輪不新增 —— 這是純 AI 內部行為,沒有可見的 DOM 判準。
最終驗收是專案負責人的試飛。

## 7. 已知取捨與未解

### 7.1 300 m 附近的平衡偏移仍略高於開火錐

線性斜坡在 `t = 0.36 s`（約 250 m）時給出 3°,等於開火錐。250~850 m 之間平衡偏移
仍高於錐。

**刻意不處理**,理由：
- 開火錐是**紀律**門檻不是物理門檻,那個距離上真正決定命中的是散佈與目標機動。
- 把斜坡調陡（例如 `sweetYieldTime` 取 2 × `PROJECTILE_LIFETIME`）能壓下去,代價是
  中距離幾乎廢掉這一層。
- `sweetYieldTime` 是一個明確的旋鈕,實作時會掃 1× / 1.5× / 2× 三個值並回填。**定值
  是專案負責人的決定**,以試飛為準。

### 7.2 `sweetSpotMaxPitch = 10°` 本身沒有實證依據

§1.5 已記載：掃了但掃不出來,留在起手值。本輪不動它 —— 讓位機制解決的是「該開火時被
擋住」,不是「10° 對不對」。後者需要一個解析得出這個尺度的判準,那是另一輪的事。

### 7.3 `defend` 路徑同時吃兩層俯仰偏置

`defendPitchBias` 與 `sweetPitch` 在 `intent === 'defend'` 時都會生效。是否重複、要不要
互斥,本輪沒查。列為未解。

### 7.4 P-51 的方向相反,同一個病

P-51 對 109 在 250~350 km/h 是 **−3.1 ~ −4.1°**（低頭,去換速度）。同樣不看射擊解,
所以慢速的 P-51 對付高於自己 4° 以內的目標時有同樣的病,只是幅度較小。本輪的修法對
兩台同時生效,不需要額外處理。
