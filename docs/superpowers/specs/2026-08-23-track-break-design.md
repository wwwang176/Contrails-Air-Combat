# 追不上就別追 —— 用視線角速度決定何時改為佈局

**一句話：AI 會在機頭物理上追不上預瞄點的時候，繼續全力追瞄，把高度與速度
全部繳在一個永遠收斂不了的轉彎裡。**

- 人工回報：2026-08-23，Bf 109 護送 He 111
- 判準的來源：專案負責人（真人飛行經驗）的原話，見 §2
- 實測：`test/tools/escort-trace.probe.ts`、`test/tools/slash-track.probe.ts`

---

## 1. 問題

### 1.1 專案負責人的原話

> 真人在飛行的時候，如果對方要從我下方穿越，穿越前我當然會壓低機頭瞄準敵人。
> 但當敵人越來越靠近時，我的機頭壓低速度跟不上預瞄點了（在我的視角中準星
> 跟不上預瞄點的移動），這時候我就會拉平並轉向方位，或是抬高 90 度轉方位
> （因為我有能量所以可以垂直抬高）。
>
> 之所以轉向的原因是**我要創造下一次瞄準敵人的機會**。

最後那一句決定了這份設計的性質：**這不是脫離，是換一種飛法繼續打。**

### 1.2 現況

AI 沒有任何一層在問「我的機頭追不追得上」。實測交會後那 20 秒：

| 意圖 | 佔比 | 瞄準解 |
|---|---|---|
| `approach` | 53.2% | `normalizeInto(basis.leadPoint, …)` —— **純預瞄追擊，沒有任何旋鈕** |
| `extend` | 24.5% | 卸載脫離（本文不碰） |
| `defend` | 20.5% | `defendAim`（本文不碰） |
| `engage` | **1.8%** | `aimFromKnobs` |

於是 AI 用 45~75° 坡度硬轉 18 秒，掉 800 m 高度，把距離由 330 m 拉開到
2295 m —— 轉是轉完了，但目標已經在 2.3 km 外。

### 1.3 這一份與前一份的關係

`2026-08-23-turn-plane-discipline-design.md`（迴轉平面的紀律）修的是同一個
回報，用的判準是**方位角**。實測結果：那一層在關鍵的 11 秒**逐位元無作用**
（方位角只有 8~23°，門檻 60°），而且打壞了 1v1 掠襲。**那份設計本文取代，
實作要移除**（見 §9.1）。

## 2. 判準

### 2.1 量

```
trackRatio = 視線角速度 ÷ 我此刻的瞬時轉彎率上限
```

**兩個量都是專案裡本來就有的：**

- `Situation.losRate` —— 註解逐字寫著「視線角速度，rad/s。**「跟不跟得上」的
  直接量度**」。目前只被 `fire.ts` 用來決定「要不要開火」，**沒有任何一層拿它
  決定要不要繼續追**
- `analysis/envelope.ts` 的 `instantaneousTurnRate(spec, altitude, tas)` ——
  取氣動與結構過載的較小者，`g·√(n²−1)/V`

### 2.2 為什麼是它，而不是前面三個被否決的量

| 判準 | 下場 |
|---|---|
| 比能量差（`energyAdvantage`） | 把高度與速度視為等價。追擊期間讀出「我贏」。**否決兩次** |
| 比超量功率差（`psSelf − psTarget`） | 同一個根因，而且在 −67~+44 震盪。**實測否決** |
| 方位角（預瞄點相對機鼻） | 目標在正前方時只有 8~23°，看不到問題。**實測否決** |
| **`trackRatio`** | 尖峰正好落在該收手的那一刻，其餘時候安靜 |

【它為什麼結構上不同】**無因次，而且分子分母各自自動適應**：分子由幾何決定
（距離近、橫向快就大），分母吃 `spec` + 高度 + 空速。換機種、換高度、換關卡
都不需要重訂。前三個要嘛是有因次的絕對值，要嘛把兩件事混成一個數。

【`instantaneousTurnRate` 用的是最大過載】所以 `trackRatio > 1` 的意思是
「**即使拉到極限也轉不過去**」—— 這是保守的方向，只在真正做不到時才成立。

### 2.3 用瞬時而不是持續轉彎率

`sustainedTurnRate`（Ps = 0 的最大轉速）在本文的場景**全程回傳 0**（撐不住），
拿它當分母整條線都是「追不上」。而「準星跟不跟得上」問的是**此刻拉得出多少
角速度**，那是瞬時量。

護送」這個問題的答案。

【1.5 也在同一個空隙裡】1.4 與 1.5 對非護送場景都是 0.0%，差別只在護送關
（4.5% vs 4.2%）。取 1.4 是專案負責人的起始裁定，待掃描與人工試飛定案。

## 4. 動作 —— 佈局，不是脫離

### 4.1 兩個旋鈕已經在表達那兩個動作

`Knobs` 是既有的型別：

```ts
/** −1 = 後置追擊、0 = 純追擊、+1 = 前置追擊（彈道預瞄點） */
leadLag: number
/** −1 = 壓到交戰平面下方、0 = 同平面、+1 = 拉到上方 */
vertical: number
```

| 原話 | 旋鈕 |
|---|---|
| 拉平並轉向方位 | `leadLag = −1`（後置追擊）—— 瞄他後方，需要的角速度立刻降下來 |
| 抬高 90 度轉方位 | `vertical = +1`（高 yo-yo） |

**「後置追擊 + 高 yo-yo」在空戰教範裡的用途就是佈局下一次射擊機會。**

### 4.2 上下由能量決定，而且是連續的

```
vertical = smoothstep(zoomEnter, zoomFull, cornerRatio)
```

【為什麼用 `cornerRatio` 而不是比能量】`cornerRatio = TAS ÷ 角落速度` 是這個
專案既定的「我還打得動嗎」判準，它問的是「**現在**拉得動嗎」而不是「帳面上
有多少本錢」。比能量在這個專案已經被否決兩次（§2.2）。

`cornerRatio ≥ zoomFull` = 速度有餘裕 → 抬高換高度；
`cornerRatio ≤ zoomEnter` = 速度見底 → 水平轉，別再拿速度換高度。
中間連續，不會跳。

【`leadLag` 為什麼不連續】後置的目的是把需要的角速度降下來，而觸發條件本身
就已經是「降不下來」。給滿是對的；要調的是**保持多久**（§5），不是深淺。

## 5. 閂鎖 —— 因為觸發只有 1.7 秒

### 5.1 實測

連續超過 1.4 的**最長一段只有 1.7 秒**（護送關全場的總時間 7.8 秒）。

直接讀瞬時值的話：AI 會佈局 1.7 秒、然後立刻切回追瞄、再觸發、再切回 ——
機首每兩秒抖一次。**這一層一定要閂鎖。**

### 5.2 生命週期

```
未閂 → 閂上：  trackRatio > trackEnter
閂上 → 釋放：  trackRatio < trackExit 連續維持 trackHold 秒
```

【為什麼釋放要計時而不只是遲滯】遲滯（`latch(active, value, enter, exit)`）
處理的是門檻附近的抖動；這裡的問題是**訊號本身就很短**。佈局是一個要花
好幾秒走完的動作，不能訊號一掉就中止。兩者疊加：先要低於 `trackExit`，
還要連續維持 `trackHold` 秒。

【上限也要夾】護送關全場量到的最大值是 **20.15**（極近距離擦身，分母趨近
0）。`trackRatio` 要夾在 `trackCap` 以內，否則它乘進任何東西都會爆掉。

## 6. 接線位置 —— 這一節是本文與前一份最大的差別

### 6.1 不加第六層後處理

`steerCommand` 尾端的後處理鏈有一條紀律：**每一層只能動一個東西**
（縮誤差／改航跡角／改方位，三選一）。而「後置追擊 + 高 yo-yo」是**換一個
瞄準點**，同時動方位與航跡角 —— 它不屬於後處理鏈，屬於**瞄準點的選擇**。

前一份設計（迴轉平面）加了第五層，實測無效。本文不重蹈。

### 6.2 接在意圖分支裡，只碰兩個意圖

```ts
case 'engage':
  aimFromKnobs(basis, sit, track.latched ? repositionKnobs(sit, cfg) : k, out.aimWorld, cfg)
  break
case 'approach':
  if (track.latched) aimFromKnobs(basis, sit, repositionKnobs(sit, cfg), out.aimWorld, cfg)
  else normalizeInto(basis.leadPoint, basis.losAxis, out.aimWorld)
  break
```

| 意圖 | 受影響 | 理由 |
|---|---|---|
| `approach` | **是** | 問題窗的 53.2%。目前是**純預瞄追擊、零旋鈕** |
| `engage` | **是** | 問題窗的 1.8%，但它是正常追擊的主力，行為要一致 |
| `merge` | 否 | 它管交會的那 2.5 秒，要的是「乾淨的預瞄追擊，拿一次正面快照」。那是刻意的 |
| `defend` | 否 | 走 `defendAim`，對**威脅來源**做的，與能不能打中攻擊目標無關 |
| `extend` | 否 | 卸載脫離，動作與佈局互斥 |
| `rally` | 否 | 指揮層位階最高 |

【為什麼不做成 `SteerMode`】`mode` 在 `steerCommand` 裡**壓過意圖**，做成 mode
會連 `defend` 與 `extend` 一起蓋掉。寫在意圖分支裡，上表的「否」是**結構上
保證**的，不是靠額外的 if。

### 6.3 幾何閘門仍然壓過它

`geometryGate` 的四個 mode（超前、沒空速、拉太猛、平面退化）都在 `steerCommand`
的 mode 分支裡，發生在意圖分支**之前**，所以它們自動壓過本文。那是對的：
撞上去、失速、沒空速都比「佈局下一次」急。

### 6.4 射擊解是自動豁免的 —— 不需要寫

`DEFAULT_FIRE.maxLosRate = 0.35 rad/s = 20.1°/s`，而 `shouldFire` 的條件之一
是 `losRate <= maxLosRate`。

實測的 `instantaneousTurnRate` 在這些場景是 22~25°/s，所以
`trackRatio > 1.4` ⟹ `losRate > 31°/s` ⟹ **`shouldFire` 早就是 false**。

**閂鎖成立時不可能有射擊解**，所以不需要像 `sweetYield` 那樣寫一層讓位。
這個蘊含關係要在單元測試裡釘住（§8.1），因為它依賴兩個常數的相對大小 ——
哪天有人調 `maxLosRate` 或換一台轉彎率很低的飛機，它就不再成立。

## 7. 參數

| 名稱 | 意思 | 起始值 | 掃描範圍 |
|---|---|---|---|
| `trackEnter` | 閂上的門檻（`trackRatio`） | **1.4** | 1.3 / 1.4 / 1.5 / 1.8 |
| `trackExit` | 釋放的門檻 | 1.0 | 0.8 / 1.0 / 1.2 |
| `trackHold` | 低於 `trackExit` 之後還要維持幾秒 | 3.0 s | 1.5 / 3 / 5 |
| `trackCap` | `trackRatio` 的上限 | 4.0 | 不掃，防爆用 |
| `zoomEnter` | 開始抬高的 `cornerRatio` | 1.00 | 0.9 / 1.0 / 1.1 |
| `zoomFull` | 抬到滿的 `cornerRatio` | 1.30 | 1.2 / 1.3 / 1.5 |

**`trackEnter <= 0` 是消融開關** —— 閂鎖永遠不成立，兩個意圖分支逐位元退回
改動前。（與 `extendTurnCap: 0`、`climbMax: 0` 同一個慣例：0 在語意上是
「任何值都觸發」，那是永遠不會要的設定，所以拿來當關閉開關。）

## 8. 驗收

**判準是「玩起來合不合理」，不是攻擊效率。** 不得拿 `fireShare` / `redDamage`
的**大小**當否決依據；`redDamage > 0` 是一條「打得起來」的門檻，不是要
最大化的量。

### 8.1 單元（純函數與蘊含關係）

- `trackRatio` 的退化：分母為 0、`losRate` 為 NaN、極近距離 → 夾在 `trackCap`
- 閂鎖的生命週期：1.7 秒的脈衝要能閂上並維持 `trackHold`；低於 `trackExit`
  但不足 `trackHold` 不得釋放
- `repositionKnobs`：`cornerRatio` 低時 `vertical → 0`、高時 → 1，中間單調
- **射擊解的蘊含關係**（§6.4）：以 `DEFAULT_FIRE` 與實測的轉彎率量級，
  `trackRatio > trackEnter` 時 `shouldFire` 必為 false
- `trackEnter <= 0` 時兩個意圖分支逐位元不動

### 8.2 主判準（行為的絕對量測）

跑 `escort-trace.probe.ts`（axis-escort、seed 20260805）：

| 量 | 改動前 | 目標 | **實測（1.4 / 1.0 / 3.0）** |
|---|---|---|---|
| 谷底時對轟炸機的高度差 | **−443 m** | 不得為負 | **−1073 m** ❌ |
| 峰值到谷底掉的高度 | **1132 m** | 明顯減少 | **1759 m** ❌ |
| 交會後 20 秒的平均坡度 | **53°** | 顯著下降 | **28°** ✅ |
| 閂鎖佔時 | 0% | 個位數 % | **15.2%** ❌ |

（消融那一次逐字重現 −443 / 1132 —— 接線沒有洩漏副作用。）

### 8.2b 量測否決（2026-08-23）

**機制做到了它被設計要做的事，但沒有達成它被設計的目的。**

閂上的那 5.3 秒（25.9~31.1 s）完全照設計走：坡度由 −52° 收到 −22°，
而消融版本在同一段是 −56° → −68°。問題在**釋放之後**：

```
   t |  開啟:  y   坡度   航跡角  |  消融:  y   坡度   航跡角
  36 |  3698   -22   -25.5     |  3690   -68   -10.4
  38 |  3414   -11   -78.0     |  3586   -72   -22.7
  40 |  3046   -10   -56.8     |  3464   -59   -16.0
  42 |  2809    -9   -18.6     |  3405   -60    -1.9
```

閂鎖在 31.1 s 釋放，AI 回到純預瞄追擊，而目標此時已經在更下方 ——
**37~42 秒它以航跡角 −78°、坡度只有 −11° 幾乎垂直俯衝下去，四秒掉 889 m。**
消融版本在同一段是正常的大坡度盤旋，只掉 200 m。

**判準本身看不到那一段** —— t = 38 的 `trackRatio` 只有 **0.45**，機頭追得上，
所以不閂。這個設計問的是「追不追得上」，而那一段的問題是「**追得上，但追
下去代價太大**」。

### 8.2c 參數空間裡沒有出路

`trackEnter` 由 1.3 掃到 2.2，谷底一路是 −1072 ~ −1084 m —— **完全不敏感**。
傷害來自交會那一次閂上，門檻推多高都躲不掉（2.2 時仍有 7.3% 佔時）。

`trackHold` 才是唯一有效的旋鈕，而它把兩個目標放在直接對立的兩端：

```
trackHold   谷底對轟炸機   峰值→谷底   閂鎖佔時   交會後 20s 坡度
   1.5        −1117 m      1803 m     10.5%        26°
   3.0        −1073 m      1759 m     15.2%        28°
   5.0        −1047 m      1734 m     20.1%        31°
   8.0         −632 m      1319 m     28.2%        48°
  12.0         −473 m      1161 m     46.7%        51°
  消融          −443 m      1132 m      0.0%        53°
```

**每省一公尺高度，就換回一度坡度。** 12 秒之所以「好轉」到接近消融值，
是因為機制在那個設定下把自己關掉了 —— 它不是找到了平衡點，是退出了。

結論：**這一版把「大坡度硬轉」換成了「小坡度垂直俯衝」，能量帳一樣，只是
形狀不同。** 不是調參數能解決的，要改的是設計。

【為什麼加「平均坡度」】它直接對應「不再用大坡度硬轉一個收斂不了的彎」。
高度是結果，坡度是動作本身。

### 8.3 硬否決（任何一條破線就退回）

- `ai-manoeuvre`、`ai-visible-evasion`、`ai-defence` 不得新增紅
- **`ai-duel-matrix` 的三張卡都必須仍然打得起來**（`redDamage > 0`）——
  高能量、共速共高、低能量。上一輪就是在這裡爆的
- `ai-duel-matrix` 的**共速共高**要特別看：那一場閂鎖佔時應接近 0（§3.1
  量到 1.4 門檻下是 0.0%）。若實際跑起來不是 0，表示動態中的比值與這次
  的靜態量測不同，**當場停手重量**
- 低速安全：`belowStall`、`safetyShare` 不得惡化

## 10. 風險

**一、閂上之後打不到人。** 佈局的代價是暫時放棄射擊解。§6.4 說明閂上時本來
就沒有射擊解，但**閂鎖會持續到訊號消失後 `trackHold` 秒** —— 那段時間可能
已經有解了。`trackHold` 訂太長就是在丟機會，掃描時要看。

**二、纏鬥被誤傷。** §3.1 量到 1.4 門檻下纏鬥是 0.0%，但那是**現況**的纏鬥。
本文上線後 AI 的飛法會變，可能繞出新的幾何。§8.3 把它列為必看。

**三、與 `extend` 的邊界。** 兩者都是「別追了」，但 `extend` 是離開戰場、本文
是留在戰場換飛法。若閂鎖與 `extendTurnLatch` 同時成立，`extend` 勝（意圖層
位階較高，而且本文不碰那個分支）。這是結構保證的，但要在整合測試裡看一次
兩者的佔時有沒有互相吃掉。

**四、`approach` 的行為改變範圍比預期大。** `approach` 是 AI 最常見的意圖之一
（不只護送關）。本文讓它在閂上時改用旋鈕瞄準 —— 那是一個**全域**的行為改動，
不限於回報的那個場景。§8.3 的三張卡與 20v20 都要看。

**五、只修一半。** 大坡度下「撐不住」那一半（§9.3）本文不處理。AI 進入佈局
之後若仍然拉大坡度，高度照樣會掉，只是不該再進那個彎。驗收時要說清楚。
