# 指揮 AI 第三份：決策層 —— 什麼時候該下哪一種命令

**日期**：2026-08-08
**前置**：`2026-08-07-command-ai-orders-design.md`（指令通道與集合點）、
`2026-08-07-command-ai-tactics-design.md`（側翼與集火）

## 1. 為什麼要有這一份

第二份把集火做出來了，而且**局部強成立**：被指名那一架的掉血速率是同一場、
同一隊其他敵機的 **4.8 倍**（spec 第二份 §11.2）。

但它**全域有副作用**。實測 20v20：接敵瞬間（t = 24.0 s）**八個分隊同時
拿到集火令** —— 因為現行的觸發階梯是「近就集火」，而接敵之後每個分隊都在
`FLANK_RANGE`（2500 m）以內。後果：

- 兩隊質心**在 150 秒內從來沒有靠近到 900 m 以內**（兩隊不再真正混戰在
  一起），`multi-battle` 的「巡航相位」是用那個距離判定結束的，於是那條
  判準整場為真。
- 撤退令從 5 張變 11 張、到達率從 5/5 掉到 5/11。
- 134 次安全層接管（全部在撤退期間、全部在 5,345 m、TAS 50 m/s —— 是失速
  被撞地分支吞掉）。
- 離場佔時 33.5%，超過第一份定的 25% 上界。

**問題不在集火這個戰術，在「什麼時候給誰下命令」。** 第二份 §3 已經明寫
那個階梯是刻意笨的、第三份會整條換掉。這一份就是那件事。

## 2. 主判準：傷害交換比

專案負責人 2026-08-08 裁定：**這一份要買的是「打得更好」，不是「戰場看
起來像空戰」。**

具體量法見 §7.3。這與前兩份不同 —— 前兩份用的是絕對門檻（傷害地板）與
品質指標（方位角、掉血集中度）；這一份是**真的對打**：有指揮的一方要贏
過沒指揮的一方。

第 1 節列的那四個現象（質心不合流、離場佔時、撞地接管、撤退到達率）
**不是這一份的閘門**，但要量、要回報。若決策層順便讓它們轉綠，那是附帶
收穫；若沒有，spec 要記下來。

## 3. 架構：在規劃段插一個排名

現行 `stepCommand` 的規劃段是「每支分隊各自決定」，於是接敵那一瞬所有人
做出同一個決定。**局部條件治不了同時性** —— 條件再挑，符合的分隊還是會
一起符合，因為接敵是一個所有分隊同時經歷的事件。

改成兩階段：

```
階段一（不變）  每支分隊各自算「該不該撤退」。撤退不佔配額
階段二（新增）  把沒有命令、也不在撤退的分隊排名，
                取前 K 支發進攻命令
```

### 3.1 為什麼是全域配額而不是更挑的局部條件

**排名本身就是更挑的條件。** 要排名就得有分數，而「這支分隊該不該拿到
命令」正是那個分數在回答的問題；取前 K 名就是配額。分數再帶一個最低門檻，
它就同時扮演了「更挑的條件」。**一個機制，兩件事都做到** —— 用兩個機制
會有兩個地方在回答同一個問題。

另外三個好處：

- **K 的兩端都已經量過**：K = 0 是關掉指揮（第一份的對照組），K = 全部是
  現在的狀態（接敵時八個同時）。掃描的兩個端點都有數據。
- **遲滯是免費的**：只排「沒有命令」的分隊，已持有命令的不參與排名，
  命令照既有的解除條件走。不會出現「這一輪排第 3 拿到命令、下一輪排第 6
  又被收回」的抖動。這個專案為了遲滯付過三次代價（`latch`、`switchMargin`、
  `spent` 歸零），這次結構上就沒有。
- **仍然是純函數**：排名收全部分隊的快照陣列，回傳一個順序，照樣能用
  字面物件出考題。

### 3.2 撤退不佔配額

「打不動了」是一個**事實**，不是指揮官在分配資源。而且撤退本來就有自己的
門檻與遲滯（`spentSeconds`、到達歸零），實測一場 120 秒只發 11 張。

**已知代價**：離場佔時那條紅主要就是撤退造成的（單獨 33.5%），不管它就
修不到。這是專案負責人 2026-08-08 的裁定，記在這裡供追溯。

### 3.3 動到哪些檔案

| 檔案 | 改動 |
|---|---|
| `src/ai/command.ts` | 新增 `rankFlights` 純函數（簽名見 §5.3）；`CommandUnit` 加 `shotInstant`；`CommandState` 加 `idle`；`CommandConfig` 加 `maxOrders` 與 `idleSeconds`；規劃段改成兩階段 |
| `src/battle/setup.ts` | 每步把 `AiController.shotInstant` 抄進快照（三行，與 `cornerRatio`、`hpFraction` 同一手） |
| `test/unit/ai-command.test.ts` | 加 §7.1 與 §7.2 的考題 |
| `test/integration/ai-command-decision.test.ts` | **新增**：§7.3 的三場 A/B |

**不動的**：`src/ai/AiController.ts`、`src/ai/wingman.ts`、`src/ai/rally.ts`、
`src/ai/steer.ts`、`src/ai/target.ts`。這一份只改**指揮層怎麼挑人**，
不改戰機收到命令之後做什麼。

## 4. 排名分數：機會成本

分數只問一件事：**這支分隊現在有沒有人握著射擊解**。有就不要打擾，沒有
就派它去集火。

### 4.1 為什麼是機會成本，不是「誰最有機會」

**它是唯一編碼了實測教訓的特徵。** 第二份 §12 量到側翼失敗的機制是「一支
已經咬住人的分隊放棄了現有位置」。純幾何量不到那件事 —— 「離最近的敵分隊
多近」對正在得手的和正在挨打的分隊是同一個數字。

**它回答一個別人沒回答的問題。** 打誰，`planFocusTarget` 已經在算（挑血
最少、可及的）；誰離得近，幾何在算。「叫誰去損失最小」沒有人在算。把目標
價值也放進分數會讓同一個問題有兩個答案 —— 第二份 §5.3 花了整節說明為什麼
不重用 `targetScore`，同一條紀律。

### 4.2 資料從哪來

`AiController.shotInstant` **已經存在**，它的註解寫的就是「上一格的射擊解
強度鏡像，只為量測存在」。`setup.ts` 每步抄進 `CommandUnit`，與
`cornerRatio`、`hpFraction` 同一手。

### 4.3 為什麼是計時器而不是瞬時值

`shotInstant` 是瞬時的，而分隊在一次大彎途中會短暫失去射擊解。直接讀瞬時
值會把「正在纏鬥」誤判成「閒」。

所以 `CommandState` 加 `idle: Float32Array`，每步累積、一有射擊解就歸零 ——
**與既有的 `spent` 逐字同一個形狀**，不新發明一套。

```
worst = 分隊裡任何一個存活成員的 shotInstant 最大值
worst <= 0  →  idle[f] += dt
否則        →  idle[f] = 0
```

### 4.4 一件要先講清楚的事

**實測射擊解很稀有**：整場開火取樣只佔存活取樣的 1.7%（第一份的通道量測）。
所以「閒置滿 `idleSeconds`」這個門檻幾乎所有分隊都會滿足 —— **真正在限制
數量的是 K**，門檻的作用只是防止「一支剛剛還在得手的分隊立刻被調走」。

門檻不是主角。spec 明寫這件事，免得日後看到「幾乎所有分隊都合格」以為是
bug。

## 5. 每個規劃週期做什麼

```
1. 數目前持有進攻命令（kind !== 'rally'）的分隊數，得到剩餘名額
2. 候選 = 沒有命令 且 idle >= idleSeconds 且 count > 0 且 不是玩家那一隊
3. 依 idle 由大到小排序；同值以分隊索引破平手
4. 依序呼叫 planFocusTarget：
     回 null（沒有可及的目標）→ 跳過，名額不消耗
     有命令 → 發出，名額 −1
   名額用完就停
```

**排名只決定考慮順序，能不能發由 `planFocusTarget` 自己說。** 我方這邊看
閒置度，敵方那邊看有沒有打得到的目標，各管一半，不重疊。

### 5.1 遲滯

進攻命令解除時把 `idle[f]` 歸零，要再閒置滿 `idleSeconds` 才重新有資格。
與第一份「到達集合點就把 `spent` 歸零」逐字同一招（第一份 §4.2），不新增
機制。

少了這一行，一支剛解除命令的分隊在下一個週期就會回到榜首（它確實是閒的），
於是被永久釘在命令狀態 —— 那正是第一份記載過的病。

**只有進攻命令的解除會把 `idle` 歸零。** 撤退令解除時歸零的是 `spent`
（第一份既有的行為），兩個計時器各管各的 —— 一支剛撤退回來的分隊本來就
是閒的，沒有理由再罰它一次。

### 5.2 配額算的是「非 rally 的命令」

不是「focus 的命令」。所以之後重新打開側翼時它自動參與配額，這一段不必改。

### 5.3 `rankFlights` 的簽名

```ts
export function rankFlights(
  flights: readonly CommandFlight[],
  own: readonly number[],
  units: readonly CommandUnit[],
  orders: readonly (FlightOrder | null)[],
  idle: Readonly<Float32Array>,
  skipFlight: number,
  out: number[],
  cfg?: CommandConfig,
): void
```

**寫進 `out`（先清空）而不是回傳新陣列** —— 它每 `planPeriod` 秒跑一次，
呼叫端重用一個模組層級的陣列，與 `MEMBERS` / `TARGET` 那一組同一個做法
（第二份 §6）。

收 `orders` 與 `idle` 而不是整個 `CommandState`：排名不需要知道計時器
（`timer`）與見底秒數（`spent`），收最小的那一組才能用字面物件出考題 ——
與 `CommandUnit` 只收最小介面同一個理由。

## 6. 退化與邊界

| 情況 | 行為 |
|---|---|
| 沒有合格的分隊 | 空榜，不發令。**不是錯誤** |
| `maxOrders = 0` | 指揮官只做撤退。合法設定，也是掃描的一個端點 |
| 分隊全滅（`count === 0`） | `idle[f] = 0`，與 `spent` 對全滅分隊的處理一致 |
| 玩家座位沒有 `AiController` | `shotInstant` 寫 0（視為閒置）。無害 —— 玩家那一隊本來就被 `skipFlight` 跳過 |
| 候選比名額少 | 發出的比 K 少。不補、不放寬門檻 |

**排名刻意不看敵方。** 要不要發、發給誰打由 `planFocusTarget` 決定；排名
只回答「先考慮誰」。這讓 `rankFlights` 的考題可以完全不造敵機。

## 7. 驗收

### 7.1 考題：`rankFlights` 純函數

1. 閒最久的排第一
2. 同 `idle` 值 → 以分隊索引由小到大破平手（**決定性**）
3. `idle` 沒到 `idleSeconds` 的不進榜
4. 已持有命令的不進榜（不論哪一種命令）
5. `count === 0` 的不進榜
6. 玩家那一隊（`skipFlight`）不進榜
7. 同一個快照算兩次，回傳逐位元相同的順序
8. `idle` 微擾 ±0.1 s 只會讓相鄰兩名互換，不會讓整個順序翻轉
9. 全部不合格 → 回空

### 7.2 生命週期：`stepCommand`

10. 名額滿了就不再發進攻命令
11. 一張命令解除後名額釋出，下一個規劃週期補上
12. 解除時 `idle` 歸零 → 不會立刻重發
13. **一支見底的分隊在 K 已滿時仍然拿得到撤退令**（撤退不佔配額）
14. `maxOrders = 0` 時完全不發進攻命令，但撤退照發
15. 玩家那一隊照舊自治
16. 同時持有進攻命令的分隊數，全程不超過 `maxOrders`

### 7.3 主判準：三場 A/B

```
基準場   兩隊都不指揮      → 藍方交換比 R0 = 紅掉血 / 藍掉血
第二場   只有藍方指揮      → R1 = 紅掉血 / 藍掉血
第三場   只有紅方指揮      → S1 = 藍掉血 / 紅掉血

要求   R1 > R0 × 1.10   且   S1 > (1 / R0) × 1.10
```

三場、兩條斷言。

- **為什麼要兩個極性**：`DEFAULT_BATTLE` 是 P-51D 對 Bf 109 G-6，兩個機種
  的性能不同。只跑一個極性的話，量到的是機種差異加上指揮效果，分不開。
  機種差異在兩個極性裡方向相反，基準場把它量掉。
- **`margin` = 0.10，專案負責人 2026-08-08 在跑之前裁定。** 看到結果再定
  門檻等於量到綠為止 —— 這個 session 已經在這件事上摔過（第二份 §11.7）。
- 「關掉指揮」的做法沿用第一份：每步把該隊的 `orders` 清乾淨並把每架的
  `ai.order` 設為 null。**兩邊跑的是完全同一份程式**，差別只有命令有沒有
  真的傳到戰機端。

### 7.4 否決條件

任何一條成立就退回設計（沿用第二份 §7.5 那一層）：

- 排名非決定性
- `idle` 出現門檻式跳變（它是連續量）
- `src/ai/` 的熱路徑配置記憶體
- `src/ai/` import `src/battle/`

### 7.5 量但不當閘門

離場佔時、命令期間的安全層接管、`multi-battle` 的巡航相位、撤退令的
發出／到達張數。**專案負責人已裁定主判準是傷害交換比**，這四項是觀測值。
若它們順便轉綠要記下來；若沒有，也要記下來。

## 8. 待掃描的參數

| 參數 | 起始值 | 來歷 |
|---|---|---|
| `maxOrders` | 2 | 每隊五個分隊，K = 2 表示同時最多四成的分隊在執行戰術。兩個端點（0 與 5）都已經量過 |
| `idleSeconds` | 3 | 與 `spentSeconds` 同值：一次完整的水平大彎的量級，用來濾掉單次失去射擊解 |

兩個都要掃。掃描的判準是 §7.3 的三場 A/B —— **這一次判準是量得動的**，
不像第二份的品質指標。

## 9. 這一份不做的事

- **不重新打開側翼。** `FLANK_ENABLED` 維持 `false`。理由：我們對側翼失敗
  有一個具體假設（命令解除時位置優勢被自由選目標丟掉），**光是把它放回
  選單那個機制一個字都沒改** —— 測到的仍然是「沒有交接目標的側翼」。而且
  兩件事一起開，贏了不知道誰的功勞，輸了不知道誰的錯。重開的成本很低
  （翻一個布林值 + 跑同一組 A/B），沒有理由綁在一起。
- **不修那三條紅**（離場佔時、撞地接管、巡航相位）。它們主要由撤退與集火的
  全域效應造成，而主判準已經裁定是傷害交換比。
- **不碰 `safety.ts`。** 第二份 §12 發現撞地分支在低速時會吞掉失速
  （5,345 m、TAS 50 m/s 被標成撞地接管），那是一個獨立的既有問題，
  不在這一份的範圍。
