# 依能量狀態限制拉桿量 設計

**日期**：2026-08-06
**前一份**：`2026-08-05-ai-defence-batch2-design.md`（甲乙已實測否決，丙未做）

## 1. 這份 spec 從哪來

第二批防禦機動的兩個提案（異平面破防、力道連續化）都被實測否決。過程中量到的
東西比提案本身值錢：**AI 在每一個交戰意圖裡都在燒能量，燒的速度是引擎產出的
兩倍半。**

1v1、300 秒、六種開局，把比能量變化率按意圖拆開，並與「同高度同速度下乾淨
平飛能拿到的超量功率」比較：

```
意圖       佔比   過載   TAS      實得 Ps   乾淨 Ps   取得率
extend     44%   1.67   430 km/h   +6.2      15.7      40%
approach   33%   4.32   508 km/h   −31.8     13.6    −235%
defend      5%   2.42   504 km/h   −38.8     13.7    −283%
engage     15%   1.40   512 km/h    +7.3     13.5      54%
```

`approach` 佔三分之一的時間，以 **52° 坡度拉 4.32 G**，每秒燒掉 32 公尺的比
能量，而引擎在同樣條件下只給得起 13.6。

後果是一條完整的鏈：

```
approach 硬拉 → 能量見底，而且此刻機頭朝上 +36°
   → cornerRatio 跌破 0.75，extend 觸發
   → extend 接到的是最糟的一手牌：要把航跡由 +36° 扭到 −12°
   → 指揮儀先試推桿（80%），1 秒後改成滾轉倒飛再拉（split-S）
   → 坡度 40° → 110° → 170° → 132° → 11°，花 8 秒、最高 3.7 G
   → 真正乾淨的俯衝 8 秒後才開始
   → extend 只拿到 40% 的可用超量功率，一次要 18~49 秒
   → 於是 extend 佔 40~47%，engage 只剩 8~15%
```

**AI 花在逃的時間是花在打的四倍。**

## 2. 病因不是爬升，是過載

一個容易犯的誤判（本 spec 初稿犯過）：把 +36° 的爬升當成病因，於是想加一條
「速度低時不准爬」的護欄。

**那是錯的。** 比能量 = 高度 + V²/2g，爬升只是把速度換成高度，**不消耗能量**。
真正消耗的是誘導阻力，而誘導阻力 ∝ n²。4.32 G 的誘導阻力是 1 G 的 **18.7 倍**。

機頭朝上 +36° 是「在垂直面硬拉」的**症狀**。護欄要架在過載上。

## 3. 為什麼現有的三道閘門攔不住

| 機制 | 判準 | 為什麼在這裡失效 |
|---|---|---|
| `geometryGate` 的 `unload` | `stallMargin < 1.15` | 量的是「拉太猛會不會失速」，4.32 G 在 508 km/h 離失速還很遠 |
| `geometryGate` 的 `speedRecover` | `speedMargin < 1.25` | 量的是「還飛不飛得動」，那時 `speedMargin` 還有 2.0 |
| `rules` 的 `extendFloorLatch` | `cornerRatio < 0.75` | **事後**才動。它是「已經沒能量了」的宣告，不是預防 |

三者都在問「我現在安不安全」，**沒有一個在問「我付得起這個拉桿嗎」**。

> **實作後否決（2026-08-06）。** §4 的設計做出來了、掃描完、整段撤回。掃描表
> 與根因寫在 `src/ai/steer.ts` 的 `DEFAULT_STEER` 註解「已經試過並否決的：
> 依能量狀態限制拉桿量」。§6.3 的兩條事前否決條件同時觸發：`engage` 佔比
> 七行全部是 13%（沒有上升），攻擊產出掉 36~70%（否決線 15%）。
>
> **根因（§2 的診斷沒錯，§4 的手段錯了）**：指揮儀是 bank-to-turn，**坡度決定
> 過載的下限**（`1/cos φ`），拉桿量只在那之上再加。坡度來自誤差的**方位**，
> 而 `shrinkTowardNose` 刻意不動方位。收小誤差角因此減不了過載 —— 實測 44°
> 坡度對應 `1/cos = 1.39`，加上追瞄的拉桿正好是量到的 3.6~3.8。
>
> **仍然成立的**：§1 的量測（approach 每秒燒 32 m 而引擎只給 13.6）、§2 的
> 病因判斷（是過載不是爬升）、§3 的缺口（三道閘門都不問代價）。錯的只有
> §4 的手段。真正該減的是**坡度**，那要動瞄準的方位，需要另開設計。
>
> 以下保留原設計供追溯。

## 4. 設計

### 4.1 一個連續的拉桿係數，鑰匙是 `cornerRatio`

```
energyPull(cornerRatio) : 0..1
```

- `cornerRatio ≥ pullEase` → **1**（能量充足，不限制）
- 由 `pullEase` 線性降到 `DEFAULT_RULES.cornerEnter`（0.75）→ `pullFloor`
- 低於 `cornerEnter` → 維持 `pullFloor`（不再繼續降，見下）

套用方式**沿用既有的 `shrinkTowardNose`**：把瞄準誤差角乘上這個係數，**方位
一個字都不動**。那是 2026-08-05 治好 0.1 秒抖動時確立的形狀——誤差的方位決定
往哪邊滾，大小決定拉多少 G，兩者必須分開。

【為什麼不是限制爬升角】見 §2。也因為改瞄準點的**鉛直分量**等於改方位，
指揮儀會讀成滾轉需求——那正是抖動的來源。

【為什麼有 `pullFloor` 而不是降到 0】降到 0 等於「沒能量就直線飛」，那既不
真實也危險（連基本的指向都做不到）。而且低於 `cornerEnter` 之後 `extend` 已經
接手，這個係數不再是主導者。

### 4.2 有射擊解時不限制

```
shotInstant > 0  →  係數恆為 1
```

`shotInstant > 0` 的定義是「距離 900 m 內、有預瞄解、機首在 15° 錐內」——也就是
**我正咬著他**。此時的硬拉是有產出的，不是浪費。

這與 `rules.ts` 的 `arbitrate`（「有槍在手時，『比他弱』不是離開的理由」）和
`target.ts` 的 `shotRelief`（「有射擊解時免除分攤折扣」）是**同一條分野的第三次
套用**：

- **相對／預防性的理由**（我能量不夠、有人比我適合）→ 有槍在手就先開槍
- **絕對的理由**（我飛不動了、我要失速了）→ 開著槍也得處理

省能量是預防性的，所以讓位。

**連續性**：`shotInstant` 是 0..1 的連續量，但這裡用的是布林門檻，會產生跳變。
折衷是與 `shotRelief` 相同的線性內插：

```
relief = min(1, shotInstant / pullShotRelief)
factor = energyPull + relief × (1 − energyPull)
```

`shotInstant` 由 0 長到 `pullShotRelief` 的過程中係數平滑回到 1。

### 4.3 套用範圍

| 意圖 | 套用？ | 理由 |
|---|---|---|
| `engage` | ✅ | 挖坑的主力之一 |
| `approach` | ✅ | **挖坑的主力**（33%、4.32 G、−31.8 Ps） |
| `merge` | ✅ | 同為追擊型瞄準 |
| `extend` | ❌ | 它的瞄準點在**速度向量**上；往機首收會把它拉到速度向量**上方**（大攻角時機首高於航跡），變成命令爬升——與 extend 的目的相反 |
| `defend` | ❌ | 使用者的訴求是「AI 不太會閃」，這一批不動防禦 |

幾何模式 `overshoot` / `speedRecover` / `planeDegenerate` 都**不套**：它們的優先序
高於意圖，而且各自在處理一個更急的問題。

### 4.4 與既有的 `unload` 係數相乘

`unloadPull`（失速裕度）與 `energyPull`（能量狀態）管的是兩件不同的事，都表達成
「把誤差角乘上一個 ≤1 的係數」，所以**相乘**：

```
factor = unloadFactor × energyFactor
```

兩者都在門檻上等於 1，乘積因此也在各自的門檻上連續。

## 5. 介面

**`src/ai/steer.ts`**

```ts
export function energyPull(
  cornerRatio: number, shotInstant: number, cfg?: SteerConfig,
): number
```

`SteerConfig` 新增：

| 參數 | 起始值 | 意義 |
|---|---|---|
| `pullEase` | 1.0 | 高於此 `cornerRatio` 不限制 |
| `pullFloor` | 0.5 | 係數的下限 |
| `pullShotRelief` | 0.25 | `shotInstant` 達此值即完全免除（與 `DEFAULT_TARGET.shotRelief` 同值同理由） |

`steerCommand` 的後處理段由

```ts
if (mode === 'unload') shrinkTowardNose(self, unloadPull(...), out.aimWorld)
```

改為先把兩個係數相乘再套一次。

**不新增任何狀態。** 全部是純函數，`Situation` 已經有 `cornerRatio` 與
`shotInstant`。

## 6. 量測與驗收

### 6.1 主要指標（1v1、300 秒、六種開局、子彈無傷害）

| 指標 | 修改前 | 期望方向 |
|---|---|---|
| `extend` 佔比 | 40–47% | **下降** |
| `engage` 佔比 | 8–15% | **上升** |
| `approach` 的比能率 | −31.8 m/s | **上升**（往 0 或正） |
| `approach` 的平均過載 | 4.32 | 下降 |
| split-S 發生率（進入 extend 後 4 秒內坡度 > 90°） | 待量 | 下降 |

### 6.2 護欄（不得退步）

- `test/integration/ai-manoeuvre.test.ts` 六場的五個門檻全部維持。
- `test/integration/ai-defence.test.ts` 四條維持，特別是 **`dealtToA > 0`**——
  少拉一點不能變成打不到人。
- `test/integration/ai-duel-matrix.test.ts` 的能量優勢開局仍須毫髮無傷擊落。
- **攻擊產出**：受控場景 36 種幾何的「打掉紅 A」總量不得下降超過 15%。這是
  這個提案最可能付出的代價，事前定好可接受的範圍。

### 6.3 事前約定的否決條件

若 `engage` 佔比沒有上升、或攻擊產出下降超過 15%，**整個提案撤回**，掃描表與
根因寫進 `DEFAULT_STEER` 的註解（比照「射程內控速」「力道連續化」「異平面
破防」三筆）。

### 6.4 混沌紀律

- 單場勝負、擊落時間、單一軌跡的傷害**不作為判準**。
- 聚合的比率量（意圖佔比、比能率、過載）與受控場景的逐場可重現值才算數。
- 受控場景的觀察窗**至少 120 秒**——30 秒看不到能量問題（2026-08-06 的教訓）。

## 7. 風險

1. **指向變慢 → 打不到人。** 最主要的風險，由 §6.2 的攻擊產出守住。
2. **`pullFloor` 太低會讓 AI 在低能量時形同放棄機動**，看起來像「呆滯」。
   0.5 是起始值，要掃。
3. **與 `unloadPull` 相乘可能過度削減。** 兩者同時觸發時係數可能低到 0.3 以下。
   要量兩者同時生效的時間佔比；若過高，改成取最小值而不是相乘。
4. **混沌敏感。** 比照前三次，只採聚合量。

## 8. 明確不做

- 不動 `defend`（使用者的訴求是要更會閃，不是更省）。
- 不動 `DEFAULT_RULES` 的任何門檻（改動門檻會與本提案的效果混在一起，量不出
  是誰的功勞）。
- 不動 `ALPHA_MARGIN`／`PILOT_G_POSITIVE`（那是玩家手感的旋鈕，見
  `specs/feel.ts`；本提案只約束 AI 的**指令**，不改飛機能力）。
- 不碰 `DifficultyProfile`。
