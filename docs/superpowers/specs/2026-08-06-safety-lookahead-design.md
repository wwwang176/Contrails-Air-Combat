# 撞地保護的前瞻 設計

**日期**：2026-08-06
**前一份**：`2026-08-06-ai-reaction-delay-design.md`

## 1. 病灶

`applySafety` 用閉式解算「由目前的俯衝角拉回水平要掉多少高度」：

```
R      = V² / (g·√(n²−1))
needed = R·(1 − cos|γ|)·factor + clearance
```

**它假設 γ 不再變陡。** 而 AI 在檢查通過之後還在繼續加深俯衝，於是所需高度
的成長比飛機拉得起來的還快。實測軌跡（受控低空場景，紅機）：

```
  t        高度   TAS    γ    安全層   needed（回推）
113.00      367   128   −40°    否        279 m   ← 367 > 279，通過
113.25      345   129   −47°    否        333 m
113.50      320   130   −54°    否        392 m   ← 這一刻已經追不上了
113.75      292   131   −60°    是        459 m   ← 觸發時缺 167 m
117.22        0                            —      觸海
```

**這不是延遲造成的。** 同一場零延遲也只剩 115 m，`factor = 1.5` 的餘裕幾乎
被吃光。延遲只是讓 AI 更常把自己開進這個角落。

## 2. 為什麼不是「把 factor 調大」

`factor = 1.5` 的原意是「閉式解假設立刻拉到 nMax，實際上指揮儀要花時間滾平
與建立過載」——它補的是**建立過載的時間**，不是**俯衝角還會變陡**。

兩者的量綱不同：前者是一個固定的比例，後者隨 `γ̇` 變化。用 factor 去蓋
γ̇ 的話，在平飛時會過度保守（安全層在高空亂動），在急劇加深時仍然不夠。
`safetyShare` 那條門檻（≤5%）正是防這個 —— **把飛行品質外包給安全層**。

## 3. 設計：預測 γ，不改 factor

```
γ̇      = g·(n·(L̂·ĉ) − cos γ) / V
γ_pred = clamp(γ + γ̇·lookahead, −π/2, 0)
needed = recoveryAltitude(V, min(γ, γ_pred), nMax)·factor + clearance
```

- `L̂` 是機體升力方向（`UP` 套上姿態），`ĉ` 是**垂直平面內、垂直於速度、朝上**
  的單位向量。`L̂·ĉ` 在無側滑的座標轉彎裡就是 `cos φ`（坡度餘弦），但用向量
  內積寫，倒飛與大側滑時仍然正確。
- `n` 取 `diag.loadFactor`（機體 Y 方向比力 / g），**已經是現成的**。
- `min(γ, γ_pred)` 取較悲觀的那個：只在**變陡**時提前，變緩時不會反而延後
  介入。

【為什麼這是無狀態的】`γ̇` 由當下的升力方向、過載與速度算得出來，不需要
上一步的 γ。`applySafety` 因此維持純函數（spec §4.3 的分層前提）。

【驗算】用實測軌跡的 t=113.00 那一格：γ̇ ≈ −26.7°/s（由 −40° 到 −60° 花
0.75 s）。`lookahead = 0.5` 時 γ_pred = −53°，needed = 390 m > 高度 367 m
—— **提前 0.75 秒觸發**。那 0.75 秒約 56 m 的高度，加上少 20° 要拉回的角度。

## 4. 介面

**`src/ai/safety.ts`**

```ts
export function flightPathRate(self: Aircraft): number    // rad/s
export interface SafetyConfig { …; lookahead: number }     // s
```

`recoveryAltitude` 的簽章不動 —— 餵給它的 γ 換成預測值就好。這讓既有的
`recoveryAltitude` 單元測試（給定速度與俯衝角，所需高度是確定的數字）
一個字都不用改。

## 5. 量測與驗收

### 5.1 主要指標（受控低空場景，五場、120 秒、子彈無傷害）

延遲 0 / 0.3 / 0.5 / 0.8 各跑一次，記錄全場最低高度與觸海步數。修補前：

```
延遲     對頭@600  對頭@400  追擊@500  側舷@700  俯衝@2000   最低  觸海
0.00        387      400      121      115       228      115   無
0.30        387      170      499       63       568       63   無
0.50        386      348      257       −0       547       −0   有 644 步
0.80        549      389      488      275       524      275   無
```

**驗收：四列都不得觸海，且最低高度不得低於 `clearance`（120 m）。** 後者是
安全層的宣稱 —— 它現在做不到，這正是要修的。

> **實作後修正（2026-08-06）。** 後半句**寫錯了**，`clearance` 不是最低高度的
> 保證。安全層在 `margin ≤ needed` 時觸發，`clearance` 是那個判準裡的**餘裕**；
> 觸發之後拉平還要時間，那段時間高度還在掉，所以飛機本來就會落到 120 m 以下。
> 實測任何 `lookahead` 都達不到 ≥120 m（最好的 1.0 是 106 m），而且那個數字
> 是**混沌的** —— 同一場在六個 lookahead 下是 115/54/16/121/106/114，沒有趨勢。
> 實際採用的判準只有「不觸海」，掃描表記在 `SafetyConfig.lookahead` 的註解。
>
> 另外，`lookahead` 的**上界**是這份 spec 沒有預見的：§5.2 只把六場機動測試
> 列為「不得退步」的護欄，實際上它給出了決定性的上界 —— `lookahead ≥ 0.75`
> 時側舷@1000 的 `longestExtend` 由 34 s 炸到 285 s（300 秒的仗），機首 96%
> 的時間偏離目標超過 90°。可用區間因此只有 0.25~0.50。

  **`safetyShare ≤ 5%`**（現況最差 1.83%）—— 這一條抓的就是過度介入。

- `test/integration/ai-defence.test.ts` 全部。
- `test/integration/ai-reaction-delay.test.ts` 三條。

  240 Hz × 40 架，必須不配置記憶體。

### 5.3 `lookahead` 的定值

掃 0.25 / 0.5 / 0.75 / 1.0 / 1.5 s。判準：

1. §5.1 的四列全部不觸海、最低高度 ≥ 120 m；
2. 在滿足 1 的前提下取**最小**的值 —— 過度前瞻就是過度介入；
3. `safetyShare` 六場最差不得超過修補前的 1.83% 太多（掃描時一併記錄，
   超過 5% 的門檻直接淘汰該值）。

掃描表寫進 `SafetyConfig.lookahead` 的註解。

### 5.4 事前約定的否決條件

若沒有任何 `lookahead` 能同時滿足「不觸海」與「`safetyShare` 不爆」，
**整個提案撤回**，掃描表與根因寫進 `applySafety` 的註解，並改記為
「已知缺陷，需要另一種修法」。

## 6. 風險

1. **過度介入。** 最主要的風險，由 `safetyShare` 守。急劇的正常機動（例如
   split-S 的入口）會有很大的負 γ̇，前瞻可能把它讀成「要撞地了」。若在高空
   也觸發，代表 `lookahead` 太大。
2. **既有基準移動。** 安全層改變任何一格的指令，之後的軌跡就全變了。六場
   機動測試與對戰矩陣都可能翻號。**不得為了讓它們綠而放寬門檻** —— 那些
   門檻每一條都低於修補前的最差值，放寬會讓整層失去意義。
3. **`diag.loadFactor` 在建構後、第一次 `update` 前是 0。** 那時 `γ̇` 會算成
   `−g·cos γ/V`（自由落體），可能誤觸發。既有測試已經踩過這個坑
   （`ai-controller.test.ts` 的 fixture 註解），要確認第一步的行為。

## 7. 明確不做

- 不改 `factor`、`clearance`、`recoveryPitch`（改了就分不清是誰的功勞）。
- 不改 `DEFAULT_STEER` 的任何參數。
- 不碰失速硬接管那一段。
- 不改 `recoveryAltitude` 的簽章與語義。
