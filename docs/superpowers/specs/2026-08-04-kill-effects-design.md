# M8 擊墜表現 —— 火球、黑煙、零件、殘骸墜落

## 1. 目標

擊墜目前是**憑空消失**（`main.ts:262` 的 `v.model.group.visible = c.alive`）。M7 之後，打中一發子彈的回饋比打爆一架飛機還強 —— 這份 spec 補上那個落差。

一次擊墜要看到四件事：

| 元素 | 觸發 | 樣子 |
|---|---|---|
| 火球 | 擊墜的瞬間 | 白 → 橘 → 暗紅，一次性 |
| 零件 | 擊墜的瞬間 | 同機色的方塊，沿飛行方向散射，翻滾 |
| 黑煙 | 殘骸與大零件持續拖曳 | 深灰，膨脹並淡出 |
| 殘骸 | 擊墜之後 | 原模型無動力翻滾墜落，一路掉到海面，入水濺起水花 |

### 1.1 不在範圍內

爆炸音效（專案沒有音訊子系統）、動態光源（特效用的是無光照材質，40 架會有上百個光源）、機體本身解體成多塊（零件是**額外生成**的，機體保持完整）、水面油污與燃燒、地面（只保留接口）。

---

## 2. 分層：`World` 只記錄事實

`World` 完全不知道有火焰、煙、零件或殘骸這些東西存在。它在 `destroy()`（`World.ts:466`）推一筆擊墜事件，其餘全部發生在渲染層。

這是 M7 已經劃過的界線：**「這一步發生了什麼」是物理，「它長什麼樣子」是渲染**。

### 2.1 為什麼是事件而不是每幀比對 `alive`

「上一幀活著、這一幀死了」看起來是一個更省事的做法 —— 死亡是單向的，邊緣偵測不該漏。

**但玩家會在同一幀之內死而復生。** `main.ts:254` 的 `if (!player.alive) respawnPlayer()` 跑在所有子步之後；一個排在它後面的邊緣偵測器看到的 `alive` 從頭到尾都是 `true`，**玩家自己的死會被整個漏掉**。

把偵測器排到重生前面可以修好它，但那是一個沒有任何東西保護的順序相依。事件緩衝沒有這個問題，而且與 `hitEvents` / `splashEvents` 同一條路。

## 3. 擊墜事件

```ts
// src/world/kills.ts
export const KILL_STRIDE = 7   // x, y, z, vx, vy, vz, index

export interface KillEvents {
  readonly capacity: number
  readonly data: Float32Array
  count: number
}

export function createKills(capacity: number): KillEvents
export function pushKill(e: KillEvents, x: number, y: number, z: number,
                         vx: number, vy: number, vz: number, index: number): void
export function clearKills(e: KillEvents): void
```

**容量 = 參戰架數，於是溢位在結構上不可能發生。** 一個子步之內每架最多死一次（重生走的是每幀一次的 `main.ts` 路徑，不在子步裡），所以 `capacity = combatants.length` 是一個上界而不是一個猜測。

**因此不需要 `dropped` 計數器。** `ImpactEvents` 需要它，是因為命中數沒有結構上界（4,000 發彈丸都可能在同一步命中）。這裡有，所以用不上 —— 掉一次擊墜等於少一次爆炸，那是絕不能默默發生的事。

`index` 存在 `Float32Array` 裡是安全的：float32 對 2²⁴ 以內的整數精確，而參戰架數是 40。

### 3.1 速度來自事件，姿態來自模型

火球、零件、噴濺是**世界錨定的一次性事件**，用事件裡的子步位置 —— 與火花同一個理由（M7 spec §2.2）。

**殘骸不同。** 它接管的是那個已經畫在**內插後**姿態的模型群組，所以它的初始位置與旋轉直接讀模型的現況，只有**速度**取自事件。用事件位置去設殘骸會讓它在誕生的那一幀跳最多 0.83 m（200 m/s × 一個子步）。

## 4. 廣告板粒子系統

火球、黑煙、噴濺共用**同一份幾何、同一支著色器、同一個積分器**，只換混合模式與參數。三個 `InstancedMesh` 實例，各 1 個 draw call。

```ts
// src/render/particles.ts
export interface ParticleConfig {
  capacity: number
  blending: Blending      // AdditiveBlending | NormalBlending
  life: number            // s
  sizeFrom: number        // m
  sizeTo: number          // m
  gravity: number         // m/s²，負值為下墜、正值為上浮
  drag: number            // s⁻¹，指數阻尼（與 SPARK_DRAG 同一種）
  alphaFrom: number
}
export function createParticles(cfg: ParticleConfig): Particles
```

### 4.1 為什麼是一份實作而不是三個檔案

M7 的三個特效（槍焰／火花／水柱）刻意寫成三個獨立檔案，因為它們的**幾何本身**不同（十字／拉長的圓柱／收緊的圓柱），運動也不同。

這裡相反：三者的幾何完全相同（一個面向相機的四邊形）、積分器完全相同（`v += g·dt; v *= e^(−k·dt); p += v·dt`）、淡出曲線完全相同。差別只有數值與混合模式。

三個長得幾乎一樣的檔案正是這個專案一再點名的**「只有一份會被修好」**的危險。

### 4.2 為什麼是廣告板

M7 否決廣告板當槍焰，理由是「槍焰有方向，從正側面看會退化成一個圓片」。

**煙與火球沒有方向**，它們本來就是各向同性的 —— 那條理由在這裡不成立，反而廣告板才是對的：不論從哪個角度看都是一團，而且成本是每顆 **2 個三角形**（低多邊形球體是 20 個）。

### 4.3 為什麼要自訂著色器 —— 黑煙沒有別條路

`InstancedMesh` 的逐實例顏色**只有 RGB 沒有 alpha**。M7 兩次繞開這條限制（槍焰靠加法混合淡到黑、水柱靠幾何曲線），這次繞不開：

- **加法混合對黑煙無效。** 加法是 `dst + src`，黑色加上去等於沒加 —— 黑煙用加法會直接隱形。
- **往黑淡是反的。** 4,000 m 高空背景一半是亮天空、一半是深海；深色的煙往黑淡等於越淡越明顯。
- **不淡出直接消失也不行。** 水柱可以（消失前只剩 4 cm，次像素），但一團 9 m 的深色物體在天空上「啪」地不見非常明顯。

所以逐實例 alpha 是必要的，走一個 `InstancedBufferAttribute`。

**這不是新的技術類別**：`ocean.ts:62` 已經用 `onBeforeCompile` 注入頂點著色器、`sky.ts:46` 是一支完整的 `ShaderMaterial`。

著色器做兩件事，約 15 行：

1. **頂點端**：從實例矩陣取出平移與縮放，在**視圖空間**組出四邊形 —— 這就是面向相機。
2. **片段端**：`alpha *= smoothstep(0.5, 0.2, length(uv − 0.5))`，得到**軟邊的圓形**。

**不用貼圖。** 專案目前一張貼圖都沒有（海面、天空、機體全是程序化幾何或著色器），為了煙開這個頭不划算，而一個程序化的徑向衰減效果一樣好。

## 5. 火球

```
數量 12 顆        初速 = 母機速度 × 0.5 + 等向 15 m/s
壽命 0.5 s        尺寸 3 m → 8 m 膨脹
混合 Additive     顏色 1.0,0.95,0.80 → 1.0,0.45,0.05 → 0.25,0.02,0.0
重力 0            阻尼 4 s⁻¹（時間常數 0.25 s）
```

**【為什麼要繼承一半的母機速度】** 火球若完全靜止，一架 150 m/s 的飛機在
火球的 0.5 s 壽命內會飛出 75 m —— 畫面上是「爆炸發生在飛機後面」。真實的
火球會先隨著殘骸往前衝，再被空氣迅速煞住；阻尼 4 s⁻¹ 的時間常數 0.25 s
正好在壽命之內煞停，所以它是**跟著衝出去再停下來**。

**顏色即透明度**：加法混合下淡到黑就是淡出，與 `muzzle.ts:164` 同一招。所以火球不需要 alpha 屬性，但它與黑煙共用同一支著色器（alpha 恆為 1）。

8 m 的火球在 1 km 上是 **13.5 px**（1920 px、65° 視野下每像素 5.9e-4 rad，見 `tracers.ts`）。空戰交戰距離通常在 500 m 內 → 約 27 px。**不需要距離剔除。**

## 6. 黑煙

```
壽命 2.5 s        尺寸 2 m → 9 m 膨脹
混合 Normal       顏色 0x1a1a1a，alpha 0.55 → 0
阻尼 1.5 s⁻¹      上浮加速度 +4.5 m/s² → 終端上浮 3 m/s
容量 3072
```

**上浮寫成加速度而不是速度**，因為積分器只有 `gravity` 這一個欄位（§4）。
終端速度是 `a / k`，要 3 m/s 就是 `a = 3 × 1.5 = 4.5`。與殘骸的阻尼是由
終端速度反推的（§8.2）同一個做法。

煙是**世界靜止**的：一團煙生出來之後就與發射體脫鉤，初速為零，只受上浮與阻尼。拖曳的觀感來自「發射體在動、每一團生在不同位置」，不是來自跟著跑 —— 殘骸每 0.08 s 生一團，150 m/s 下相鄰兩團相距 12 m，本來就是一條連續的煙帶。

### 6.1 發射器與間隔

| 發射器 | 間隔 | 每個發射器的穩態團數 |
|---|---|---|
| 殘骸 | 0.08 s | 31 |
| 大零件（36 片裡最大的 4 片） | 0.30 s | 8 |

20 具殘骸 + 80 片大零件的穩態約 **1,260 團**，容量 3,072 有兩倍餘裕。

**為什麼不是每片零件都冒煙**：36 片全冒的話發射器會從 20×4 變成 20×36，穩態爆到 5,700 團 —— 而且畫面上會糊成一片，讀不出「零件在散開」。只有大的冒煙反而更像。

## 7. 零件

`BoxGeometry` 的單一 `InstancedMesh`，逐實例顏色、縮放與旋轉。

```
數量 36 片／次     尺寸 0.16 – 0.4 m（逐實例縮放）
初速 = 母機速度 + 沿飛行方向的散射錐（半角 40°、20 m/s）
重力 −9.81        阻尼 0.4 s⁻¹ → 終端速度 24.5 m/s
角速度 每軸 ±180°/s，恆定不衰減
壽命 直到入水，或 40 s 上限
容量 40 架 × 36 = 1,440
```

**【尺寸與數量在人工驗收後改過】** 初稿是 12 片 0.8–2.0 m。在試驗場上那讀
起來像「飛機掉了幾塊板子」而不是解體 —— 一片碎片有機翼弦長的一半那麼大。
專案負責人裁決**縮小五倍、數量三倍**：小而多才像碎片。

零件比殘骸輕得多，所以終端速度低得多（24.5 vs 80 m/s）—— 畫面上零件會
被殘骸拋在後面，那是對的。

**「沿飛行方向散狀噴射」= 繼承母機速度再疊一個朝前的散射錐。** 所以零件是往前噴而不是往四周炸開 —— 一架 150 m/s 的飛機解體，碎片的動量本來就還在。

顏色取機種的機身色：P-51D `0x9aa7b4`、Bf 109 `0x7e8a73`（`render/geometry/p51d.ts:241`、`bf109e.ts:175`）。

**方向用整數雜湊而不是 `Math.random()`**，與 `sparks.ts` 的 `hash01` 同一個做法：同一個池格永遠得到同一組方向，重播與測試都可重現。

零件入水時噴 6 顆噴濺（比殘骸的 24 顆小一號），不生水柱。

**零件的入水判定用中心點**，不用 §9.1 的角點解析式 —— 一片零件最大 0.4 m，
用中心與用角點的差距在半片零件之內，而畫面上分辨不出來。角點的做法是為
了**翻滾中的整架飛機**（翼展 11 m）而存在的。

## 8. 殘骸

### 8.1 接管既有的模型

殘骸**不新建任何幾何**。`main.ts:262` 現在是死了就 `visible = false`；改成把那個 `AircraftModel` 交給殘骸池驅動。

**渲染成本等於它活著時的成本，沒有增加** —— 一架飛機的模型在它活著時已經在畫，變成殘骸只是換一個東西寫它的 `position` 與 `quaternion`。殘骸釋放時 `dispose()`。

殘骸池除了模型還需要那架飛機的 `hitBoxes`（§9.1 的入水判定），所以接管時
一併記下 `c.aircraft.spec`。

**螺旋槳停轉。** `main.ts:258` 每幀推進一個全域的 `propRotation` 餵給所有
模型；殘骸不再吃它，而是呼叫一次 `setPropSpin(rotation, false)` 停在當前
角度並切回葉片（不是模糊圓盤）。一架失去動力的飛機，槳是停的 —— 而模型
API 本來就支援這件事（`assembly.ts:52` 的 `setPropSpin`）。

### 8.2 運動

```
初速 = 陣亡瞬間的速度（來自事件）
初始位置與旋轉 = 模型當前的內插姿態（見 §3.1）
重力 −9.81      阻尼 0.1226 s⁻¹  → 終端速度 80 m/s
角速度 每軸 ±120°/s，恆定不衰減
```

**阻尼係數是由終端速度反推的**：線性阻尼下 `v_term = g / k`，要 80 m/s 就是 `k = 9.81 / 80 = 0.1226`。時間常數 8.2 s —— 水平速度也在這個時間尺度上散掉，所以一具 150 m/s 的殘骸會往前飄約 1.2 km 才轉為近乎垂直。

從 4,000 m 掉到海面約 **58 s**。

### 8.3 壽命上限

**存活滿 120 s 就隱藏並釋放。** 正常路徑（掉到海裡再沉 25 m）約 60 s，所以這條只在異常情形觸發 —— 例如殘骸飄出海面網格（10 km 見方，`ocean.ts:39`）之外。它是一道保險，不是主要路徑。

## 9. 表面接觸

### 9.1 用 hitBox 的角點判定，不是模型頂點

殘骸是**翻滾**的，翼尖會比機身重心早很多碰到水。用重心判定會讓水花晚一整個翼展才出現。

判定用 spec 裡的 `hitBoxes`（`hit.ts:27`）：

- P-51D 的六個盒，其 spec 註解寫著「**每一個頂點（螺旋槳除外）都落在這六個盒之內**」（`p51d.ts:114`）。它是一個**已驗證的頂點外殼**，所以水花會在真正的頂點接觸的那一刻或**稍早**觸發，絕不會晚。
- 它與子彈打的是**同一份幾何**。用另一套會出現「打得到但摸不到水」這種只有翻滾殘骸才會暴露的矛盾。

**不列舉 48 個角點。** 旋轉後 OBB 的最低點有解析式：

```
minY = cy − ( |R₁₀|·hx + |R₁₁|·hy + |R₁₂|·hz )
```

其中 `R₁ⱼ` 是旋轉矩陣的第二列（世界 Y 在機體各軸上的投影）。最低角點的位置由各軸取 `−sign(R₁ⱼ)` 得到。每個盒 3 次絕對值加 3 次乘法，六個盒一具殘骸每幀 18 次 —— 可以忽略。

海面高度走 `crash.ts:11` 的 `HeightField`（真實 Gerstner 浪高），與 `isCrashed` 同一個抽象。

### 9.2 入水的表現

```
噴濺 24 顆白色粒子，從接觸點噴出，繞世界 +Y 的圓錐、半角 55°、初速 25 m/s
水柱 10 根，散佈在接觸點半徑 6 m 之內，用現有尺寸
```

**噴濺的軸是世界 +Y 而不是表面法線** —— 水面法線幾乎恆為向上（Gerstner
波的坡度很小），而向上正是水花該去的方向。命中飛機的火花才需要真正的
表面法線（M7 spec §3），因為機身的朝向什麼都可能。

**`splash.ts` 一行都不用改。** 用數量換規模，而不是給水柱加一個尺寸參數。

### 9.3 水下不模擬

入水之後運動**完全不變** —— 重力與阻尼照舊。

**因為看不見。** 海面是不透明的（`ocean.ts:52`，`MeshStandardMaterial` 沒有開 `transparent`，深度照寫），沉到水面以下的東西被水自己擋住。為一段沒有任何觀察者的過程寫水阻力是純粹的浪費。

**沉到接觸點下方 25 m 就隱藏並釋放。** 25 m 是最大包圍球半徑 7.1 m 的三倍多 —— 即使殘骸以最不利的姿態翻滾，也早已整具沒入。

### 9.4 為地面預留

之後要加地面時：

- 高度場換成陸地的 `HeightField`（同一個型別）
- 噴濺顏色是**參數**而不是寫死的白色 —— 土色只是換一個傳進去的 `Color`
- 水柱不發（那是水專屬的）

**地面本身不在這份 spec 的範圍內**，這裡只保證加它的時候不用改殘骸。

## 10. 玩家的例外

**玩家目前不生殘骸。** 他要沿用同一個 `AircraftModel` 原地重生（`main.ts:137`），而殘骸會把模型的所有權拿走。

火球、零件、黑煙照常 —— 只跳過殘骸。

這個例外寫在 `main.ts` 的事件排空處，**不是一條關於「玩家」的規則**，而是關於「這架飛機等一下還要用同一個模型」。專案負責人已載明：未來玩家陣亡會改成**接手僚機的飛機**，那時玩家原本那架不再需要模型，它就是一具正常的殘骸 —— 把那個跳過拿掉即可，殘骸池一個字都不用改。

## 11. 檔案與畫面成本

| 檔案 | 責任 |
|---|---|
| `src/world/kills.ts`（新） | 擊墜事件緩衝。`events.ts` 的鄰居 |
| `src/render/particles.ts`（新） | 廣告板粒子池 + 著色器。火球／黑煙／噴濺共用 |
| `src/render/debris.ts`（新） | 零件：方塊、逐實例顏色與翻滾 |
| `src/render/wrecks.ts`（新） | 殘骸：接管模型、翻滾墜落、表面接觸 |
| `src/world/World.ts` | `destroy()` 推事件；新增 `killEvents` |
| `src/main.ts` | 建立四個池、排空事件、每幀步進；`visible = c.alive` 改為交給殘骸池 |

**畫面成本 +4 個 draw call**（火球、黑煙、噴濺、零件）。殘骸 +0，水柱 +0。

三角形：煙 3,072 × 2 = 6,144、火球 512 × 2 = 1,024、噴濺 1,024 × 2 = 2,048、零件 1,440 × 12 = 17,280 —— 合計約 **26,000**，與一架飛機的機體同一量級。

## 13. 測試策略

與 M7 同一套：**把有行為的規則抽成純函數測，池子測紀律。**

### 13.1 純函數

| 函數 | 為什麼值得測 |
|---|---|
| `lowestCorner(box, quaternion, position)` | **唯一一段會算錯、而且錯了只會「看起來有點怪」的數學。** 對照暴力列舉 8 個角點的結果 |
| `debrisVelocity(parentVel, forward, index)` | 散射錐的半角、繼承母機速度、同一個 index 恆得同一個方向 |
| `particleSize(age, from, to)` / `particleAlpha(age)` | 膨脹與淡出曲線；壽命之外為 0 |
| `integrate(v, gravity, drag, dt)` | 終端速度確實收斂到 `g/k` |

### 13.2 池子紀律

每個池：只有一個 `InstancedMesh`（1 個 draw call）、建立時全部縮成 0、容量正確、環形覆蓋最舊的、壽命結束歸零、連續步進不產生 NaN。

### 13.3 整合

- 20v20 跑滿，`kills.ts` 的事件總數等於陣亡總數（不多不少）
- 擊墜事件緩衝**永不溢位**（容量 = 參戰架數是結構上界，§3）
- 殘骸從生成到入水的軌跡不產生 NaN，且最終被回收（不洩漏）
- 效能閘門：M7 之後 `MULTI_BUDGET_US = 300`。**擊墜表現全在渲染層，不應該動到這個數字** —— 若動了，表示有東西跑進了物理迴圈

## 14. 驗收條件

### 14.1 自動化

1. 擊墜事件的容量等於參戰架數，且一場 20v20 之內不溢位
2. `World` 不 import 任何 `render/` 的東西
3. `lowestCorner` 與暴力列舉 8 角點的結果一致（隨機姿態 1,000 次）
4. 三個粒子池各只有一個 `InstancedMesh`
5. 零件的散射方向落在指定半角之內，且同一個 index 可重現
6. 積分器的終端速度收斂到 `g / drag`
7. 所有池子連續步進 10 秒不產生 NaN，壽命結束都歸零
8. 殘骸釋放後模型被 `dispose()`，池格可重用
9. 玩家陣亡不生殘骸，但生火球與零件
10. `MULTI_BUDGET_US` 不變

### 14.2 人工驗收（專案負責人）

11. 擊墜的瞬間讀得出「爆炸」而不是「消失」
12. 零件明顯是**往前**噴的，不是往四周炸開
13. 黑煙拖曳讀得出殘骸的軌跡，而且不會糊成一團
14. 殘骸的翻滾像失控的機體，不像機械式旋轉
15. 殘骸入水的水花從**先碰到水的那一端**濺起（翼尖先落水時看得出來）
16. 20v20 打到後期，滿天殘骸與煙不會讓畫面變成噪訊
17. 玩家自己被擊墜時，火球與零件仍然看得到
18. 火球跟著殘骸往前衝了一小段才煞住，不是留在飛機後面（§5）
19. 殘骸的螺旋槳是停的，不是還在轉或還是模糊圓盤（§8.1）

## 15. 明確不做（記錄在案）

| 項目 | 理由 |
|---|---|
| 爆炸音效 | 專案目前完全沒有音訊子系統 |
| 動態光源（火球照亮機身與海面） | 特效用的是無光照材質，40 架會有上百個光源 |
| 機體解體成多塊 | 零件是額外生成的。真正切開程序化機體幾何是另一個量級的工作 |
| 水面油污與燃燒 | 水柱與噴濺已經回答「它掉在這裡」 |
| 地面與土色噴射 | 只保留接口（§9.4）。地面本身是另一份 spec |
| 殘骸互相碰撞、殘骸打到飛機 | 飛機互撞從 M5 起就明確不做，殘骸沒有理由更嚴格 |
| 玩家陣亡留下殘骸 | 現況玩家原地重生要沿用模型。等「接手僚機」實作後自動成立（§10） |
