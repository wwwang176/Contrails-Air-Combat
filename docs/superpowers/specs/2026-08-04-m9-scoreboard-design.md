# M9 戰績與接手僚機 —— 設計文件

## 1. 目標

讓一場遭遇戰有**結果**，而且看得到**誰打了誰**。

三件事：

1. **擊墜歸屬** —— 每一次擊墜記在兇手身上，20 秒內打過的其他人記助攻。
2. **玩家陣亡接手僚機** —— 取代目前「死了立刻無限重生」，讓「我方全滅」這件事有可能發生。
3. **記分板** —— 按住 TAB 顯示雙方 K/D/助攻，依 K 排序，自己高亮，陣亡灰字。

分出勝負時顯示勝敗橫幅並攤開記分板，按 R 重開。

【為什麼這一份不包含主選單】M10 才做選單。切開的理由是 M9 **完全不需要知道選單存在** —— 它在目前一開就打的 20v20 裡就能完整驗收。M10 屆時把臨時的勝敗橫幅換成結算畫面，並重用這裡做好的記分板元件。

## 3. 資料模型：飛行員與座位分離

**一列＝一位飛行員。飛行員與座位（`Combatant`）是兩回事。**

```ts
// src/battle/pilots.ts
export interface Pilot {
  /** 顯示名。一場內不變，跟著人走 */
  name: string
  kills: number
  deaths: number
  assists: number
  /** 還在天上 */
  alive: boolean
  /** 玩家本人。接手時跟著人走 */
  isPlayer: boolean
}

export interface Roster {
  /** 依**座位**索引：`pilots[i]` 是目前坐在 `world.combatants[i]` 裡的人 */
  readonly pilots: Pilot[]
}
```

【為什麼不把 K/D 直接掛在 `Combatant` 上】因為玩家會換座位。掛在座位上的話，玩家接手僚機之後自己的擊墜數會留在那具殘骸上，畫面上看起來像戰果被清掉了。

【為什麼陣列仍然依座位索引】所有既有的歸屬資訊（彈丸的 `owner`、擊墜事件的 `index`）都是座位索引。名冊跟著座位排，這些一行都不用改；而「換人」就只是**交換陣列裡的兩個元素**。

**接手＝交換 `pilots[a]` 與 `pilots[b]`。** 名字、K、D、助攻、`isPlayer` 全部一起搬。交換之後坐在殘骸裡的那一位（被接手的 AI）才被記為陣亡 —— 順序見 §7。

## 4. 擊墜歸屬（`World` 層）

### 4.1 兇手

`applyDamage` 已經知道射手，但 `destroy` 不知道。改成：

```ts
destroy(c: Combatant, killer?: Combatant): void
applyDamage(victim, damage, part, shooter?) // → this.destroy(victim, shooter)
```

撞海（`crashPolicy` 那一條）不帶兇手。

**自摔在戰績上完全不存在**（專案負責人於 M9 交付後裁決，見 §15.4）：受害者不吃陣亡數（D）、沒有人拿擊墜（K）、窗口內打過他的人也拿不到助攻。唯一留下的是 `alive = false` —— 他確實不在天上了，記分板要把他畫成灰的。

【為什麼連 D 都不記】自殺不是一次戰鬥結果。記了 D 而沒有對應的 K，記分板就會出現「我方死 3、敵方殺 0」這種讀起來像壞掉的畫面 —— 而玩家沒有任何欄位可以拿來對帳。不記之後守恆律變成乾淨的**擊墜總和 = 陣亡總和**。

### 4.2 擊墜事件多帶一欄

`KILL_STRIDE` 由 7 加到 8，第 8 欄是兇手的座位索引，**−1 表示無兇手**。

【為什麼加在既有的事件上而不是另開一個結構】「誰死了」這件事已經有一個緩衝在傳了，再開一個平行的緩衝就是兩份要同步的真相。火球、黑煙、零件三個消費者都用 `e * KILL_STRIDE + 偏移` 取值，加一欄對它們是透明的（但那三個檔案的既有測試若寫死了 stride，要一併更新）。

### 4.3 誰來記

**記分板的更新在 `stepBattle` 裡**，緊接在 `world.step(dt)` 之後、`main.ts` 排空特效之前。

【為什麼不是 `World`】`World` 不該知道有「名字」或「玩家」這回事 —— 它連隊伍顏色都只知道 `'blue' | 'red'`。而且放在 `stepBattle` 裡，接手的身分互換與擊墜的記錄可以保證在同一個地方、同一個順序（§7 依賴這件事）。

【為什麼不是 `main.ts`】`main.ts` 進不了單元測試。整場戰鬥的統計必須是可測的。

## 5. 助攻

**規則：擊墜發生時，除了兇手之外，任何在最近 `ASSIST_WINDOW` 秒內對死者造成過傷害的人各記一次助攻。**

### 5.1 要存什麼

```ts
// World
/** 世界時鐘，s。每個 step 累加 */
time: number
/** damageTime[攻擊者 * N + 受害者] = 最後一次命中的世界時間 */
damageTime: Float32Array
```

`applyDamage` 有射手時寫入 `damageTime[shooter.index * N + victim.index] = this.time`。

【初值用 −Infinity 而不是 0】世界時間從 0 開始，用 0 當「沒打過」等於宣稱每個人在 t=0 都打過每個人。`time − (−Infinity) = Infinity`，恆大於窗口。`Float32Array` 存得下 −Infinity。

【容量】`N` 是 `world.combatants.length`，而 `World.add` 會讓它成長 —— `damageTime` 要和 `killEvents` 一樣在 `add` 裡重配。20v20 是 1,600 個 float。

### 5.2 判定

擊墜時掃受害者那一欄（N 次）：

```
記助攻 ⟺ a !== killer
       && a !== victim
       && time - damageTime[a * N + victim] <= ASSIST_WINDOW
```

【為什麼要排除 `a === victim`】自傷目前不可能發生（彈丸判定排除自己），但一條「自己助攻自己」的縫隙不該留著等某天被打開。

【`World.respawn` 要清掉受害者那一欄】殲滅制下沒有人重生，但靶機路徑還在（M2 遺留）。不清的話重生後的第一次擊墜會把上一條命的攻擊者算進助攻。

## 6. 飛行員名冊

### 6.1 名字怎麼來

- 每個陣營一份名冊：**同盟國英美名、軸心國德名**。
- 開局抽一顆 32 位種子，用 `mulberry32` 洗牌各自的名冊，前 N 個依序指派。洗牌保證**同一場內名字不重複**。
- 種子存在 `Battle` 上 —— 記下來就能重現同一場的名單。

【為什麼名冊要 ≥ 24 個】M10 的每隊上限是 20。24 留一點餘裕，而且洗牌的前 20 個不會每場都是同一批。

【陣營而不是隊伍顏色】名冊跟著**機種所屬的陣營**走。M9 的機種還是寫死的（藍隊 P-51、紅隊 Bf109），所以現在等價；M10 讓玩家選陣營之後，藍隊飛 Bf109 時就會拿德文名。這條規則現在就定好，M10 不用回頭改。

### 6.2 這是專案第一次用 `Math.random()`

只用在**抽那一顆種子**，之後全部走 `mulberry32`。

【為什麼不違反決定性】M5 spec §3.1 要求「同一組設定跑兩次要逐幀一致」，指的是**物理**。名字不進入任何物理路徑 —— 它只是一個字串，不影響出生位置、AI 決策或彈道。既有的決定性整合測試不比對名字，或者自己指定種子。

### 6.3 玩家怎麼標

玩家和所有人一樣從自己陣營的名冊抽一個名字，記分板上那一列名字後面加「（你）」並高亮。

【為什麼不是固定寫「玩家」】接手僚機時名字要跟著人走（§7）。給玩家一個真正的名字，「他替你死了」這件事在板上才讀得出來 —— 否則會看到「玩家」這個名字出現在陣亡列。

## 7. 玩家陣亡與接手僚機

### 7.1 順序

玩家的座位 A 被擊毀，在 `stepBattle` 排空擊墜事件時：

1. **選接手目標 B** —— 同分隊壓縮後的 `members[1]`（玩家釘在 `members[0]`，所以那就是他的僚機）。同分隊只剩玩家一人時，取索引順序上第一個存活的其他友軍。都沒有 → 跳到 7.3。
2. **立刻交換 `pilots[A]` 與 `pilots[B]`。** 現在 `pilots[A]` 是那位 AI（坐在殘骸裡）、`pilots[B]` 是玩家。
3. **才記錄這次擊墜**：`pilots[A].deaths++`、`pilots[A].alive = false`；有兇手的話 `pilots[killer].kills++`；助攻照 §5 記。

於是板上讀到的是「那位 AI 陣亡了」，玩家的名字、擊墜數與助攻數一格也沒少。

【為什麼交換一定要在記錄之前】反過來的話這次陣亡會記在玩家頭上，交換只是把它搬給 AI —— 結果一樣，但兇手的擊墜對象也會變成「玩家」。一個順序解決兩件事。

### 7.2 控制權延後 `TAKEOVER_DELAY` 秒

身分立刻互換，但**操縱權在 2 秒後才移轉**。那 2 秒鏡頭停在擊墜點。

【為什麼要這 2 秒】M8 的人工驗收條件 17（「玩家自己被擊墜時看不看得到火球與零件」）到現在無法驗收，正是因為玩家死掉的同一幀就重生到別的地方去了。這 2 秒是那個條件成立的前提。

【為什麼鏡頭是停住而不是追殘骸】模型交給殘骸池之後，`Visual.position` 就不再更新（M8 的 `wrecked` 旗標）。停在擊墜點看火球與四散的零件，讀起來就是一個死亡鏡頭。要追殘骸得讓相機改讀殘骸池的位置，那是為了兩秒鐘多開一條耦合。

延遲結束時要跟著轉移的東西：

| 東西 | 怎麼轉 |
|---|---|
| 控制器 | `combatants[B].controller = playerController`（B 原本那顆 `AiController` 丟掉） |
| `battle.player` | 指向 `combatants[B]`。**欄位要從 `readonly` 改成可寫** |
| 編制的釘選 | `flights.pinned = B`。`compactFlights` 每步重跑，下一步自動生效 |
| 觀測用 AI | `playerAi.selfIndex = B`、`setDecisionPhase` 重設 |
| 第一人稱眼點 | `rig.options.firstPersonOffset` 抄 B 的模型 `eyePoint`（兩隊機種不同時位置不一樣） |
| 站位 | `wireStations` 用 `instanceof AiController` 判斷，自動跟上 |

### 7.3 沒有人可以接手

不交換，玩家自己那一列記陣亡，`outcome = 'defeat'`。

**「我方全滅」與「玩家無機可接」是同一個條件** —— 玩家佔著友軍的一個座位，所以只要還有第二個藍隊座位活著就接得到。這讓落敗條件只有一條。

### 7.4 已知的邊界情況

延遲的 2 秒內，座位 B 仍然由它原本的 AI 在飛（控制器還沒轉移），所以**B 有可能在那 2 秒裡被打死**。那時 `pilots[B]`（＝玩家）再死一次，規則遞迴套用：再選一個 C、再交換、再延遲。

玩家因此可能在沒有操縱的情況下多吃一次陣亡。這是罕見（2 秒窗口）且行為明確的結果，寫在這裡是為了不讓它變成一個「怎麼會這樣」的 bug 回報。

## 8. 勝負結果

```ts
export type Outcome = 'fighting' | 'victory' | 'defeat'
```

掛在 `Battle` 上。`stepBattle` 判定：敵方全滅 → `victory`，我方全滅 → `defeat`。

**移除 `BattleConfig.resetCountdown` 與自動重置。** R 鍵維持現有行為（`resetBattle` 重開整場），並把 `outcome` 歸回 `fighting`。

【為什麼世界要繼續跑】分出勝負之後不停止 `world.step` —— 殘骸還在掉、煙還在飄。立刻凍結畫面看起來像當掉，而 M5 spec §3.2 條件 15 已經為「不要瞬間換場」下過同樣的判斷。

## 9. 記分板

### 9.1 為什麼是 DOM 而不是 HUD 的 canvas

40 列 × 4 欄的表格、排序、灰字、高亮 —— canvas 要自己排版每一格；DOM 一個表格加 CSS 就好。而且 M10 的結算畫面本來就是 DOM，**兩邊共用同一個渲染函式**。

HUD 那塊 canvas 的職責是每幀重畫、位置與世界相關的飛行儀表。記分板是按需顯示的靜態表格，不屬於那裡。

### 9.2 版面

兩欄並排（藍隊左、紅隊右），各自依 K 排序。每列：名字、K、D、A。玩家那一列高亮並在名字後加「（你）」，陣亡者整列灰字。

20 列 × 2 欄在 1080p 放得下。

### 9.3 排序

依 K 降序；K 相同時依助攻降序；再相同時依名字。

【為什麼要指定第三層】只比 K 的話同分的列會隨著陣列順序跳動 —— 一個看起來像 bug 的東西，而且測試會不穩定。

### 9.4 顯示時機

- 戰鬥中：按住 TAB 顯示，放開隱藏。`keydown` 要 `preventDefault`（Tab 預設會移動焦點）。
- 分出勝負：自動攤開並停留，配上勝敗橫幅。

## 11. 測試

**純函數（node 環境，不碰 DOM）**

- 名字產生器：同種子同結果；一場內不重複；陣營對到正確的名冊。
- 助攻窗口的邊界：`ASSIST_WINDOW − 0.1` 算、`+ 0.1` 不算。
- 排序：K 降序；K 同比助攻；全同比名字（穩定）。
- 接手目標的選取：同分隊優先；同分隊全滅時取索引順序第一個存活友軍；無人可接回傳 −1。

**`World` 層**

- 擊墜記在兇手身上。
- 撞海不記在任何人身上（事件的兇手欄是 −1），而且受害者自己也不吃陣亡數、沒有人拿助攻 —— 只剩 `alive = false`。
- 兇手不重複拿助攻。
- 窗口外的傷害不算助攻。
- `respawn` 清掉受害者那一欄。

**`stepBattle` 層**

- 接手時**先交換再記錄** —— 斷言陣亡記在那位 AI 身上、玩家的擊墜數不變。這是 §7.1 的核心，必須有一條會紅的測試守住順序。
- 無人可接時 `outcome === 'defeat'`。
- 敵方全滅時 `outcome === 'victory'`。

**整合**

- 一場戰鬥跑完，守一條**守恆律：全體擊墜數 ＝ 全體陣亡數**（自摔在戰績上不存在，所以沒有補正項）。那是這套歸屬最有力的一條總體檢查 —— 任何漏記或重複記都會讓它失衡。另配一條**退場人數 ＝ 陣亡數 ＋ 自摔數**，守住「不記戰績」沒有被實作成「當作沒發生」。實際採用的編制與理由見 §15.2。
- 既有的 20v20 整合測試要維持逐幀一致（名字不比對）。

**不測**：DOM 的渲染。與 HUD 繪製同一條紀律。

| 常數 | 值 | 為什麼 |

## 13. 人工驗收條件

1. 按住 TAB 看得到雙方 40 列，依 K 排序，自己高亮。
2. 打下一架敵機，自己的 K 加一。
3. 打傷一架、由僚機補掉，自己拿到助攻。
4. 只擦到一發、二十幾秒後那架才被打掉 —— **沒有**助攻。
5. 自己撞海：沒有任何人的 K 增加，我方的陣亡數也**不變**，只是那一列變灰。
6. 自己被打下來：看得到火球與零件散開約兩秒，然後接手僚機。
7. 接手之後記分板上自己的名字還在活著那一列、K 沒有歸零，而被接手的那位在陣亡列。
8. 接手後第一人稱視角的眼點是對的（不會落在座艙外）。
9. 接手後僚機隊形沒有亂掉（玩家仍然是分隊長機）。
10. 打光敵人 → 勝利橫幅 + 記分板攤開；按 R 重開一切歸零。
11. 藍隊被打光 → 落敗橫幅。
12. 一場打完，記分板上雙方 K 的總和**恰好等於**雙方陣亡數的總和。灰掉但陣亡數為 0 的那幾列就是自摔的人。

## 14. 與 M10 的介面

M10 會用到、所以這一版就要定好的東西：

- `Battle.outcome` —— 結算畫面讀它決定顯示勝或敗。
- `src/ui/scoreboard.ts` 的渲染函式 —— 結算畫面原封不動重用，只是不再需要按住 TAB。
- 名冊依**陣營**而不是隊伍顏色（§6.1）—— M10 讓玩家選陣營時不用回頭改。

M10 才動、這一版刻意不碰的：`BattleConfig` 仍然是單一的 `perSide` 與寫死的機種。

## 15. 交付紀錄

### 15.1 實作中發現並修掉的缺陷

**無。** 十四個任務全部照計畫落地，沒有一條測試在實作階段暴露出設計上的錯誤。計畫寫作時的自我覆核已經先抓掉三處（僚機座位寫成 `b.blue[1]`、擊墜緩衝的游標式排空、兩處含糊指示），那三處若留到這裡都會是實作階段的紅燈。

### 15.2 與 spec 的偏離

**一、§11 的整合測試由「2v2 真打到分出勝負」改為「在一場真的在跑的 20v20 上人為安排擊墜」。**

實測（實作過程中量的，見下表）顯示這一版的 AI 打不完一場小規模戰鬥：

| 編制 | 開局距離 | 跑多久 | 第一次陣亡 | 總陣亡 |
|---|---|---|---|---|
| 2v2 | 800 m | 120 s | 從未 | 0 |
| 2v2 | 1,500 m | 240 s | 從未 | 0 |
| 4v4 | 800 m | 120 s | 從未 | 0 |
| 20v20 | 2,000 m | 90 s | 43.1 s | 1 |
| 20v20 | 10,000 m | 180 s | —— | 1 |
| 20v20 | 2,000 m | 240 s | —— | 1 |

對頭通場之後雙方追不到彼此。這是 AI 的性質，不是 M9 的缺陷 —— M6 spec §4.1 已經記過同一件事（「60 秒內陣亡數可能是 0」）。

依 spec 原文寫的測試會是一條**空的**斷言：一場只死一個人，測不到助攻、測不到自摔、測不到接手，而且要花 24 秒的實際時間才跑得完。改成世界照常在跑（編制壓縮、站位、命中判定、彈道全部是真的），只有「誰在什麼時候死」由測試安排，四種路徑輪流走：被打死（含助攻）、自摔、玩家陣亡接手。守恆律因此覆蓋到全部三種歸屬，跑 30 秒模擬時間、約 4 秒實際時間。

測試自己守住非空覆蓋：`scripted >= 20`、`takeovers >= 5`、`selfDestructs >= 5`。少了這三條，「安排擊墜」的版本會有一天悄悄退化成「什麼都沒安排、守恆律當然成立」。

兩條新測試都做過**紅燈驗證**：拿掉 `pickTakeover` 的跨分隊後備，接手鏈報 `expected 'fighting' to be 'defeat'`；把 `recordKill` 的自摔守衛移到 `deaths++` 之後（也就是讓自摔重新記陣亡），守恆律報 `expected 21 to be 29`。

**二、多加一條整合測試「接手鏈打到底」（8v8）。**

spec §7.3 只說「無人可接時判落敗」，而單元測試是用「人為把其他藍機標成死亡」造出那個狀態的。8v8 讓玩家從第二個 Schwarm 一路接到第一個 Schwarm，把**跨分隊接手**那一條分支端到端走過一次 —— `pickTakeover` 的第二個迴圈只有在這裡才走得到。

**三、`main.ts` 的接手多做一件 spec 沒寫的事：把瞄準點放回新機的機首。**

不放的話它還指著舊機體墜落前指的方向（多半是海面），接手的第一瞬間新機就被硬扯下去。與 `I` 交還操縱時「把瞄準點留在機首」是同一條既有理由。

### 15.3 實作時觀察到、留給人工驗收判斷的

**玩家陣亡後那 2 秒，相機定在死亡地點不動。** 舊機體的模型交給殘骸池之後，每幀的內插迴圈就不再寫它的 `position`，而相機讀的正是那個值。結果是一個定點的死亡鏡頭：火球與零件都在那裡，看得很清楚；但殘骸自己會翻滾著飛出畫面。

要改成跟拍殘骸只需一行（把 `v.model.group.position` 抄回 `v.position`），但「定點看爆炸」與「跟著殘骸翻滾」哪個對，是一個要用眼睛決定的問題。列入人工驗收條件 6 一起看。

---

### 15.4 交付後的裁決：自摔在戰績上完全不存在

**起因**：專案負責人在遊戲裡按 TAB，看到「我方陣亡 3、敵方擊墜 0」。

**量測**：

| 情境 | 結果 |
|---|---|
| 20v20 真打 240 s（玩家也交給 AI） | 全場 **0** 次陣亡 —— AI 之間幾乎打不死人 |
| 把玩家推到海面下、跑一步 | 我方陣亡 +1、敵方擊墜 0，玩家同時接手僚機 |

那三次是玩家自己撞海。原設計（§4.1 初版）只規定「自摔不算任何人的擊墜」，陣亡數照記 —— 數字合法，讀起來卻像壞掉：記分板沒有自摔欄，玩家無從對帳；而且因為接手時身分互換，玩家自己那一列的陣亡數是 0，畫面上是「三個不認識的人死了、沒人殺他們、而我好端端的」。

**裁決**：自殺不算真的擊殺 —— **不記 K、不記 D、也不記助攻**。只有 `alive = false` 留下來。

**後果**：

- 守恆律由「擊墜 = 陣亡 − 自摔」變成**「擊墜 = 陣亡」**。玩家可以直接拿記分板對帳。
- `drainKills` 對自摔連助攻都不掃 —— 讓這條規則在呼叫端看得出來，而不是藏在 `recordKill` 裡面。
- `assistCredits` 從此不會收到 `killer = −1`。那條路徑的測試一併刪除：一條敘述已經與設計相反的測試，比沒有測試更糟。
- 「陣亡」這一欄的意義收窄成**被敵人擊落的次數**。撞海的人是灰的一列、陣亡數 0 —— 那正是自摔在記分板上的樣子。

**一個沒有一起改的**：被打成重傷、失控掉進海裡，敵人一樣拿不到擊墜（只拿得到助攻，因為助攻走的是傷害時刻表而不是擊墜事件）。多數空戰遊戲會把這種算給最後一個打中的人。判定用的資料（`damageTime`）已經在了，要改是小工，但這一版不做 —— 專案負責人未裁決。
