## 1. 這一輪為什麼不是「AI 的路徑層」

backlog §7 把「AI 的路徑層：集合點要繞開山」標成 ★、排在戰術層前面。
開分支之後第一件事是量它值不值得做，**量出來的答案是不值得**。

### 1.1 量到什麼

把群島完整注進每一架的 `AiController.terrain`，跑遍**全部十張任務卡加
遭遇戰**，各 300 秒：

```
                      繞島佔時   安全層-地形
  遭遇戰                0.00%      0.00%
  allies-sweep          0.00%      0.00%
  allies-intercept      0.00%      0.00%
  allies-strike         0.00%      0.00%
  allies-escort         0.00%      0.00%
  allies-evac           0.00%      0.00%
  axis-patrol           0.00%      0.00%
  axis-intercept        0.00%      0.00%
  axis-strike           0.00%      0.00%
  axis-escort           0.00%      0.00%
  axis-evac             0.00%      0.00%
```

**對照組**（同一支探針，把一座 900 m 的島搬到戰場正中央、仗擺在 600 m）：

```
  對照：島在場中央      11.74%      0.16%
```

對照組排除了「儀器壞了」這個解釋。上一輪寫的地形感知是好的，**是真實的仗
從來不靠近山**。

### 1.2 兩個獨立的原因

```
  高度   開場恆為 4,000 m。20v20 實跑 600 秒，全場最低只到 2,292 m ——
         離最高的島頂還有 1.3 km
  位置   就算把仗壓到 600 m，戰場中心 4.7 km 之內最高的島只有 362 m。
         AI **正確地**直接飛過去（`checkClimb` 回 ok，不轉）。
         第一座 861 m 的山在 4,675 m 外
```

第二條特別值得記：那個情境下的 `繞島 0.00%` **不是缺陷，是正確行為**。
一座 362 m 的島對 600 m 的飛機不構成障礙。

### 1.3 順帶量到的第三件事

路徑層唯一活著的消費者是**撤退令**（`flank` 由 `FLANK_ENABLED = false` 關著、
`focus` 不使用 `point`）。它在上面每一場裡發出的張數是 **0** —— `idle` 計時器
被射擊解一直歸零，而 `gap >= withdrawRange − arriveRadius × MIN_TRIP_RATIO`
這道閘門在散開的 20v20 裡幾乎恆真。

所以就算地形進得了場，路徑層仍然要先解決「撤退令發不出來」。那是另一件事。

### 1.4 裁定

專案負責人 2026-08-27：**先讓地形進得了場。**

## 4. 山什麼時候才擋得住路

這一節是這一輪全部定值的依據。

`terrainSense` 的 `checkClimb` 判「爬得過」的條件是，沿航跡每一個取樣點 `s`
都滿足

```
  y₀ + s · tan(recoveryPitch) ≥ h(s) + clearance
```

`recoveryPitch = 20°`、`clearance = 120 m`、前視 `SENSE_RANGE = 1,200 m`。
所以**一座峰高 `peak` 的山擋得住路，條件是**

```
  y₀ < peak + 120 − s · 0.364
```

`s` 是它離飛機多遠。代進 `peak = 900`：山在 1,200 m 外時要 `y₀ < 583 m`，
山在 600 m 外時放寬到 `y₀ < 802 m`。**離山越近，越擋得住。**

實測（8v8，一座 `peak = 900` 的島在 (1200, −2400)，跑 120 秒）：

```
  開場高度   繞島佔時   安全層-地形   低於 583 m 佔時
     400 m    13.92%       0.85%          28.39%
     600 m     7.23%       0.28%          14.53%
     800 m     2.09%       0.07%           2.80%
   1,000 m     0.00%       0.00%           0.83%
   1,500 m     0.00%       0.00%           0.00%
   4,000 m     0.00%       0.00%           0.00%
```

曲線與上面那條式子對得起來。**分水嶺在 800～1,000 m 之間**，而不是
「只要有山就會繞」。

## 5. 設計：選得到

### 5.1 `SkirmishSetup` 加兩個欄位

```ts
export interface SkirmishSetup {
  readonly blue: readonly string[]
  readonly red: readonly string[]
  readonly playerAt: number
  /** 這一場的地形 */
  readonly terrain: TerrainKind
  /** 開場高度，m */
  readonly altitude: number
}
```

**兩個都有預設值，而且預設等於現況** —— `terrain: 'archipelago'`（`main.ts`
現在就寫死這個）、`altitude: 4000`（`DEFAULT_BATTLE.altitude`）。不動設定的
人玩到的**規則**一個字都沒變；**地圖會變**，見 §6.3。

**`TerrainKind` 要搬家。** 它現在定義在 `render/terrain.ts`，而
`battle/skirmish.ts` 不該相依渲染層。搬到 `world/terrainKind.ts`，
`render/terrain.ts` 再匯出（既有 import 站點不用動）。

**任務模式不吃這個設定。** 任務有自己的劇本，地形固定 `'archipelago'`。
`main.ts` 的 `enterBattle` 在遭遇戰與任務兩條路上各自決定 kind ——
共用一個「上一次選了什麼」的變數的話，打完一場海面遭遇戰再點任務卡，
任務會靜靜地變成海面。

### 5.2 高度只給三個選項

```
  甲板     600 m   ← 地形是主角。§4 實測繞島 4.2~7.2%
  低空   1,500 m   ← 島在腳下，但擋不住路
  中空   4,000 m   ← 預設，現況
```

**為什麼上面不再加。** He 111 的實用升限是 6,300 m，而 `altitudeSpread`
還會再加 ±300。開場給到 6,000 的話，混編裡的 He 111 一出生就在升限上、
會一路往下沉 —— 那不是「高空關卡」，是壞掉的關卡。4,000 已經是地形完全
不相干的高度，再往上不增加任何玩法維度。

**為什麼甲板是 600 而不是 400。** 400 m 在 8v8 給出更高的繞島佔時
（13.92%），但那是因為飛機被壓在海面上；20v20 的同一組反而掉到 0.00%。
600 m 在 8v8 與 20v20 兩種規模都穩定落在 4~7%，**兩邊都不是邊界**。

**為什麼中間那一格留著。** 1,500 m 的繞島佔時確實是 0 —— 島在那裡是景，
不是障礙。那仍然是一種玩法（貼著島頂纏鬥、看得見地面參考），把它寫成
「擋不住路」而不是假裝它有戰術意義。

### 5.3 選單

`index.html` 的 `#skirmish` 區塊加一列，`ui/menu.ts` 用與 `renderSide`
同一套按鈕樣式。**兩組都是單選按鈕列**，不是下拉 —— 與同一頁的其他控制項
一致。

**DOM 接線的護欄是 `test/e2e/skirmish-roster.e2e.ts`**（專案沒有
`menu.test.ts`）。那一支照既有模式加一條「點高度按鈕之後開場高度真的變了」。

## 6. 設計：打得到

### 6.1 為什麼是搬山，不是搬戰場

戰場幾何（`entryRange = 10,000`、出生在 z = ±5,000、`lateralOffset = 1500`）
是**幾十條既有護欄的基準** —— `ai-withdraw-anchor`、`multi-battle`、
`ai-targeting`、`replayDigest` 全部建立在它上面。動它等於重錄全部。

搬山只影響三支直接建群島的測試（`archipelago`、`terrain`、
`terrain-avoidance`），而那三支斷言的都是**性質**，不是座標。**搬山便宜得多。**

### 6.2 錨島：兩座，取代兩座大島

```ts
const ANCHORS = [
  { cx: 2500, cz: -950, radius: 1400, peak: 900, pa: 0, pb: 0 },
  { cx: -2500, cz: 950, radius: 1500, peak: 850, pa: 2.1, pb: 4.3 },
]
```

- **`TIERS[0].count` 由 2 改成 0**，兩座錨島補上那兩席。島數維持 48。
- 兩座**先放進 `islands`，自己不呼叫 `rand()`**（位置與相位都是常數）。
- 島緣離原點 868 m 與 739 m，兩座之間的通道 **1,608 m**。

**為什麼是兩座。** 一座山對一團會漂的纏鬥是**開關式**的結果。實測單座在
4v4~20v20 五種規模裡只有兩種會用到，而且其中一種繞的還是**別的島**：

```
  單座 (2600,−1400)   4v4 0/8   8v8 2/16(繞 #6)   12v12 0/24   16v16 7/32   20v20 6/40
  單座 (2000,−800)    4v4 0/8   8v8 7/16          12v12 1/24   16v16 0/32   20v20 2/40
  兩座                4v4 1/8   8v8 0/16          12v12 1/24   16v16 2/32   20v20 7/40
```

兩座之後四種會用到，**而且每一次繞的都是錨島**。

**通道 1,608 m 是刻意的。** 那正是 `CHANNEL_MIN` 當初設計的情境：
「左右有島、中間通得過」。兩隊由 z = ±5,000 對頭進場，從中間穿過去，
纏鬥在兩座山之間展開。實測**交會前的地形介入率是 0.00%** —— 進場沒有被
干擾，山是在纏鬥開始之後才起作用。

**兩座尺寸不同是必要的。** 相同的話「最高」與「最寬」會是同一座，而
`terrain-avoidance` 的飛行掃描以那兩者當代表 —— 192 組裡有 64 組會靜靜地
變成重複。相位也不同，不然畫面上是兩座一模一樣的山。

**為什麼是寫死的，不是調 `SEED` 調到有兩座落在那裡。** 種子釣魚的結果沒有
人看得懂，而且下一個動生成器的人會把它釣掉。

**為什麼 `peak` 不貼 `PEAK_MAX`（1,000）。** 上限是給隨機那一批的餘裕；
寫死的這兩座貼著上限只是在跟自己的護欄擦邊。

### 6.3 地圖會變，而且 LCG 的呼叫次序也會變

**不要宣稱「序列不變」。** 錨島本身不抽數，但它會讓後面的島在 rejection
時多抽位置，而 `TIERS[0].count` 從 2 改成 1 更是直接少掉一整輪的
radius／peak／相位。**後續每一座島都會不一樣。**

逐位元決定性仍然成立（同一個種子、同一段程式、同一個結果），既有的四條
性質測試（決定性、直徑下限、峰高上限、通道間隙）也都是性質而不是定值。
但下面這三支的**實測值**要重跑、重記：

```
  archipelago.test.ts        島數與最差通道間隙（上一輪 48 / 1,504 m）
  terrain.test.ts            islands[0] 現在是錨島；逐三角形比對跑新地圖
  terrain-avoidance.test.ts  它動態挑最高／最寬／最小三座，三座都會換人
```

`terrain-avoidance` 的 `worstClear` 與「沒回到出發距離」那些數字**必須重跑**，
不能假設不受影響。

### 6.4 沒有出生帶淨空

初稿有一條「島不得侵入出生帶」的約束。**砍掉了**，三個理由：

- 現行地圖唯一侵入那塊矩形的是 (3031, −5963)、`peak ≈ 90` 的小島。甲板
  開場是 600 m，`altitudeSpread` 最低只到 −300 → 出生高度 ≥ 300 m。
  **90 m 的峰不可能撞到。**
- 那是一個粗矩形，會為了兩塊出生區重畫地圖。
- 它與初稿的錨島座標**自相矛盾** —— 錨島自己的膨脹圓侵入 206 m。

取而代之的是一條直接的斷言：**每一架的出生點高度減去 `heightAt` 大於
`clearance`**。那正是我們真正在乎的事，而且不必發明一個矩形。

## 8. 量測與驗收

### 8.1 主要護欄：`test/integration/terrain-in-play.test.ts`

20v20 遭遇戰（預設編制）、群島、180 秒，兩個高度各跑一次。地形照既有探針
的做法直接注入建好的 battle（`ctl.terrain` 與 `world.crashPolicy`）。

```
  altitude  600   被地形接管過的架數 > 0     實測 7/40，佔時 0.25%
                  撞山只能是「來不及」的     實測 1 次，接近率 124 m/s
                  出生點離地 > clearance     實測 300 m
  altitude 4000   被地形接管過的架數 = 0     ← 對照組
```

**為什麼用 `safetyAction === 'terrain'` 而不是 `sense.island >= 0`。**
前者已經是公開欄位，而且語意更強：**地形真的改寫了控制輸出**，不只是
「感知到有一座島」。`sense` 是 private，為了測試把鎖存索引公開出去是
test-only API 污染。

**為什麼是「架數」而不是「佔時」。** 佔時是 0.25%，那個數字對規模與這一場
的走向都很敏感。「有幾架被地形接管過」是一個整數，而且它問的正是我們在乎
的事。

**為什麼「> 0」而不是「> 某個百分比」。** 那個百分比是這一輪第一次量到的
數字，訂門檻等於把觀測值抄成護欄 —— 上一輪的教訓（backlog §7）。

**為什麼要對照組。** 沒有它的話，`> 0` 這一條在「地形層永遠回報介入」時
也會綠。對照組把「高度是那個變因」一起釘住。

**這一條是承重的。** 把兩座錨島拿掉、`TIERS[0].count` 還原成 2（也就是回到
上一輪那張隨機地圖），同一場量到 **0/40**，護欄立刻紅 —— 那正是這一輪開工
前量到的那件事。

### 8.2 撞山：判準與那一次實測

**「撞山」怎麼數。** 兩個坑：

```
  事後讀 hp        World.destroy 第一行就是 c.hp = 0 —— 判準恆為「沒撞山」
  只數死在陸地上   被打下來的殘骸落在島上會被算成撞山（實測一場 1，實際 0）
```

正確做法是**在 `crashPolicy` 這個 predicate 裡讀 `hp`** —— 那一刻它還是
真值，兩者分得開。

**實測有一架撞了，而且判準因此改了。** 滿血的 P-51D 俯衝追人，2.5 秒掉
240 m，而**腳下的地形同時升了 85 m**。`clearance` 是 120 m，那個常數照
**平的海面**訂的 —— 地形會自己迎上來這件事不在它的模型裡。

```
  clearance 120  撞山 1   最低餘裕   6 m   存活 34   ← 現況
  clearance 160  撞山 0   最低餘裕 125 m   存活 27
  clearance 200  撞山 0   最低餘裕 216 m   存活 22
  clearance 260  撞山 0   最低餘裕 373 m   存活 28
```

提高到 160 確實歸零，但那是全域 AI 常數：存活由 34 變 27，對戰矩陣、
六場機動、命令通道全部要重錄。**專案負責人 2026-08-28 裁定不付那個代價，
判準改成有物理意義的那一個：**

```
  一、安全層必須正在接管           抓「地形感知根本沒觸發」
  二、餘裕撐不到 RECOVERY_SECONDS  抓「AI 慢慢飄進山裡」
```

`RECOVERY_SECONDS = 2` 是推導的：P-51D 在 400 km/h 拉 5 G 的轉彎半徑是
256 m，把航跡由 −40° 拉平要走 179 m 弧長 —— 111 m/s 下是 1.6 秒。
**餘裕撐不到一次拉平，那就是來不及。** 門檻因此是 120 / 2 = 60 m/s，
而實測那一次是 124 m/s，兩倍餘裕。

與上一輪「仍在鎖存中的組別，高度必須高於進場高度」是同一手：
**不把觀測值抄成門檻，換一個說得出理由的判準。**

### 8.3 其餘新測試（每一條先驗紅）

```
  archipelago   交會區兩側各有一座 peak >= 800 的山，而且真的分在兩側
  archipelago   兩座錨島之間留得下一條通道（>= CHANNEL_MIN）
  archipelago   島數仍然是 48（錨島取代，不是追加）
  skirmish      DEFAULT_SKIRMISH 的兩個新欄位等於現況
  skirmish      三個高度都接得到 BattleConfig
  skirmish      甲板那一格低於島頂 —— 山才擋得住路
  skirmish      不合法的高度退回預設，不是 NaN
  skirmish      地形不進 BattleConfig
  skirmish-roster.e2e  兩列按鈕在、預設對、點了會變、開場高度真的接上
```

### 8.4 不得退步

```
  rematch            replayDigest 逐位元不變
  perf-gate          6/6
  全套               3,007 條（新增的除外）全綠
  ai-command-tactics 8108 / 14319 / 0.566
```

**`replayDigest` 不變是一條窄的保證。** `DEFAULT_BATTLE` 與 headless 的
`battleConfigFrom` 都不帶地形，而 digest 本身也不含地形狀態。它證明的只是
「沒有地形時舊模擬沒變」—— **它抓不到錨島改了地圖、也抓不到任何接線問題**。
不要把它當成這一輪的證明。

## 9. 事前約定的否決條件

- 甲板群島跑不出「被地形接管過 > 0」→ **改錨島位置或尺寸，不改門檻**
- 交會前的介入率高於交會後 → 錨島壓在進場航跡上，換位置
  （實測交會前 0.00%，這一條沒有觸發）
- `replayDigest` 變了 → 有東西漏進了不該有地形的路徑，回頭修，不重錄基準
- 甲板關卡出現撞山 → **觸發了**。見 §8.2：判準由「零撞山」改成
  「只能是來不及的那一種」，專案負責人裁定

## 10. 明確不做

- **AI 的路徑層** —— 見 §1。等這一輪讓它有分母之後再回頭
- **AI 的地形戰術層** —— 依賴路徑層
- **`BattleConfig.terrain`** —— 見 §3。架構整理，不是這一輪
- **出生帶淨空** —— 見 §6.4
- **任務卡選地形／高度** —— 任務有自己的劇本
- **大島海岸線與內陸地形** —— `TerrainKind` 長得到，這一輪不生成
- **島的 LOD** —— 已量到佔 p50 的 25.1%，值得做，不是這一輪
- **搬戰場** —— 見 §6.1
- **玩家自訂錨島／地形種子** —— 沒有需求的擴充點

## 11. 全域限制

- `src/ai/` 熱路徑不得配置、不得 `Math.random`
- 註解寫現狀，不寫沿革
- 不寫飛機外形的測試
- 每一條新測試先驗紅，或以變異證明承重
