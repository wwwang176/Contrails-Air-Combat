# 轟炸機自衛砲塔

**日期**：2026-08-20
**分支**：`feat/bomber-turrets`

## 1. 為什麼

`src/weapons/he111.ts` 與 `src/weapons/b17g.ts` 的檔頭寫著同一句話：

> 自衛砲塔要等 `Mount` 長出射界與旋轉之後才做 —— 現有的 `mountDirection`
> 是純幾何、所有掛架同向，表達不了「這一挺朝後」。

後果是**尾追一台 B-17 完全安全**。轟炸機現在只有朝正前方的武裝（B-17G 下巴
兩挺、He 111 機首一挺），戰鬥機從任何其他方向進來都不會被還擊。

同一份檔頭也點出了做這件事的核心難題：

> 沒有散佈的模型裡，一挺零延遲的機槍是必殺的。轟炸機的壓力必須來自
> 「你不能久留」而不是「你進來就死」。

十二根完美瞄準、零延遲的 .50 裝上 B-17，任何進到射程的戰鬥機會瞬間蒸發。
所以砲手一定要有「不準」的來源 —— 這份 spec 的 §6 就是在解這件事。

## 2. 範圍

**做**：
- `Turret` 這個新概念（射界錐、旋轉速率、搖晃），以及推進它的 `world/turrets.ts`
- B-17G 八道彈流、He 111 五道彈流的配置
- 砲塔的槍焰與**黑色三角柱槍管**（跟著砲塔轉）
- 兩台轟炸機的 `Battery.mounts` 清空 —— 它們史實上沒有任何固定前射武器

**不做**（各有理由，不是遺漏）：
- **玩家操作砲塔**。切到砲手位要動輸入層、相機、HUD 與代飛邏輯，那是另一份
  完整的 spec。這一輪砲塔一律由 AI 操作，不管載機是 AI 飛的還是玩家飛的。
- **AI 轟炸機的行為**。見 §8 的已知後果。
- **砲塔本體的外形**（球罩、風擋、砲手）。那是外型的事，跟 `docs/backlog.md`
  §2.15 一起走。
- **彈藥量、過熱、砲塔被打壞、砲手傷亡**。都可以之後加。
- **不規則射界**。見 §5 的理由。

## 3. 架構

### 3.1 為什麼 `Turret` 是新概念而不是擴充 `Mount`

`Battery` 是**玩家扣扳機時發射的東西**，由 `c.command.firing` 驅動。砲塔不是
—— 它自己找目標、自己決定開火。兩者的驅動來源不同。

另外三個具體的阻礙：

1. **`MAX_MOUNTS = 8`。** B-17G 一共八座砲塔、十二根槍管，塞不進去。
   `weapons/types.ts` 的註解明寫：「某天有人加一台九挺槍的飛機，第九挺會
   **靜靜地畫不出來** —— 沒有錯誤、沒有警告，只是那一管永遠不閃。」
2. **`mountDirection` 是純函數**（位置 → 方向）。砲塔有指向**狀態**，那個
   狀態要跨步保存。
3. **槍焰的 `InstancedMesh` 用「架數 × MAX_MOUNTS」預配。** 把砲塔塞進
   `mounts` 就要把 8 提到 16，等於整個槍焰池翻倍，而其中一半永遠是空的
   （戰鬥機沒有砲塔）。

把驅動來源不同的東西合在一條路上，第一個要加的就是分流旗標。

## 4. `Turret` 的資料形狀

```ts
export interface Turret {
  id: string
  weapon: WeaponSpec
  /** 槍口位置，機體座標，m */
  position: Vector3
  /** 射界錐的中心方向，機體座標單位向量 */
  axis: Vector3
  /** 射界半角，rad */
  halfAngle: number
  /** 旋轉速率上限，rad/s */
  rotationRate: number
  /** 幾管。雙聯砲塔填 2 —— 見下方 */
  guns: number
}
```

放在 `AircraftSpec.turrets`。**戰鬥機是空陣列**，不是選填 —— 必填欄位在加
新機種時會由型別擋下來，選填不會（`role` 那一輪的同一個理由）。

### `guns` 乘的是傷害，不是射速

雙聯砲塔照實模擬要吐兩倍彈丸，而彈丸池只有 4,000 格（§7）。乘傷害的話 DPS
一樣、彈流看起來是一道而不是兩道 —— 1,000 m 外分不出來，但省一半的池子。

**這是被預算逼出來的簡化，不是物理。** 註解要寫明，日後有人擴容池子時才知道
這裡可以改回去。

## 5. 射界是「錐」不是多邊形

真機的射界是不規則的：腰部機槍被機身擋、球形砲塔打不到正上方、尾砲塔的上下
界不對稱。但**照片讀不出精確邊界**，而這個專案已經為「從照片讀來的前提」付過
一整輪的代價（`.claude/skills/aircraft-from-reference` 坑 22：一個錯的前提讓
六次修正每一次都合理、每一次都不對）。

一個中心方向 + 一個半角足以做出「從哪個角度進來比較安全」，而且它是**可以被
試飛推翻的形式** —— 不規則多邊形不是。

**半角是設計值不是量測值**，spec 檔的註解要這樣寫。

## 6. 搖晃：砲手為什麼打不中

**專案負責人的裁定**：AI 砲手一律瞄準預瞄點（最佳解），但射出去的子彈方向帶
一個隨時間擺動的小偏移，看起來像搖晃掃射。

射出去的方向 = 預瞄方向繞兩個與它垂直的軸各轉一個小角：

```
  θ₁ = A · sin(ω·t + φ)          繞 e₁ 轉
  θ₂ = A · sin(ω·t·Φ + φ)        繞 e₂ 轉，Φ = 1.6180339887（黃金比）
```

`e₁`、`e₂` 是與 `aim` 垂直的一組正交基底，**必須由 `aim` 唯一決定**（否則
「確定性」是假的）：`e₁ = normalize(aim × u)`、`e₂ = aim × e₁`，其中 `u` 取
機體上方 `(0, 1, 0)`；`aim` 與 `u` 幾乎平行時（`|aim·u| > 0.99`，例如正上方
的 Sperry 砲塔）改取 `(0, 0, −1)`。這個切換門檻要寫成常數並被測試涵蓋 ——
砲塔正好指向正上方時基底若翻轉，彈流會瞬間跳一下。

**為什麼是兩個而且頻率比是無理數**：單一正弦是一條來回掃的直線，目標只要離開
那條線就永遠打不到。兩個頻率不整除的正弦疊起來是**李薩茹圖形** —— 不重複、
會把整個錐面掃滿，但每一瞬間仍然是連續平滑的移動。

**為什麼不用亂數散佈**：這一輪要寫一支真正逐位元比對的重播測試（見 §11.5
—— 既有的 `rematch.test.ts` **並沒有**做那件事）。確定性的搖晃不必處理亂數
種子；而且玩家看得見那道掃過來的彈流因此**學得到「別停在那裡」** —— 隨機
散佈學不到，只能碰運氣。

### 相位

```
  φ = (載機的 combatant 索引 × 該機砲塔數 + 砲塔索引) × 黃金角(2.39996 rad)
```

黃金角讓相位在 [0, 2π) 上散得最開。同一架 B-17 的八道彈流不會同步擺動（那看
起來像機械故障），編隊裡相鄰兩架也不會一模一樣。**零亂數。**

### 兩個要調的數字

| | 起始值 | 怎麼來的 |
| --- | --- | --- |
| 振幅 `A` | 1.0° | 400 m 處 1° ≈ 7 m，戰鬥機翼展約 11 m。掃幅 ±7 m 表示「定點不動會被掃到，動起來就掃不到」 |
| 頻率 `ω` | 2π × 0.7 Hz | 週期 1.4 秒。快到看得出在掃，慢到「這一下掃過去了」是一個可以反應的事件 |

**兩個都是起始值，由試飛裁定**（護欄重新定值是專案負責人的決定）。

### 搖晃只作用在砲塔

`M2_BROWNING` 是 P-51D 六挺翼槍與 B-17 下巴砲塔**共用的同一支 `WeaponSpec`**。
把搖晃加在 `WeaponSpec` 上會滲進玩家的翼槍，而那是已經調好的手感。所以搖晃的參數是 `world/turrets.ts` 的**模組常數**，不放在 `WeaponSpec` 上。
真正要守的是「不滲進玩家的六挺翼槍」，模組常數同樣滿足；讓每一座砲塔各自
可調是 YAGNI —— 十三座砲塔各兩個旋鈕，而目前沒有任何一座需要與別座不同。

## 7. 每步流程與彈丸預算

### 7.1 流程

`world/turrets.ts` 在 `World.step` 裡、`fire()` **之後**、`resolveHits()`
**之前**推進。兩者都往同一個 `Projectiles` 池寫，**順序固定才可重現**
（`rematch.test.ts` 需要）。

每個砲塔每步：

1. **選目標**：敵隊、存活、`interceptTime` 有解且 `t ≤ PROJECTILE_LIFETIME`、
   預瞄點落在射界錐內。多個候選取**離槍口**最近的。搜尋一律受
   `searchCooldown` 節流，**與現在有沒有目標無關** —— 「找不到目標」才是最常
   見的狀態（開局全部在遠處），若「沒目標就每步重掃」等於完全沒有節流。
2. **轉向**：`aim` 往預瞄方向轉，每步最多 `rotationRate · dt`。
   **這是「不能久留」的來源** —— 高速掠過的戰鬥機角速度超過砲塔轉速，砲塔
   就永遠落後。
3. **開火**：`aim` 與預瞄方向的夾角小於門檻才扣扳機，走同一支 `stepCadence`。
4. **搖晃**：§6。
5. **生彈丸**：同一個 `Projectiles.spawn`，`owner` 填載機的 combatant 索引。
   自傷與友軍誤傷因此自動排除（`World.ts:453` 已經跳過同隊）。

`interceptTime` 與 `solveLead` 直接用 `src/world/lead.ts` 現有的閉式解。
**「有解且 t ≤ 彈丸壽命」正好就是 HUD 預瞄環的顯示條件** —— 射程判定不必
另外訂一個數字。

`TurretState`：

```ts
interface TurretState {
  aim: Vector3            // 目前指向，機體座標；初始 = spec 的 axis
  phase: number           // 搖晃相位，見 §6
  targetIndex: number     // −1 = 沒有目標
  searchCooldown: number  // 距離下一次重新搜尋還有幾秒
  burstFiring: boolean    // 點放：現在是開火段還是停火段
  burstTimer: number      // 點放：這一段還剩幾秒，恆為正
  flash: number           // 槍焰剩餘秒數
  lastBarrel: number      // 上一發從哪一根管口出（雙聯輪替，見 §10）
}
```

射速時鐘**不在這裡** —— 它是 `Combatant.turretCooldowns: Float32Array`，
直接餵給既有的 `stepCadence`。放在 state 裡要每步搬進搬出一個一格陣列，
而那個轉接在「沒有目標」與「預瞄失敗」兩條分支上都會漏掉寫回。

**熱路徑零配置**（spec §10 的既有紀律）：`TurretState` 在 `setSpec` 時配好，
每步只寫入既有的 `Vector3`，模組私有的暫存向量沿用 `World.ts` 的 `S.v` 做法。

### 7.2 彈丸預算

`PROJECTILE_CAPACITY = 4000`、`PROJECTILE_LIFETIME = 1.2`。環狀緩衝滿了會
**覆寫最舊的** —— 子彈在半空中消失，而且不會有任何錯誤。

三件事一起收：

1. **雙聯算一道彈流**（§4 的 `guns` 乘傷害）
2. **射程門檻** `t ≤ PROJECTILE_LIFETIME`（本來就是流程的一部分）
3. **點放**：打 `burstOn` 秒、停 `burstOff` 秒，起始值 **1.2 / 0.8**。真機砲手
   因槍管過熱與彈藥限制本來就是點放，而且這讓搖晃**讀得出來** —— 連續彈幕看
   不出掃描，一梭一梭才看得到。

最壞情況（全部有目標、全部在射程內）：

```
  B-17G  8 道 × 800 rpm × 0.6 責任週期 = 64 發/秒 → ×20 架 = 1,280 → 存活 1,536
  P-51D  6 挺 × 800 rpm                = 80 發/秒 → ×20 架 = 1,600 → 存活 1,920
                                                        合計 3,456 < 4,000  ✓
```

**上面那一段是算的。實測結果如下**（`test/tools/projectile-peak.probe.ts`，
20v20、300 秒、同一顆種子）：

```
  對手              峰值    平均   佔容量
  Bf 109 G-6         486      51    12.2%
  B-17G（160 座砲塔） 981      48    24.5%
```

**實測峰值只有算出來的 981 / 3,456 = 28%**，容量綽綽有餘。差距的成因是
「全部有目標、全部在射程內」這個最壞情況在一場真的戰鬥裡幾乎不出現 ——
20 架 B-17 的 160 座砲塔裡，同一瞬間有解又在射界內的通常只有十幾座。

**平均值幾乎不變**（51 → 48）而峰值翻倍，這也說明砲塔的彈流是**尖峰型**
的：點放讓它成梭出現。用平均值判斷池子夠不夠會嚴重低估。

量法有一個坑：在 `stepBattle` 回來之後讀 `live` 會低估，因為一步之內是
生成 → 推進／過期 → 命中／回收，讀到的是回收後的殘量。所以
`Projectiles` 加了 `peakLive`，在 `spawn()` 裡更新。

## 8. 兩台轟炸機沒有前射武器

**史實**：

- **He 111 的機首 MG 15** 是球形槍座（Kugellafette）上的**手持活動槍**，由
  機首的投彈手操作。H-6 後期換成 20 mm MG FF。
- **B-17G 的下巴砲塔**是 Bendix Model D **動力砲塔**，由機首的投彈手**遙控
  瞄準**。

兩者都不是駕駛員能扣的槍。現在把它們做成 `Battery`（`c.command.firing` 驅動）
在史實上是錯的。**專案負責人裁定：可以轉向的都交給 AI，玩家不控火砲。**

於是兩台的 `Battery.mounts` 清空，兩挺槍都變成 `Turret`。

**已驗證不會弄壞任何東西**：`hitbox.test.ts` 是逐掛架迴圈（0 個就是不跑）、
`weapons.test.ts` 的 DPS 比較只涉及兩台戰鬥機、`MAX_MOUNTS` 掃描 0 個自然通過、
`World.setSpec` 配 0 長度的 `Float32Array` 沒有問題。

### 保留 `Battery.sight`

`ai/assess.ts`（兩處）與 `ai/steer.ts`（兩處）在讀 `battery.sight.muzzleVelocity`
算預瞄，而**這一輪不碰 AI**（負責人裁定）。所以 `sight` 保留，但它對轟炸機
已經沒有物理意義，註解要寫明是「為了讓 AI 這一輪不必改動而留的欄位」。

### 已知後果，刻意留到下一輪

`src/ai/` 裡沒有任何一處讀 `role` 或分辨轟炸機。清空 `Battery` 之後，**AI 轟炸機
會繼續把機首指向敵人、繼續扣扳機、繼續射不出東西**。

這由負責人裁定留到下一輪，會寫進 `docs/backlog.md` §2.21 而不是藏起來。

### HUD

`main.ts:1007` 的預瞄環改判準為 `mounts.length > 0`。轟炸機駕駛員沒有瞄準具
—— 這是對的，而且它是 HUD 不是 AI。

## 10. 視覺

**槍管**：黑色三角柱（3 側面 6 三角形 + 2 端蓋 = **8 三角形/根**）。
B-17G 十二根 ≈ 96、He 111 五根 ≈ 40。

**雙聯砲塔的兩根管口輪流出彈**（`TurretState.lastBarrel`）。`guns` 乘的是
傷害所以只有一道彈流，若彈丸固定從中心生，畫面上就會看到彈流從兩根管子
**中間**冒出來。輪替之後每一發都從某一根真的管口出來，DPS 不變。槍焰也跟著
同一根走。

**槍管跟著砲塔轉**，用 `InstancedMesh`：跟槍焰走同一條更新路徑
（`render/muzzle.ts` 已經是 InstancedMesh、每幀寫入每個實例的變換），砲塔的
`aim` 直接餵進去。實例容量是 40 架 × `MAX_TURRETS`(8) × 每座最多 2 根 = 640，對 InstancedMesh 是零壓力，
而且**不新增任何場景節點**。

靜態槍管（烘進機身）被否決：砲塔一轉，彈流就會從槍管**旁邊**飛出去，而砲塔的
重點就是它會轉 —— 這個穿幫每一次射擊都看得到。

**砲塔的槍焰**另有一個實例池，不動 `MAX_MOUNTS`。

**不做**：砲塔本體的外形（球罩、風擋、砲手）。留在 backlog §2.15 跟外型一起走。

## 11. 測試

### 11.1 純函數（`test/unit/turret.test.ts`）

- **射界錐**：錐內、錐外、剛好在邊界
- **轉向**：一步的轉角不超過 `rotationRate · dt`；目標在錐外時不開火
- **搖晃**：確定性（同一個 `t` 與索引必然給同一個角度）、有界
  （`|偏移| ≤ A√2`）、兩個頻率不整除所以 N 個週期內不重複
- **相位**：同一架的各座互不相同

### 11.2 跨模組一致性（**新檔** `test/unit/turret-mount.test.ts`）

**不要擴大 `hitbox.test.ts` 的 `CASES`** —— 那會讓整套**外形**斷言（頂點數、
命中盒幾何）開始跑兩台轟炸機，違反「不為飛機外形寫測試」的既有裁決。

- `axis` 是單位向量
- **這挺槍接在飛機上**：從槍口沿 −axis 回走 `TURRET_MOUNT_REACH`，必須碰到
  某個命中盒。判準是 `segmentBox(...) !== NO_HIT` —— 起點在盒內時它回傳
  **`0`** 而不是 `NO_HIT`，用 `> 0` 判斷會讓下巴砲塔與機首槍必假紅
- **方向語意**：機首朝前的砲塔 `axis.z < 0`、尾部朝後的 `axis.z > 0`、
  左右舷的 `axis.x` 各自有正確的符號。這一條抓的是「正負號打反」，而上一條
  抓不到（槍口本來就在盒內時，正反兩個方向都回傳 `0`）
- 砲塔數與槍管數

**刻意不做「射界錐不指向自己的機身」。** 專案負責人 2026-08-20 裁定：同隊
已被 `World.ts:453` 跳過，那些彈丸不造成任何傷害；剩下的成本（曳光彈穿出
自己機身的視覺穿模）改成**目視驗收**。用測試綁住一個接近史實的半角
（80° 對球形砲塔）會逼出「為了配合測試去改飛機」。

**`TURRET_MOUNT_REACH` 為什麼比 `BARREL_LENGTH` 長**：命中盒是**簡化的傷害
體積，比實際機體小**。B-17G 的機身外殼到 z = 16.25，而 `tail` 命中盒只到
15.30 —— 差將近 1 m。回走的距離必須吸收這個差，否則尾砲塔必然判成「沒接在
飛機上」。

### 11.3 整合驗收（`test/integration/turrets.test.ts`）

20 架 P-51D 對 20 架 B-17G、300 秒：

- **主判準是 A/B 對照**：同一場關掉砲塔再跑一次，比較 P-51 的存活率。這才是
  「砲塔有沒有用」，單看絕對數字看不出來
- 彈丸池峰值存活數 **< 90% 容量**（實測 981 / 4,000 = 24.5%，見 §7.2）
- **兩個方向都要成立**：B-17 的擊落數 > 0（砲塔真的打得到），P-51 仍然打得下
  B-17（砲塔不是無敵的）

### 11.4 不寫

砲塔外形的測試。照專案的既有裁決（skill「不要為外型寫測試」）。

### 11.5 護欄

`perf-gate` 必須保持綠。砲塔推進是新的熱路徑，零配置的紀律同樣適用。

**現有的 `test/integration/rematch.test.ts` 沒有做任何逐位元比對** —— 它測的
是「改設定重開、戰績清空、十場的效能」。所以「跑它」不能證明確定性。這一輪
另外寫 `test/integration/turret-replay.test.ts` 做真正的比對（比較底層的
`Uint8Array`；`!==` 對 ±0 與 NaN 都與逐位元相反）。

**刻意不測「`resetBattle` 之後與全新一場相同」**：`resetBattle` 保留 AI 控制器
的目標、決策計時與規則閂鎖，實測「跑 20 秒 → reset → 再跑 20 秒」與全新一場的
最大位置差 **508.939 m**。那是既有缺陷（`src/main.ts:389` 的註解宣稱「已經與
新建一場等價」是錯的），記進 `docs/backlog.md` §2.22。
