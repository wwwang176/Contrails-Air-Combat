# 脫離之後回得來 —— `extend` 的出場條件與回場方向

**狀態**：待專案負責人審。實作尚未開始。

**前置**：本文與 `2026-08-22-energy-tactics-design.md`（AI 的主動能量經營）
是**兩件事**。那一份加的是戰術層（`quota` 預設 0，尚未上線）；這一份修的是
**意圖層既有的 `extend`**，與戰術層開不開無關。

**修訂**：2026-08-23 大幅改寫。第一版有三個阻擋級缺陷 —— 傾斜角上限在
`aimWorld` 介面下表達不出來、主判準量錯東西、出場條件破壞了閂鎖語意。
三者都由 Codex 審查指出、由實測確認。舊版的 `extendBankMax`、
`extendRecoverHold` 兩個參數整個作廢，理由見 §3 與 §5。改了什麼見 §12。

## 1. 人工回報

> 「當我觸發 extend 能量時，飛機會以目前方位向前飛，通常你向前飛，等於是
> 遠離戰場了，結果等到能量補完要回頭根本追不上（轟炸機已被打或是戰場已
> 轉移）。」

同一次驗收另外回報：`extend` 的理由**九成是「能量」**，偶爾是「能量＋見底」。

專案負責人接著指出方向：把出場條件「從『比敵人強』改成『我自己回到能打的
狀態』」，並且「飛行的方位朝向敵人，但不可以大幅度轉彎以免又減少速度」。
本文的 §4 與 §5 分別落實這兩句話。

## 2. 程式現況

以下每一條都逐行查證過。標「**修正**」的是本文第一版寫錯、由 Codex 指出的。

### 2.1 `extend` 沒有「往哪裡退」這個概念

`steer.ts` 的 `extend` 分支只呼叫 `unloadAim(self, extendPitchAngle(…), out)`。

**修正**：`unloadAim` 維持的是**速度向量的水平航向**，不是機頭方位（機首
只在水平投影退化時才用）。結論不變 —— 水平方向完全不參與決策，這條路徑
回答的是「要不要退」與「退得多陡」，從來沒有回答「退到哪裡去」。

### 2.2 出場條件對劣勢方不可達

```
extendEnergyLatch   energyAdvantage < energyEnter (−300 m) 觸發
                    energyAdvantage > energyExit  (+100 m) 才解除
```

**進場與出場都是相對的。** 而會觸發脫離的定義上就是劣勢的一方 —— 要「比對手
多 100 公尺比能量」才准回頭，這個條件在整場戰鬥中都達不到（對手也在休息）。
實測玩家座位代飛時，能量閂鎖曾連續開著 46 秒、166 秒不曾關過。

**修正**：閂鎖開著**不等於**意圖是 `extend`。`arbitrate` 的相對路徑還要求
`range < extendRange`（1,500 m）且沒有射擊解：

```ts
if (s.extendFloorLatch && sit.energyAdvantage < cfg.floorExempt) return 'extend'
if (!shooting && (s.extendEnergyLatch || s.extendTurnLatch)
    && sit.range < cfg.extendRange) return 'extend'
```

所以「閂鎖開 166 秒」是閂鎖的持續時間，不是 `extend` 的持續時間。真正的
`extend` 段落長度要另外量（§8.4）。這不改變結論 —— 閂鎖開著就隨時可能再
掉回 `extend`，而每一次都沒有方向 —— 但本文不得再用那兩個數字當作
「AI 直飛了 166 秒」的證據。

### 2.3 `ai-withdraw-anchor` 是紅的，但它量的不是這件事

`test/integration/ai-withdraw-anchor.test.ts`「撤退令不得把戰鬥推出戰場」，
在本分支的起點（`af8f976`）就已經是紅的。實跑 HEAD：

```
maxRadius       11110.26   >  6500      ← 先炸在這裡
leavingShare       2.39%   <  5%        ← 第二條，也是紅的
```

**修正**：第一版把它當主判準是錯的，三個理由：

1. **它的根因註解逐字指向指揮層的 `planFlightOrder` rally 撤退令**（集合點
   相對當前位置反覆外移，一個沒有不動點的積分器）。受 rally 命令的飛機
   intent 被 `AiController` 覆寫成 `rally`，**根本不走本文的 `extend` 分支**。
2. 它綁死 `DEFAULT_BATTLE` —— 20v20 對頭遭遇戰，沒有 `transit` 單位，因此
   `protectedMask` 全 0。§5.3 最主要的「回到轟炸機」那條路它一次都驗不到。
3. `leavingShare` 那條數的是 rally 命令的佔時，修 `extend` 完全不會動到它。

所以「它變綠就是本文成立」在目前基準上不成立。它降為**全域護欄**（不得比
現況更糟），主判準另立，見 §8。

### 2.4 這個量對設定極度敏感，不要拿它比大小

玩家座位代飛、只把初速擾動 ±0.5%，`extend` 佔時：

```
axis-escort   bf109g6    6.2%   29.1%   11.8%   36.4%   27.6%
allies-escort p51d      43.6%   27.0%   72.8%   17.0%   16.9%
```

兩張卡的範圍完全重疊。**「哪一張卡比較嚴重」這個問題，目前的方法答不了。**
任何逐卡的結論都要有五次以上的微擾才算數。

### 2.5 指揮儀的介面限制（這一節決定了 §5 能怎麼寫）

控制鏈只有一個世界方向：

```
steerCommand → aimWorld → FlightDirector → roll/pitch/yaw rate → 舵面
```

`FlightDirector` 把方向誤差解成 `rollCommand = atan2(aimBody.x, aimBody.y)`
—— 那是**機動平面**（要往哪一側繞），不是傾斜角。傾斜角是它解出來的結果，
**下不了指令**。

兩個會咬人的特例：

```
errorAngle < deadZoneAngle (1.5°)                完全不下滾轉指令
errorAngle > π − reverseHysteresis (175°)        沿用上一格滾轉指令
```

後者是「目標在正後方」的奇異點 —— 而**戰場在正後方正是 `extend` 回場的
常態**。

## 3. 實測

三支新探針，都在 `test/tools/`。

### 3.1 `turn-cost.probe.ts` —— 判準選錯的那一次

第一版想用「誘導阻力 ∝ n²、n = 1/cos φ」反推一個傾斜角上限（15° → +7%
阻力）。這支去量它，結果**否決了整個做法**，但它自己的判準也是錯的。

**它問對的兩件事：**

- 「每個決策拍偏離當前航向 Δψ」控制不了轉彎率。指令 80°/s、實測 1.9°/s、
  坡度 0.4°。`deadZoneAngle` 加上方向舵通道會把小橫向誤差直接抹平成平飛
  側滑。
- 這個介面**沒有緩轉檔位**。叫它轉 45° 給 69° 坡度、轉 90° 給 85°，連只轉
  15° 都給 16~37° 坡度。`extendBankMax` 想限制的那個東西根本不存在。

**它問錯的一件事：** 它量比能量 `h + V²/2g`，把高度與速度加在一起。
「轉 180° 只花 179 m」看起來很便宜 —— 而同一列高度 **+205 m**、
`cornerRatio` 由 1.00 掉到 **0.826**。比能量守住了，速度沒有。
專案負責人指出「要爬升又快速大轉彎，速度不是會被消耗太多嗎」，正是這件事。

它也漏了 `extend` 在低速時 `extendPitchAngle` 是**負的**（低頭換速度）——
拿水平轉彎的數字代替俯衝中的轉彎不成立。

### 3.2 `extend-return.probe.ts` —— 判準換成速度與高度

照抄 `steerCommand` 的 `extend` 那條路徑（`unloadAim` → `shrinkTowardNose`
→ `applyFloor`），只換航向。錨點在原點、飛機朝反方向離場、起始
`cornerRatio = 0.75`（`extend` 觸發的狀態），跑 60 秒。

`bias` = 每個決策拍把航向往錨點方位拉過去的比例。

**Bf 109 G-6 @ 4,000 m**

| bias | 離錨點 20s / 60s | cornerRatio 20s / 60s | 坡度中位／峰值 | 高度變化 |
|---|---|---|---|---|
| 0（現況） | 507 / 311 m | 1.22 / 1.70 | 62° / **178°** | **−3,435 m** |
| 0.10 | 871 / 860 m | 1.03 / 1.07 | 50° / 112° | **+524 m** |
| **0.25** | **237 / 183 m** | **0.96 / 0.94** | **77° / 100°** | **−717 m** |
| 0.50 | 204 / 217 m | 0.99 / 0.97 | 76° / 102° | −1,112 m |
| 1.00 | 218 / 627 m | 1.11 / 1.57 | 64° / **180°** | **−3,834 m** |

P-51D 與 1,200 m 低空三組同樣的形狀。四組共同的結論：

**甲、轉彎不吃速度，吃高度。** `cornerRatio` 在所有 `bias` 下維持 0.91~1.13
—— `extendPitchAngle` 是閉迴路，速度一掉就把機頭壓下去換回來，代價自動
轉嫁到高度。高度代價隨 `bias` 單調上升：60 秒內 0.10 是 +524 m、0.25 是
−717 m、0.50 是 −1,112 m。

**乙、兩端都會滾成倒飛。** `bias = 0`（補滿之後整個轉回去，就是現況）與
`bias = 1.0`（立刻全轉）的坡度峰值 173~180°、高度掉 3.4~3.9 km；4,000 m
那兩組直接摔到 50 m 以下。中間值 0.1~0.5 的峰值都 ≤ 118°。這就是 §2.5 的
奇異點，現在有數字。

**丙、0.25 是甜蜜點。** 離錨點穩定在 130~250 m、`cornerRatio` 0.94~1.01、
坡度峰值 ≤ 104°。往下（0.10）留不住人，往上（0.50）高度代價加倍卻沒有更
靠近。

**這張表的邊界條件要說清楚**：錨點固定不動，飛機等於繞著它盤旋 60 秒 ——
這是**最壞情況**。真實情況錨點會移動、`extend` 也會結束，高度代價會比表上小。
所以 0.25 是**起始值**，不是定值。

### 3.3 `alarm` 的分布

`alarm-dist.probe.ts`，兩張護送卡各 300 秒。結果與它怎麼定出
`extendAlarmFull` 見 §6.3 —— 放在那裡是因為它只服務那一個參數。

一句話的結論：**全體 p95 在兩張卡上都是 0.000**，「有人瞄我」只佔 0.3~4.5%
的取樣。§6 的抑制絕大多數時候不作用。

### 3.4 補速度只要 3~5 秒

同一支探針的第一版量到：`cornerRatio` 由 0.75 補到 0.95 只要 **3~5 秒**，
而且只跑了 400 m。這個數字是 §4 的直接依據 —— 速度早就補完了，`extend`
還在繼續，因為它的解除條件不是速度。

## 4. 改動一：把「能量劣勢」與「我回到能打的狀態」拆成兩個閂鎖

### 4.1 做什麼

**不動 `extendEnergyLatch`。** 它現在的語意就是「我比他弱」，一個純相對量，
一直都是對的。

**新增 `extendRecoveredLatch`** —— 一個只吃 `cornerRatio` 的絕對閂鎖：

```
進場（回到能打的狀態）   cornerRatio > recoverEnter (0.95)
出場（又飛不動了）       cornerRatio < recoverExit  (0.85)
```

仲裁時把「因能量而脫離」改成兩者的合取：

```
   舊    !shooting && (extendEnergyLatch || extendTurnLatch) && range < extendRange
   新    !shooting && ((extendEnergyLatch && !extendRecoveredLatch)
                       || extendTurnLatch) && range < extendRange
```

### 4.2 為什麼是兩個閂鎖，不是給同一個閂鎖第二條解除路徑

第一版寫的是「`extendEnergyLatch` 的解除多一條 `cornerRatio > recoverRatio`」。
那會產生：

```
energyAdvantage   = −800     明確仍在能量劣勢
cornerRatio       = 1.05     速度足夠
extendEnergyLatch = false    ← 欄位在說謊
```

HUD 的 `extendReason` 與 `extend-trigger.probe.ts` 都直接把這個布林讀成
「能量」。它不再是能量閂鎖，而是一個混了 readiness 的小型狀態機。

**專案的既有規矩是「一個閂鎖只維護一種事實」。** 拆成兩個之後每個欄位都
誠實，HUD 與探針一個字都不用改語意，判讀也留在 `rules.ts` 裡。

【更新順序要釘住】`stepRules` 是先更新所有閂鎖再仲裁。同一拍若
`energyAdvantage < −300` 且 `cornerRatio > 0.95`，兩個閂鎖都會成立，
合取為 false —— **不進 `extend`**，不會產生一拍脈衝。這是刻意的：
「我比他弱但我飛得動」本來就該去打。

### 4.3 為什麼不需要再進入冷卻

第一版配了一個 8 秒的 `extendRecoverHold`，理由是「用絕對條件解除之後
`energyAdvantage` 仍然低於 −300，下一拍就重新閂上，變成 10 Hz 抖動」。

**兩個閂鎖的寫法讓那個問題消失**：`extendRecoveredLatch` 自己就帶遲滯
（0.95 進 / 0.85 出），速度要真的掉回 0.85 才會讓「因能量脫離」重新成立。
抖動由遲滯擋住，不需要一段盲時間。

而那個冷卻本身有害：期間 `energyEnter` 被硬忽略，態勢真的惡化（還沒到
`defend`、turn/floor 兩個閂鎖也還沒成立）時，AI 是聾的。

### 4.4 `recoverEnter` 為什麼與 `cornerExit` 同值，`recoverExit` 為什麼是新的

`recoverEnter = 0.95 = cornerExit` —— 「我飛得動了」只該有一個定義，
與 `extendFloorLatch` 共用同一把尺。**它不是一個可獨立掃描的參數**，
直接引用 `cornerExit`；第一版讓它獨立掃描是自相矛盾（見 §12）。

`recoverExit = 0.85` 是新的、待掃描的：它訂的是「回復狀態要掉多少才算
失效」。取 `cornerEnter (0.75)` 與 `cornerExit (0.95)` 的中間，理由是它
不該比「見底」更早失效（那就變成 floor 閂鎖了），也不該一路撐到 0.95
（那等於沒有遲滯）。

### 4.5 不動的東西

`extendTurnLatch`（機體轉不贏）與 `extendFloorLatch`（我飛不動了）**一個字
不動**。前者談的是機體，補能量改變不了它；後者本來就是絕對的，而且它的
絕對路徑（`floorExempt`）也不動。

### 4.6 HUD

`extendReason` 加一列：`extendRecoveredLatch` 為真時，「能量」那一項改印
「能量（已回復）」。**理由是那時候能量閂鎖確實還開著**，但它已經不是意圖
`extend` 的成因了 —— 讓人工驗收看得到這個差別。

## 5. 改動二：補能量時把航向拉回戰場

### 5.1 做什麼

`extend` 的瞄準解，把水平航向按比例往回場方位拉：

```
here = 當下速度向量的水平航向          （與 unloadAim 同一個定義）
home = 由自身位置指向錨點的水平方位
err  = wrap(home − here)              ∈ (−π, π]
ψ    = here + err × extendHomeBias × homeAuthority
aim  = 航跡角 extendPitchAngle(…) 的方向，水平航向為 ψ
```

其後照舊套 `shrinkTowardNose(pull)` 與 `applyFloor` —— 兩者都是既有的
後處理，一個字不動。

`extendHomeBias` 起始值 **0.25**（§3.2 實測）。`homeAuthority` 是 §6 的
威脅抑制係數，0..1。

**錨點是 `null` 時整條偏置不套用** —— `ψ = here`，逐位元等於今天的行為。
（`null` 只可能來自「沒有目標也沒有存活的 protected」，那時沒有任何方向
可言，不是「權限為 0」。兩者的差別在於前者連 `home` 都算不出來。）

### 5.2 為什麼上限訂在「每拍收掉多少方位差」，而不是傾斜角

**傾斜角下不了指令**（§2.5）。第一版的 `extendBankMax = 15°` 混淆了指令
與結果，而且那個值從來不曾成立過 —— 實測坡度中位在任何 `bias` 下都是
50~80°。整個參數作廢。

「每拍收掉多少方位差」是這個介面下真正下得出的指令，而且它同時買到三件事：

1. **代價可調且已量過**（§3.2 的高度欄）。
2. **天然避開 180° 奇異點**：指令航向永遠不超過 `bias × 180° = 45°` 偏離
   當前航向，`errorAngle` 不可能接近 π。實測坡度峰值由 178~180° 掉到 ≤ 104°。
3. **收斂時自動變輕**：`err` 隨著轉過去而縮小，偏置跟著縮小 —— 一個連續、
   自限、沒有翻轉點的量。這與 `stationKeeping` 的徑向律同一個手法。

### 5.3 錨點指向誰

**指向被保護單位，不是指向當前目標。** 人工回報在意的不是「追不上那架
P-51」，是「回去的時候轟炸機沒了」。

由 `AiController` 在 10 Hz 決策節拍算出一個世界座標點，**照 `rallyPoint`
的成例當參數傳進 `steerCommand`** —— `src/ai/steer.ts` 不得 import
`TargetBoard`，那條界線一直都在。`homeAuthority`（§6）同樣由
`AiController` 算好傳進來，因為 `alarm` 只住在那裡。

選法，三條缺一不可：

1. **只算存活的。** `protectedMask` 是角色標籤，死後仍然是 1
   （`stepPressure` 明確另外檢查 `alive`，證明遮罩本身不帶存活語意）。
   全部陣亡時視同全 0。
2. **取存活者的形心，不是最近的一架。** 「最近的一架」在兩架距離接近時、
   或某一架陣亡時會瞬間換錨點；形心是連續的。這與 `stationKeeping` 用
   `orbitSide` 閂鎖避免幾何選邊翻轉是同一個顧慮，而形心根本不需要記憶。
3. **`protectedMask` 全 0（或全滅）的關卡退回當前目標的位置。** 遭遇戰、
   掃蕩沒有「戰場中心」這種東西，目標在哪裡戰場就在哪裡。這條 fallback
   的風險由 §6 承擔 —— 沒有 §6 它就是「直接衝向剛剛打不贏的那一架」。

### 5.4 位階：只在 `extend` 那一支，不做全域後處理

放在 `switch (intent)` 的 `case 'extend'` 裡。這表示 `planeDegenerate`、
`speedRecover`、`overshoot` 三個幾何模式生效時它**不生效** ——
**那是對的**，不是缺陷：那三個閘門存在的意義就是「這個幾何下一般解法會
出錯」，它們的優先序高於意圖是既有的設計決定。

放到所有分支之後會蓋過那三個安全閘門，明確不做。

### 5.5 只偏水平，不動俯仰

俯仰仍由 `extendPitchAngle` 決定，其後 `shrinkTowardNose`、`sweetPitch`、
`applyFloor` 照舊。

**修正**：第一版寫「俯仰完全由 `extendPitchAngle` 決定」，那是錯的 ——
其後那三層都會動到三維方向。本文的意思是**這一項改動不新增任何俯仰
分量**，既有的那幾層一個字不動。

## 6. 改動三：有人瞄著我的時候不飄

### 6.1 為什麼

`extend` 觸發的理由是「我比他弱」，而最常見的成因就是有人咬在後面。這種
時候把航向轉向敵人等於自己送上去。§5.3 的 fallback 更是直接把機頭轉向
剛剛打不贏的那一架。

**沒有 §6 就不該做 §5。**

### 6.2 判準用 `alarm`，不是 `threatInstant`

**修正**：第一版選 `threatInstant` 是錯的。它有一個 900 m 的**硬截止**
（`THREAT_RANGE`）——

```
追兵在 900 m 外正瞄著我   threatInstant = 0     抑制 0%，偏置全開
```

而 `alarmFactor` 的射程上限是彈丸壽命（約 1,064 m），正是為了修這個毛病
才存在的（`assess.ts` 的註解記著：700/900 m 被連續射擊 180 秒，`defend`
進入率 0.0%）。

`threatInstant` 回答的是「他現在打得中我多少」；要問的是「**有沒有人把
預瞄環套在我身上**」，那是 `alarmFactor`。而且它已經算好了 ——
`AiController.update` 每一步都算 `alarmInstant * alarmRamp(alarmSeconds)`，
就是 `defendLatch` 吃的那個量。直接用，不新增任何計算。

### 6.3 公式

```
homeAuthority = 1 − min(1, alarm / extendAlarmFull)
```

`extendAlarmFull` ∈ (0, 1]，**必須大於 0**（等於 0 會除零，實作要有斷言）。
**起始值 0.5**，兩條依據：

**幾何。** `alarmFactor` 回傳 `1 − off / ALARM_CONE`，`ALARM_CONE = 15°`。
所以 0.5 精確地等於「他的預瞄方向偏離我 **7.5°**，錐的一半」——
一個讀得懂的判準，不是一個從分位數挑出來的數字。

**實測**（`test/tools/alarm-dist.probe.ts`，兩張護送卡各 300 秒、10 Hz）：

| 卡 | alarm > 0 佔時 | 非零 p50 | 非零 p75 | 非零 p90 | 非零 max |
|---|---|---|---|---|---|
| `axis-escort` | 4.5% | 0.437 | 0.654 | 0.789 | 0.983 |
| `allies-escort` | 0.3% | 0.186 | 0.271 | 0.374 | 0.501 |

0.5 落在 `axis-escort` 非零分布的中段（約 p55），而 `allies-escort` 的最大值
恰好是 0.501 —— 在那張卡上只有最嚴重的一瞬間會完全飽和。

**「大多數時候沒有人瞄我」**：全體 p95 在兩張卡上都是 0.000。所以這個抑制
在 95% 以上的取樣裡完全不作用，§5 的偏置照常全開；它只在真的被瞄住的那
4.5%（或 0.3%）介入。這正是要的行為。

【為什麼是連續的而不是布林】門檻式的開關會在威脅邊界上讓水平指令跳變，
那正是這個專案反覆治過的病。

【`defend` 不必特別處理】真的要閃的時候意圖已經是 `defend`，不走 `extend`。
這一項擋的是「還沒到要閃、但後面確實有人」那一段。

## 7. 順序與相依

**兩次上線，不是三次。**

```
第一步   §4（兩個閂鎖）              可單獨上線、可單獨量
第二步   §5 + §6 一起，配消融旗標     三檔對照
```

**修正**：第一版排成三步、§6 單獨一步是錯的。§6 只是 §5 偏置的乘數 ——
偏置還不存在時沒有可抑制的東西，也不會改變任何行為。它單獨上線量不到
任何東西，只能落純函數與單元測試。

第二步的三檔消融（沿用戰術層那一輪的手法）：

```
偏置關                    extendHomeBias = 0        恆等基準，必須逐位元等價
偏置開、威脅抑制關        homeAuthority ≡ 1         量偏置本身的效果
兩者全開                                            出貨組態
```

**第一步不保證無風險。** 第一版寫「縮短脫離不會讓 AI 死得更快」是沒有依據
的斷言：§3.4 量到速度 3~5 秒就補滿，所以 §4 上線後「因能量脫離」的窗口會
**大幅縮短到數秒**。那是預期的行為，但「更早回頭交戰會不會死更多」必須由
§8.2 的副判準回答，不能預設。

## 8. 驗收

### 8.1 主判準：每一段 `extend` 之後回得來

**新寫一支整合測試**，跑 `axis-escort` 與 `allies-escort` 兩張卡各 300 秒。

**判準是配對比較，不是絕對距離。** 對每一段 `extend`（進場 → 出場），
記下進場當下與出場當下「己方戰鬥機到**存活** protected 形心的水平距離」，
要求：

```
出場時不比進場時更遠的段落  /  總段落數   >  0.5
段落數 > 0
```

**這個門檻沒有可調的數字。** 0.5 是「過半」，不是量出來的。

【為什麼不用絕對距離】「先量現況當基準」會退化成變更偵測器 —— 那正是
`ai-withdraw-anchor.test.ts:236` 的註解逐字警告過的事（「單次量測當門檻是
變更偵測器不是設計判準」）。而這個專案已經有現成的手法：那支測試的主判準二
就是「同一張命令的發令當下與解除當下」的配對比較，門檻 0.5。這裡沿用。

【為什麼配對比較剛好答對這一題】本文的標題就是「脫離之後回得來」。
「出場時不比進場時更遠」逐字就是那句話，不多也不少。絕對距離答的是
另一個問題（「戰鬥機該離轟炸機多近」），那是打法問題，不是本文要修的。

**下列一律只印不斷言**，供人工判讀與掃描選值：

- 到 protected 形心的距離 p50 / p90
- protected 單位的存活數與累計損傷
- 每一段 `extend` 的最大離場距離、持續秒數、**高度變化**（p50 / p90）
- **每一條出場路徑各觸發幾次**（`energyExit` / `extendRecoveredLatch` /
  `extendRange` / 射擊解）—— 這一項是 §10 但書的觀測窗，見 §8.5

【為什麼是這個場景】人工回報發生在護送關；而 `protectedMask` 只在護送／
攔截關才非零，§5.3 的主路徑在別的場景根本不會執行。

【為什麼不用單次比大小】§2.4 已經證明這個系統的量測雜訊很大。所有比較都要
五次 ±0.5% 初速微擾。

### 8.2 副判準：不得把 AI 變弱

兩步各自跑完之後都要比對（全部含五次微擾）：

- `test/integration/ai-targeting.test.ts` 的 `fireShare`
- `test/integration/ai-duel-matrix.test.ts`
- `test/integration/ai-manoeuvre.test.ts`、`ai-visible-evasion`、`ai-defence`
  —— **新增**。縮短脫離與增加轉彎最容易先傷到失速、安全層介入與破防
- `test/unit/perf-gate.test.ts`（單獨跑）
- **實測坡度峰值與坡度佔時**，不是檢查參數叫 0.25
- `extend` 期間的 `cornerRatio`、比能量、**高度**的 before/after
  —— §3.2 證明代價落在高度，只看比能量會漏掉

另外要涵蓋的情境（§5.3 與 §6 的退化案例）：

- 有 protected、`protectedMask` 全 0、protected 全滅，三種
- 追兵在 500 / 850 / 950 m，以及不在射擊錐內

### 8.3 全域護欄：`ai-withdraw-anchor` 不得更糟

它從分支起點就是紅的，而且量的是指揮層的 rally（§2.3）。**只要求不惡化**：

```
maxRadius       ≤ 11,110（現況）
leavingShare      本文不影響它，不列入
```

它變綠**不是**本文的成功條件；它變得更糟**是**本文的失敗條件。

### 8.4 逐事件的觀察

`test/tools/extend-trigger.probe.ts`（已存在）與 `extend-return.probe.ts`
（本輪新增）。第一步之後應該看到：

- 每一段 `extend` 的持續時間掉到 §3.4 的量級（數秒）
- 進入次數可以上升（退得短、退得勤是預期的）
- 進入時的距離分布不該系統性往近距離集中（那表示脫離變成了原地抖動）

第二步之後另外看：

- 坡度峰值不得出現 §3.2 乙那種 170°+ 的倒飛
- `extend` 期間的最大離場距離下降
- **高度**：§3.2 量到 60 秒最壞情況掉 717 m，實戰的數字要另外量

### 8.5 出場路徑的計量 —— §10 但書的觀測窗

§10 承認六個護欄值「值不動但作用會變」。**那句話要看得見，不能只是一句
但書。** 所以 §8.1 的測試要逐段記下 `extend` 是**被哪一條路徑結束的**：

```
energyAdvantage > energyExit          相對出場（既有）
extendRecoveredLatch 成立             絕對出場（§4 新增）
range >= extendRange                  距離出場（既有）
shotInstant > 0                       射擊解插隊（既有）
defend / rally 覆寫                   外部插隊
```

第一步前後各跑一次，比較這個分布。**它會直接回答兩個問題**：

- `energyExit` 是不是變成幾乎不觸發（§10 預期會）
- `extendRange` 在第二步之後是不是變成死碼（§10 預期會變弱）

**死碼要說出來，不要留一個已經不作用的護欄假裝它還在守著什麼。** 若某一條
掉到零，那是一個要回報給專案負責人的事實，不是一個可以默默接受的副作用。

- **不動 `energyEnter` / `energyExit` / `cornerEnter` / `cornerExit` /

  | 參數 | 值 | 作用怎麼變 |
  |---|---|---|
  | `energyExit` | +100 | `extendRecoveredLatch` 幾乎總是先成立（3~5 秒 vs 數十秒），這條相對出場路徑會**大幅減少被用到**。它仍然是唯一能讓 `extendEnergyLatch` 本身關掉的路徑 |

  | `extendRange` | 1,500 | §5 把航向拉回戰場，距離較不容易拉到 1,500 —— 這條既有的距離出口會**變弱** |

- **不碰戰術層。** `quota` 的預設值、`order-of-battle-replay` 的基準重跑，

- **不擴充 `FlightDirector` 的介面。** 要真正保證「實際坡度不超過 N°」得在

### 11.1 §8.1 的門檻 —— 改成配對比較，不訂絕對距離

「出場時不比進場時更遠」逐字就是本文的標題。絕對距離答的是另一個問題。

### 11.2 §9 三個參數 —— 不預先訂數值，訂**選值規則**

實作還沒開始，掃描結果不存在，現在訂數值等於再犯一次「拿沒量過的數字當
定值」。所以裁定的是規則：

```
每個參數掃 3~4 檔，各檔跑五次 ±0.5% 微擾
選值判準  §8.1 的配對判準通過率最高者
並列時    取較保守的那一端
```

「較保守」逐參數的方向：

| 參數 | 掃描檔位 | 較保守的方向 | 為什麼 |
|---|---|---|---|
| `extendHomeBias` | 0.10 / 0.15 / 0.25 / 0.40 | **較小** | 轉得少 = 高度代價小（§3.2 實測單調） |
| `recoverExit` | 0.80 / 0.85 / 0.90 | **較大** | 較早承認自己又飛不動了 |
| `extendAlarmFull` | 0.3 / 0.5 / 0.7 | **較小** | 抑制較強 = 被瞄住時更不會轉回去 |

**只有掃描結果與這個規則衝突時才回來問**（例如通過率最高的那一檔同時把
§8.2 的某一項打壞）。

【`extendAlarmFull` 的但書】0.5 這個起始值是用 `alarm-dist.probe.ts` 定的，
而那支探針掃全場取最大 `alarmFactor`，`AiController` 只對
`threatSource ?? target` **一架**算。兩者若不等價，0.5 要重訂 ——
已列入送 Codex 複審的問題。

### 11.3 副判準退步超過雜訊 —— **退回那一步**

不接受退步，三個理由：

1. **專案已有先例。** 「破防力道連續化」與「異平面破防」兩個 Task 都是
   實測否決後整個退回，不是接受退步。
2. **本文修的是體驗缺陷，不是正確性缺陷。** 它沒有掙到「讓 AI 變弱」的
   額度。
3. **兩步互相獨立**（§7），退回其中一步，另一步照樣留著。

**兩個例外要分開講：**

- `ai-manoeuvre` / `ai-visible-evasion` / `ai-defence` 退步是**硬否決**，
  沒有商量餘地 —— 那三條守的是失速、安全層介入與破防，不是戰果。
- `fireShare` 或 `ai-duel-matrix` 退步、而 §8.1 的主判準**同時大幅改善**
  時，那是一個真正的取捨（護送打得比較好、單挑打得比較差），**回來問**。

### 11.4 §10 的但書 —— **接受，但加一個觀測窗**

接受。理由：§4 上線後「因能量脫離」只剩數秒（§3.4），`energyExit` 與
`extendRange` 這兩條出場路徑本來就沒什麼機會用到 —— 它們的作用變弱是

但「作用會變」不能只是一句但書。**已加 §8.5**：逐段記下 `extend` 是被

事實 —— 不留一個已經不作用的護欄假裝它還在守著什麼。
