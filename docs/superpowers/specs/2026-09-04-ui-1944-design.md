應該是要連操作邏輯都想想看怎麼改比較有遊戲風格」、「好，套用到遊戲」。

## 1. 畫面與狀態機

`src/ui/screens.ts` 新增一個畫面 `campaign`。轉移表：

```
  landing   start → menu
  menu      mission → campaign     skirmish → skirmish
  campaign  mission → mission      back → menu
  mission   back → campaign        fight → battle
  skirmish  back → menu            fight → battle
  battle    fight → battle   toMenu → menu   toSetup → skirmish   toMission → mission
```

- `campaign` 頁點一張卡：先 `hooks.onCampaign(c)`（新 hook，帶資料），再 `onEvent('mission')`。
  與既有的 `onMission` → `fight` 同一個模式（資料先於事件）。
- `battle.toMission → mission`：回到**同一條線**的簡報頁，不回陣營頁（陣營沒變）。
- `menu` 沒有 back（現況如此，landing 是一次性的）。
- `test/unit/screens.test.ts` 補 `campaign` 的四條轉移與「不合法組合回傳 current」。

### 2.4 簡報 `#mission`（重做）
左欄 300px：陣營標頭（陣營名／`第 k 關 / 4`）＋路線圖（四站，虛線相連）。
右欄：選中那一關的簡報。返回鈕「‹ 陣營」。

路線圖的站：`第 k 關　類型` ＋ 標題；`battle === null` 的站降透明並標「準備中」，**可以點**
（點了右欄顯示準備中的說明），但沒有出擊鈕。選中的站是紙（`.paperbit`）。

右欄（`battle !== null`）全部從 `ReadyMissionCard` 推（標題／類型／說明在卡上，其餘在 `card.battle`，
護送／攔截的 owner 在 `missionConfigFrom(card).rules`）：

```
  標題／類型／說明        card.title / card.type / card.summary
  目標                    battle.objective（德 M4 另加 → 返航：withdraw.message）
  我方                    blueSpec × blueCount；convoySpec 且 objective 是護送 → 再一列「↑ 要護送的」
  敵方                    redSpec × redCount；convoySpec 且是攔截 → 「↑ 要攔下的」
  戰場                    terrain → 群島／內陸農地／純海面
  時限                    seconds 有限 → 秒數；否則「無」
  敵方增援                waves.filter(side==='theirs')。**進場時刻是 `at + warnLead`**（`at` 秒發警告，
                          `warnLead` 秒後才 `reinforce`；德 M1 是 60 秒預警、64 秒進場）：
                            clock → `第 ${at + warnLead} 秒　機種 ×count`
                            alive → `${side 的白話}${role 的白話}剩 ≤ ${atMost} 架時（最晚第 ${byLatest + warnLead} 秒）　機種 ×count`
                                    side: mine → 我方、theirs → 敵方；role: fighter → 戰鬥機、bomber → 轟炸機、缺 → 空字串
  我方增援                waves.filter(side==='mine') 同上，標籤換成「我方增援」（目前沒有卡用到，但型別允許）
  中途變更                withdraw → `when 的白話 → message`
  撤離點                  withdraw → `後方 ${km} km，${seconds 有限 ? 倒數 : '無倒數'}`
```

護送／攔截的判斷：`missionConfigFrom(card).rules` 在 `kind === 'convoy'` 時帶 `owner`
（`missions.ts:577-586` 就是用它決定 convoy 放哪一隊）。`owner === 'blue'` 是護送（我方要護送的），
`'red'` 是攔截（要攔下的）。**不另寫一套判斷，也不去掃 units 的 duty。**

出擊鈕在右欄右下，只有它一顆。點了：`onMission(card)` → `onEvent('fight')`（不變）。

### 2.5 遭遇戰 `#skirmish`（重做）
見 §3 的資料模型。畫面：

- 標頭：「出擊編組」＋「最多五個分隊，每隊四架」＋想定四顆（勢均力敵／護航突破／以寡擊眾／轟炸機獵殺）
- 兩欄各：`我方 N / 20 架`；分隊列（一列一隊：帶隊圓點〔我方〕、機種名＋副名、角色／極速／耐受、
  四個三角形表示架數、− n ＋ ✕）；「＋ 加一個分隊」→ 展開八張機種卡（剪影、名、副名、極速）
- 中央：對戰條（我方藍／敵方紅按總數比例）＋ `8 : 10`、`戰鬥機 a : b`、`轟炸機 a : b`
- 下方：戰場三選一、開場高度三選一，各帶 SVG 示意圖
- 右下「起飛」；任一邊為 0 時禁用並顯示「兩邊都要有人才打得起來」

極速／耐受：耐受從 `AircraftSpec.hp` 讀；**極速不在 `AircraftSpec` 上**（Codex 審查），它在各機種檔
另外匯出的 `<ID>_HISTORICAL: HistoricalReference.vmaxAtCritical.speed`（m/s）。`skirmish.ts` 建一張
`HISTORICAL: Record<string, HistoricalReference>`（八個具名匯出），UI 從它讀並換算 km/h 四捨五入；
**測試：`ALL_SPECS` 每一個 id 都在表上**（少一格測試紅，不是畫面上少一個數字）。

### 2.6 戰報 `#board`（重做）
紙寬 760px。結構：

```
  勝敗（任務達成／任務失敗／勝利／落敗）＋ 一行：目標 · 卡名或「遭遇戰」 · 用時
  玩家卡（紙）：名字 機種 ／ 「我方第 k 分隊長機 · 存活或擊墜」／ 擊落 · 被擊落 · 助攻 · 剩餘結構%
  三行對比：擊落 a : b ／ 存活 a/n : b/m ／（convoy 卡才有）轟炸機存活 x/y
  <details>完整名單（N 架）</details> → 既有的兩張表
  出口：再打一場（紅）＋ 回設定頁／回任務列表（依模式擇一，既有的兩顆）
```

**沒有命中率** —— `Pilot` 沒有發數與命中的紀錄，不做假數字。剩餘結構 = 玩家座位 `hp / spec.hp`。
轟炸機存活：`b.convoy.seats` 是 `world.combatants` 的**索引**（`setup.ts:209`），
存活數 = `seats.filter((i) => b.world.combatants[i].hp > 0).length`。

`createScoreboard` 的介面加參數：`render(blue, red, banner, extra)`，`extra` 帶玩家卡與對比列
需要的數字；`main.ts` 算好傳進來。`scoreRows`／`sortScoreRows` 不動（它們有單元測試）。

## 3. 遭遇戰的資料模型

### 3.1 現況的問題
`SkirmishSetup.blue: string[]` 是逐架名單，`mixedLine` 把它**每 4 架硬切一隊**。UI 要的
「一個分隊 3 架」在這個模型下會變成混隊（`[p,p,p,b,b,b,b]` → `[p,p,p,b]、[b,b,b]`）。
而 `FlightPlan.members` 本來就允許 1~4 架 —— 限制只在 `mixedLine` 的切法。

### 3.2 新形狀

```ts
export interface Flight { readonly id: string; readonly count: number }   // 1 … SCHWARM_SIZE
export interface SkirmishSetup {
  readonly blue: readonly Flight[]     // 最多 MAX_FLIGHTS = MAX_SIDE / SCHWARM_SIZE = 5
  readonly red: readonly Flight[]
  readonly lead: number                // 我帶 blue 的第幾隊（分隊索引，不是座位）
  readonly terrain: TerrainKind
  readonly altitude: number
}
```

架數總和上限仍是 `MAX_SIDE`（20）；隊數上限 5。**不再有「17 架」以外的非整隊限制** ——
4+4+4+4+1 是合法的。

### 3.3 純函數（全部在 `battle/skirmish.ts`，全部有單元測試）

```
  flightsTotal(side)                       架數
  addFlight(setup, team, id)               末端加一隊 count = min(4, 剩餘架數)；沒空間原樣回傳
  setCount(setup, team, i, n)              夾在 1..4 且不超過 MAX_SIDE；n <= 0 等於 removeFlight
  removeFlight(setup, team, i)             拿掉一隊；lead 跟著夾（與現行 withoutAircraft 同一條規矩）
  setLead(setup, i)
  applyPreset(setup, key)                  四個想定（下表）；terrain/altitude 不動；**lead 重設為 0**
  uniform(blueId, n, redId, m)             介面不變，回傳新形狀；lead = floor(隊數/2)
```

四個想定（照 mockup 定案；架數是 `Flight.count`）：

```
  even    勢均力敵    我方 P-51D 4, 4              敵方 Bf 109 K-4 4, 4
  escort  護航突破    我方 P-51D 4, B-17G 4        敵方 Bf 109 K-4 4, 4, 2
  few     以寡擊眾    我方 Ki-84 3                 敵方 F6F-5 4, 4, 2
  hunt    轟炸機獵殺  我方 Bf 109 K-4 4, 4         敵方 B-17G 4, 4, P-51D 2
```

**`lead` 的夾制不能消失**：`battleConfigFrom` 必須把 `lead` 夾到 `[0, blue.length - 1]`
（現行 `playerAt` 的夾制就是為了 `assertOrderOfBattle` 的「恰好一筆 player」），`removeFlight`
與 `applyPreset` 也要維持這個不變量。**測試：lead 超界時 `battleConfigFrom` 仍產出恰好一筆 `player`。**

### 3.4 `order.ts` 新增 `flightLine(plan, blue: Flight-ish, red, leadFlight)`
輸入是「每隊一個機種與架數」，產出 `FlightPlan[]`，`members` 依 count 展開，`player: true`
掛在 `leadFlight` 那一隊（長機就是 `members[0]`，不再需要對調）。`mixedLine` **不動**
（它的測試與 `lineAbreast` 等價守則留著），`battleConfigFrom` 改呼叫 `flightLine`。

**等價守則（必須有測試）**：
- `flightLine` 對「每隊都滿 4 架、lead 隊」的輸入，與 `mixedLine(list, lead*4)` **逐項相同**
- `battleConfigFrom(DEFAULT_SKIRMISH)` 產出的 `units` 與改動前逐項相同（用 `mixedLine` 版本當對照組
  留在測試裡）

【更正】兩份重播校驗和（`spawn-baseline`、`tactics-baseline`）**不經過 skirmish** —— 它們釘的是
`lineAbreast` 與 `DEFAULT_BATTLE`（2026-09-04 grep 查證：那兩支測試與 fixture 都沒有 import
skirmish）。所以它們不是這一改的護欄，只是「順便必須仍然全綠」。
