## 2. 現況與四個量到的限制

### 2.1 網格畫不出它自己宣告的波

`OCEAN_SIZE / OCEAN_SEGMENTS = 10000 / 192 = 52.08 m` 一格。

| 波 | 波長 | 每波長取樣點 | 判定 |
|---|---:|---:|---|
| 1 | 140 m | 2.69 | 勉強 |
| 2 | 78 m | 1.50 | 低於 Nyquist |
| 3 | 31 m | **0.60** | 連一個取樣點都不到 |

第三道波在幾何上**不存在**，只是混疊。這是既有狀態，**這一份不修它**
（見 §4.3 的理由）。

### 2.2 坡度預算只有 ±10°

`A·k` 的 `atan`：2.83° + 3.23° + 4.06° = **10.02°**（方向不同，實際常在 ±5°）。

太陽仰角 53.0°（`scene.ts` 的 `DirectionalLight(-0.4, 0.8, 0.45)`）。反光要
出現，法線得落在視線與陽光的中間 —— 以現有坡度算，**觀察者以約 53° 俯角
朝太陽方位看海時進入反光帶**，±10° 的坡度把那條帶撐開到約 ±20°。

**那正是「一定角度會反光」。** 這個限制不是缺陷，是這份設計的物理基礎。

### 2.3 遠海是一片死平的四邊形

`farMesh` 是半邊 3,000 km、只有兩個三角形的平面，沒有波。而**看地平線時它
佔畫面的大部分**。只讓近海反光會在 5 km 處出現一個硬環 —— 與 `ocean.ts`
註解裡記著的「5 km 色帶」同一個失敗模式。

### 2.4 天上沒有太陽

`sky.ts` 是純兩色漸層。海面亮起來卻找不到光源，反光會顯得沒來由。而太陽
方向目前**只存在於 `scene.ts` 的區域變數裡**，沒有任何模組讀得到。

## 3. 架構

```
              src/render/sun.ts          ← 新增。太陽的唯一權威（葉節點）
                 ↑        ↑        ↑
          scene.ts    sky.ts    ocean.ts
                        ↑
                     fog.ts
```

`sun.ts` **不 import 任何 render 模組**，所以不可能有環。`fog.ts` 不准 import
`scene.ts` 這條既有約束不受影響。

### 3.1 為什麼太陽要獨立成一個模組

它現在同時被三個地方需要：`scene.ts` 的 `DirectionalLight`、`sky.ts` 的
太陽盤、`ocean.ts` 的反光。三份各自寫死的話，改一份忘另外兩份，太陽的位置
就會與它的反光、與它照出來的光分家 —— 而畫面上沒有任何東西會紅。

這與 2026-08-10 剛修掉的「漸層指數在 FRAG 字串裡與 `SKY_GRADIENT_POWER` 各
一份」是同一類的縫，處置方式也一樣：**一份常數，多處引用，測試釘住**。

### 3.2 天空漸層的 GLSL 也要共用

海面的 Fresnel 需要「往這個方向看出去的天空是什麼顏色」。那條公式現在有
兩份（`skyColorAt` 的 JS 與 `FRAG` 的 GLSL），加上海面就是三份。

`sky.ts` 改為匯出一段 GLSL 函數原始碼字串，`sky.ts` 自己與 `ocean.ts` 都
把它拼進各自的著色器。**GLSL 那一份因此只有一個來源**，JS 那一份（霧色要用）
仍然獨立，由既有測試釘住兩者的等價。

## 4. 海面著色

沿用 `MeshStandardMaterial` + `onBeforeCompile`，不換成自寫的 `ShaderMaterial`。
理由：three 的燈光、色彩空間、tone mapping 全部保留，而且這正是這個檔案已經
在用的手法。

### 4.1 法線改成解析導數，不再用 flatShading

現況 `flatShading: true` 讓法線是每個 52 m 面的常數。反光吃的是法線，而
52 m 的常數面只會給出巨大的方塊閃光。

改成在**片段**著色器裡用 `WAVES` 的解析導數算法線：

```
∂h/∂x = Σ Aᵢ · kᵢ · dirXᵢ · cos(kᵢ·(dir·xz) − spdᵢ·kᵢ·t)
∂h/∂z = Σ Aᵢ · kᵢ · dirZᵢ · cos(...)
n = normalize(vec3(−∂h/∂x, 1, −∂h/∂z))
```

### 4.2 「low poly」還在不在

**在。** low-poly 的觀感來自**輪廓**（52 m 的多邊形邊緣、地平線上的鋸齒），
不是來自法線。頂點位移一個字不動，輪廓完全不變。

換掉的只有面內的著色：由「整面同一個亮度」變成「面內平滑漸變 + 碎光」。
若人工驗收認為這樣「太寫實、不夠 low poly」，退路是把解析法線量化到有限
階數（例如 8 階），那是一行 `floor`。**這條退路要寫進 plan 的驗收步驟。**

### 4.3 為什麼法線用三道波、而幾何只畫得出一道半

這是刻意的，而且比加密網格更對。

遠處的小浪本來就是**次像素**的 —— 你看不到它的起伏，只看得到它造成的
反光變化。把第三道波留在法線裡、不留在幾何裡，正是真實海面在遠處的樣子。

代價：法線是「真波」的法線，高度是「混疊波」的高度，兩者在高頻上對不齊。
在 52 m 的面上，31 m 的波每個面內走完 1.7 個週期 —— 對不齊的尺度小於一個
面，看起來是面內的細碎明暗，不是錯位。**這是可接受的，而且是這份設計刻意
選的取捨。**

**`WAVES` / `gerstnerHeight` / `FAR_SEA_Y` 一個字都不動** —— `crash.ts` 的
入水判定、`splash`、`wrecks` 全部走 `heightAt`，動它就動到物理。

### 4.4 微觀粗糙度

比 31 m 更細的浪不進法線，改成**統計性的粗糙度**：它只決定 glitter 散得多
開，不決定往哪個方向反。

```
slope     = length(vec2(∂h/∂x, ∂h/∂z))          // 0 .. 約 0.177
roughness = mix(GLITTER_ROUGHNESS_MIN, GLITTER_ROUGHNESS_MAX,
                clamp(slope / MAX_SLOPE, 0.0, 1.0))
```

浪尖（坡度大）粗、波谷（坡度小）平 —— 於是碎光集中在波谷與背光的坡面，
浪尖那一側柔一點。這是真實 glitter path 的主要成因，而且**只用已經算出來
的導數，不需要額外的取樣**。

**不用貼圖、也不用程序噪音。** 這個專案沒有貼圖管線，加一張圖等於加一條
資產路徑；而程序噪音（value / simplex）要一整個雜湊函數，那是可觀的片段
成本，換來的隨機性在 52 m 的面上看不出比坡度好。坡度是現成的、免費的、
而且與波的相位綁在一起 —— 所以它會**跟著浪一起動**，噪音不會。

`MAX_SLOPE` 是 `Σ Aᵢ·kᵢ` = 0.1767，由 `WAVES` 推導，不是寫死的數字。

### 4.5 Fresnel

```
F = F0 + (1 − F0) · (1 − max(0, n·v))^5      F0 = 0.02（水）
最終色 = mix(海色·漫射, 天空色(reflect(−v, n)), F)
```

平視（`n·v → 0`）時 F → 1，海面幾乎全是反射的天空色；俯視時 F → 0.02，
看到的是深海色。**這一項單獨就會讓地平線附近的海自然變亮**，而那正是真實
海面的樣子。

【它與「海面近到遠幾乎沒有顏色變化」衝突嗎】不衝突。既有那條要求針對的是
**霧**造成的近遠色差（已由 `fog: false` 解掉）。Fresnel 造成的是**視角**
相依的變化 —— 同一片海你低頭看跟平視看不一樣，那是物理，不是接縫。
`fog.test.ts` 釘的是 base color，不受影響。

## 5. 遠海

**用同一段片段著色器。** 關鍵洞見：法線是由**世界座標**解析算出來的，與
有沒有頂點波無關 —— 所以遠海這片平面也能有波的法線。

於是 5 km 的接縫在**光照上完全連續**（兩邊同一條公式、同一組 `WAVES`），
只剩既有的 3 m 高度差（5 km 外張角 0.034°，小於一個像素）。

### 5.1 遠處要淡出

遠海延伸到 3,000 km。兩個問題：

1. **浮點精度**：`sin(k·x)` 在 x ~ 10⁶、k ~ 0.2 時相位是 10⁵ 量級，`highp
   float` 的 24 bit 尾數只剩約 0.006 rad 的解析度 —— 還可用，但已接近極限。
2. **物理**：夠遠時一個像素涵蓋許多個波，glitter 平均掉，該只剩鏡面。

處置：法線擾動的幅度隨**離相機的水平距離**線性淡出，在 `GLITTER_FADE_START`
（暫定 8 km）到 `GLITTER_FADE_END`（暫定 40 km）之間由 1 降到 0，之後法線
恆為 `+Y`。淡出是連續的，所以不會有環。

兩個距離常數要由人工驗收回填，**不是實作者定的**。

## 6. 天空的太陽

`sky.ts` 的片段著色器加一顆太陽盤與光暈：

```
c = dot(normalize(vDir), sunDir)
disc  = smoothstep(cos(SUN_ANGULAR_RADIUS + SOFT), cos(SUN_ANGULAR_RADIUS), c)
halo  = pow(max(c, 0), SUN_HALO_POWER)
色 = 漸層 + SUN_COLOR · (disc + halo · SUN_HALO_STRENGTH)
```

- `SUN_ANGULAR_RADIUS`：真實太陽 0.265°。畫面上 1080p / 65° 只有 8 px ——
  **太小，看起來像壞點**。取 1.0°（30 px），並在註解裡寫明這是刻意誇大的。
- 太陽盤**不寫深度**（天空球本來就 `depthWrite: false`），所以飛機一定蓋
  得過它。
- **不做鏡頭光暈、不做眩光**。那是後處理，這個專案沒有後處理管線。

## 8. 怎麼測「反光」

「好不好看」測不到。**但反光的幾何測得到**，而那才是「一定角度會反光」這句
需求的內容。

### 8.1 CPU 版的三個純函數

與 `gerstnerHeight` 同一個手法：著色器裡的東西測不到，所以每一條公式都寫一份
CPU 版，**兩份必須一致**，由測試釘住。

```ts
export function waveNormal(x: number, z: number, time: number, out: Vector3): Vector3
export function fresnel(nDotV: number): number
export function glintIntensity(n: Vector3, v: Vector3, l: Vector3, roughness: number): number
```

### 8.2 可以斷言的東西

| 斷言 | 為什麼守得住需求 |
|---|---|
| `waveNormal` 的解析導數與 `gerstnerHeight` 的數值微分一致（1e-6） | 法線與高度來自同一組波，不會分家 |
| 任何輸入下 `slopeRoughness` 都不回 NaN；`MAX_WAVE_SLOPE` 為 0 時回下限 | 退化情形不出 NaN（**2026-08-10 補**：初稿承諾了卻沒測，而且公式真的會 `0/0`） |
| `fresnel(1) ≈ 0.02`、`fresnel(0) = 1`、單調遞減 | 平視反射天空、俯視看深海 |
| `glintIntensity` 峰值的 `V` 與太陽**水平方位相反**、仰角相同 | **2026-08-10 修正**：`V` 是「水面→眼睛」，與玩家視線差 180°。初稿把兩者當同一方向 |
| `glintIntensity` 在「玩家朝太陽方位、俯角 = 太陽仰角」時取最大 | **這就是「一定角度會反光」** |
| 同一方位上俯角偏離 25° 時強度掉到峰值的 1/10 以下 | 反光是**帶**，不是整片海都在閃 |
| 峰值恆為 1、粗糙度只改變帶寬 | **2026-08-10 改**：歸一化之後亮度與帶寬才是兩個獨立的旋鈕 |
| `glintIntensity` 在 `n·l ≤ 0`（太陽在水面下）時為 0 | 不會從海底發光 |
| 淡出函數在 `FADE_START` 為 1、`FADE_END` 為 0、之間單調 | 5 km / 40 km 都不會出現環 |
| 兩個材質（細浪面、遠海）的 glitter uniform 逐值相同 | **這是 5 km 色帶的守門員**，與既有 `fog` 那兩條同一個理由 |
| **兩個材質的 `customProgramCacheKey` 不同、且不是預設值** | **2026-08-10 補**：預設是 `onBeforeCompile.toString()`，兩個閉包字串相同 → 撞 key → 近海拿到遠海那份、海變平但碰撞仍有波 |
| **注入後的著色器原始碼真的含 `glintGLSL(` / `fresnelGLSL(` 的呼叫，且在 `opaque_fragment` 之後** | **2026-08-10 補**：anchor 拼錯或整段沒接上，著色器照樣編譯、只是沒有反光，而全套測試照樣綠 |
| **近海的頂點著色器有 `transformed.y += waveH`、遠海沒有** | **2026-08-10 補**：撞 key 的直接守門員 |
| **`uGlintStrength` 等於 `GLINT_STRENGTH` 且為正** | **2026-08-10 補**：設成 0 的話兩材質仍逐值相等、測試全綠，畫面上完全沒有反光 |
| **兩個材質沒有 normal/bump map、是單面、`flatShading` 為 false** | **2026-08-10 補**：解析法線寫在 `normal_fragment_begin` 之後，而 `tbn` 已用舊法線建好 —— 這一條把「現況安全」的**前提**釘住 |
| **three 的 `ShaderLib.physical.fragmentShader` 確實含我們用的兩個 anchor，且順序正確** | **2026-08-10 補**：守 three 升級改名 |
| `sun.ts` 的方向已正規化，且 `scene.ts` 的燈用的就是它 | 反光與照明不會分家 |
| `sky.ts` 的太陽 uniform 用的是 `sun.ts` 的常數 | 天上的太陽與海上的反光不會分家 |

**這一層守不住什麼（誠實的天花板）**：GLSL 的**語意**。把 `glintGLSL` 改成
永遠回傳常數，字串測試看不出來。緩解的手段是把兩邊都要用的數字（`WATER_F0`、
`GLINT_EPSILON`）用字串模板從 TS 常數插進 GLSL，讓它們**不可能**分家；剩下
的公式形狀只能靠人眼與 Playwright 的四個觀察點。

### 8.3 量測探針（不是測試）

`test/tools/glint-geometry.probe.ts`：掃描視線仰角 0°~90° × 方位 0°~360°，
印出 glitter 強度的分布 —— 好讓「反光帶在哪、多寬」有數字可談，而不是
「感覺不太對」。

### 8.4 Playwright

沿用既有 e2e 的形式：截圖 + `console.log('[人工看] …')`，**不對像素下斷言**。
新增的觀察點：

1. 座艙視角朝太陽方位、俯角約 50°，應看到碎光路
2. 同一位置轉 180°，應**沒有**碎光
3. 上帝視角高空俯視，5 km 接縫處不得出現亮度環
4. 天頂附近應看得到太陽盤，且飛機飛過時蓋得過它

## 9. 效能

`perf-gate` 量的是 `World.step`（CPU），這一份**完全不碰它**。

GPU 側：片段著色器變重，而海面是全螢幕。三道波的解析導數是 3 次 `sin` +
3 次 `cos`，遠海還多一個全螢幕 overdraw。**要在 plan 裡加一個實測步驟**
（`battlefield-visuals.e2e.ts` 已經在讀 WebGL 參數，同一條路徑加幀時取樣），
若 1080p 掉到 60 fps 以下就得砍功能，而不是放寬。

## 10. 明確不做

- 不加密網格（§2.1 的混疊留著，理由見 §4.3）
- 不動 `WAVES`、`gerstnerHeight`、`FAR_SEA_Y`（會動到物理）
- 不做貼圖、不做後處理、不做鏡頭光暈
- 不做時間變化的太陽（日夜循環）—— 太陽是常數
- 不做浪尖白沫（可以之後再加，但它需要另一組參數與另一輪驗收）
- 不改 `fog.test.ts` 既有的任何門檻

## 11. 待人工驗收回填的參數

這些**不得由實作者定值**，plan 要留成待填：

| 參數 | 暫定值 | 由什麼決定 |
|---|---|---|
| `GLITTER_ROUGHNESS_MIN` / `MAX` | 0.04 / 0.20 | 碎光的顆粒大小 |
| **`GLINT_STRENGTH`** | **0.6** | **反光峰值有多亮**（見下） |
| `GLITTER_FADE_START` / `END` | 8 km / 40 km | 遠處還看不看得到閃 |
| `SUN_ANGULAR_RADIUS` | 1.0° | 太陽盤大小 |
| `SUN_HALO_POWER` / `STRENGTH` | 64 / 0.5 | 光暈範圍與亮度 |
| 法線量化階數（若採用 §4.2 的退路） | 不量化 | low-poly 味道夠不夠 |

【`GLINT_STRENGTH` 是 2026-08-10 Codex 審查補進來的】初稿只在 plan 裡定義了
它、卻沒有列進這張表，等於一個**未經驗收的亮度值**會直接留在程式碼裡，而所有
測試照樣綠。

同一次審查也修正了它的數量級：`glintIntensity` 現在回傳**歸一化**的形狀
（峰值恆為 1），所以這個數字就是「峰值把該像素往白色推多少」，與線性顏色
同單位。改之前它乘的是原始的 GGX `D`，而 `D_max = 1/(π·roughness⁴)` 在
roughness 0.04 時是 **1.24 × 10⁵** —— 沒有任何一個常數同時適用於窄峰與粗糙
的情形。
