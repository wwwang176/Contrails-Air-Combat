# 天空、海面與地平線的重新調色 —— 設計

> 2026-08-09。起因是專案負責人試飛後的要求。**這份 spec 推翻
> `2026-08-08-battlefield-visuals-design.md` 的一條裁定**，見 §5。

## 1. 要求（原文）

> 天空跟海面我想調整一下，不然現在接縫處太怪了
> 天空整體顏色淡一點，海面要比天空深，然後天空到海面 海面近到遠幾乎沒有
> 顏色變化，天空有頂部比較深、海面比較淺

拆成四件事：

| # | 要求 | 現況 |
|---|---|---|
| 1 | 天空整體淡一點 | 天頂 L 0.115、地平線 L 0.261 |
| 2 | 海面比天空深 | 近處成立（0.060 對 0.261），**遠處幾乎不成立**（0.169 對 0.261） |
| 3 | 海面近到遠幾乎沒有顏色變化 | 近到遠變了 **0.109**（0.060 → 0.169） |
| 4 | 天空頂部比較深、靠海面比較淺 | **已經成立**，不必改方向 |

## 2. 現況的數字，與接縫為什麼怪

明度是 three 工作色彩空間的 HSL `l`。由上到下：

| 位置 | 顏色 | L |
|---|---|---|
| 天頂 | `#1f4f80` | 0.115 |
| 天空 45° | `#54779a` | 0.205 |
| 地平線上的天空 | `#6788a7` | **0.261** |
| ─── 接縫 ─── | | |
| 海 @250 km | `#537089` | **0.169** |
| 海 @80 km | `#49657e` | 0.138 |
| 海 @30 km | `#2b4a65` | 0.077 |
| 海 @2 km | `#1d3f5c` | 0.060 |

**接縫那一階只有 0.092，而海面自己近到遠就變了 0.109。** 也就是說：那條線
比它兩側的漸層還弱 —— 讀起來不是一條界線，是一整片洗白裡的一段。這就是
「怪」。

海面的近到遠變化**完全來自霧**：`FOG_COLOR` 由天空色推導
（`skyColorAt(0) × 0.65`），所以遠海必然往天空的方向靠。要求 3 與這個推導
直接衝突。

## 3. 一個沒被講出來的問題：畫面上的「地平線」其實是遠海平面的邊

這是算的時候挖出來的，要求裡沒提，但它決定設計。

這個世界的海是**平的**（`y = −3` 的平面），所以幾何上的地平線永遠是
**與海面平行的那條視線**，也就是世界仰角 0°，與高度無關。（注意那不等於
「畫面中線」—— 相機一俯仰它就在畫面上移動。這裡談的一律是世界仰角。）

但 `farMesh` 是一片**有限**的四邊形，半邊 250 km。從離海面 `h = 相機高度
− FAR_SEA_Y` 看出去，它的邊落在俯角 `atan(h / 半邊)`。

【那是一個**上界**，不是單一角度】那片四邊形是正方形，`atan(h / 半邊)` 是
朝**邊的中點**看時的俯角；朝**角**看時距離是 `半邊 × √2`，俯角只有一半多
一點。所以畫面上那條邊是一條隨方位起伏的曲線，`atan(h / 半邊)` 是它最深的
那一點。下表取的都是這個最壞值。

像素數用透視投影算：`px = (H/2)·tan θ / tan(FOV_v/2)`，1080p / 65° 下是
`847.6 × tan θ`。

| 相機高度 | 遠海邊的俯角（最壞） | 1080p / 65° |
|---|---|---|
| 1,000 m | 0.230° | 3.4 px |
| 6,000 m | 1.376° | 20.4 px |
| 12,000 m（上帝視角上限） | **2.751°** | **40.7 px** |

仰角 0° 與那條邊之間的那一段，看到的是天空球的下半部。所以**畫面上那條
「地平線」不是幾何地平線，是遠海的邊，而且它隨高度往下跑。**

現在看不太出來，因為遠海的邊已經被霧化成 L 0.169、與天空的 0.261 只差
0.092 —— 糊掉了。**一旦照要求 3 把海面的霧拿掉，那條邊會從「糊」變成
L 0.060 對 L 0.431 的硬階。** 於是缺陷從「看不清楚」升級成「非常清楚，而且
在錯的位置、還會隨高度移動」。

所以要求 3 沒辦法單獨做。

## 4. 設計

### 4.1 天空：調色盤 B

```
SKY_HORIZON  0x9fc3d8 → 0xc6dfec
SKY_ZENITH   0x1f4f80 → 0x4d84b8
```

`SKY_GRADIENT_POWER` **不動**（0.65）。

| 位置 | 現況 | B 案 |
|---|---|---|
| 天頂 | `#1f4f80` L 0.115 | `#4d84b8` **L 0.277** |
| 45° | `#54779a` L 0.205 | `#779fc5` L 0.373 |
| 地平線 | `#6788a7` L 0.261 | `#89accd` **L 0.431** |
| 天頂 → 地平線的落差 | 0.146 | 0.154 |

要求 1 由「地平線 0.261 → 0.431」達成；要求 4 由「落差仍是 0.15 且為正」
維持 —— 那個關係本來就成立，這裡只是不能把它弄丟。

【`SKY_HORIZON` 這個常數仍然不出現在畫面上】`t = dirY × 0.5 + 0.5`，地平線
落在漸層正中間。新的 `SKY_HORIZON`（L 0.702）只出現在 `dirY = −1`（正下方），
而那裡被海擋著。既有那條記錄此事的測試繼續有效（0.431 < 0.702 − 0.2）。

### 4.2 海面：完全均勻，材質不吃霧

`ocean.ts` 的兩個材質（細浪面與遠海）都設 `fog: false`。**霧**造成的近遠
色差於是歸零 —— 現況那 0.109 全部來自霧，所以要求 3 由這一項單獨達成。

專案負責人在兩個選項（完全均勻 / 幾乎均勻）之間選了**完全均勻**。

【不要誤讀成「每一個像素都是 `#1d3f5c`」】那是 `MeshStandardMaterial` 的
**base color**，畫面上的像素還要過一次 PBR 著色與色彩轉換。細浪面另有頂點
位移與 `flatShading: true`，遠海沒有 —— 所以 5 km 那道接縫的亮度／質感差異
**不在本次處理範圍內**，它是既有的、與霧無關的事（現況 5 km 的霧量只有
0.49%，本來就幾乎沒有霧在那裡）。本次能保證的是「**霧**不再讓海面近遠變
色」，不是「海面是一片死板的單色」。

要求 2 因此變成一條乾淨的常數關係：`L(SEA_COLOR) = 0.060` 對
`L(地平線上的天空) = 0.431`，**階差 0.371**（現況 0.092）。這條關係比的是
base color 與天空色，理由同上 —— 那是唯一測得到、也唯一不會隨燈光漂掉的
一組數。

【為什麼是關掉逐材質的霧，不是把全域霧色改暗】全域霧色同時服務所有物件。
把它改到接近海色，遠處的飛機就會在**亮天空**的背景上化成暗色 —— 換一個
方向的錯。霧與海本來就要的是不同的東西，讓海退出霧比較誠實。

### 4.3 遠海放大到「實質無限」

```
FAR_SEA_SIZE  500_000 → 6_000_000     （半邊 250 km → 3,000 km）
CAMERA_FAR    800_000 → 5_000_000
```

§3 那條邊的俯角（最壞值）變成：

| 相機高度 | 半邊 250 km | 半邊 3,000 km |
|---|---|---|
| 1,000 m | 0.230°（3.4 px） | 0.019°（0.28 px） |
| 6,000 m | 1.376°（20.4 px） | 0.115°（1.7 px） |
| 12,000 m | 2.751°（40.7 px） | **0.229°（3.4 px）** |

**判準是「戰鬥高度下低於一個像素、極端高度下低於四個像素」。** 6,000 m 以下
（也就是實際纏鬥的整個高度帶）只剩 1.7 px 以內；只有上帝視角刻意爬到升限
才會到 3.4 px，而那是一條細線、不是 40 px 的色帶。

【這是近似，不是「精確落在幾何地平線」】有限平面永遠做不到精確。要精確就得
換成相機相對的程序化海面或 clip-space 的解法 —— 那是另一個量級的改動，而
現況（40.7 px）與目標（3.4 px）之間差了一個數量級，先把數量級拿掉。若專案
負責人試飛後仍看得出那條線的位置不對，再談換做法。

【為什麼不用「把天空球下半部塗成海色」那個更漂亮的做法】那樣地平線會**精確**
落在 `dirY = 0`，而且不必動遠平面。但天空球是 `ShaderMaterial`、**不吃光**，
遠海是 `MeshStandardMaterial`、**吃光**。兩者要接得上就得在 CPU 重算一次
three 的 PBR 著色 —— 一個會隨燈光設定漂掉、又沒有東西守得住的耦合。放大
平面沒有任何顏色匹配問題。

【遠平面拉大的代價】近場深度精度由**近平面**決定，`(f−n)/(n·f) → 1/n`，
近平面沒有動（1 m）。`scene.ts` 對 60 km → 800 km 那次已經算過同一件事。
頂點座標到 ±3,000 km 時 float32 的間距是 0.25 m，而那片平面是平的、
且每幀跟著相機重新置中。

### 4.4 霧色不再壓暗

```
FOG_SKY_DARKEN  刪除
FOG_COLOR       skyColorAt(0) × 0.65  →  skyColorAt(0)
```

`FOG_SKY_DARKEN` 存在的唯一理由是「遠海化進霧色之後不能與天空同色，否則
地平線消失」（見 `fog.ts` 的註解）。§4.2 之後**遠海根本不化進霧色**，那個
理由就沒了。

霧剩下的工作只有一件：物件的空氣透視。座艙視角下物件絕大多數是在**天空**
的背景上看到的，所以霧色就該是地平線上的天空色 —— 遠處的飛機自然融進天空。

【但上帝視角俯視時背景是海，而海不再吃霧】那時遠處的飛機、殘骸、煙霧會往
**亮的**霧色化，而背景是 L 0.060 的深海 —— 化出來的是偏亮的藍色斑點，不是
融進海面。這是這個設計唯一的已知代價，而且**單一的 `FogExp2` 顏色無法同時
匹配亮天空與深海** —— 要解就得做方向相依的霧色，那是另一份 spec。

幅度：`FOG_DENSITY` 不動，30 km 處霧量 16%，也就是物件的顏色往霧色移動
16%。戰場尺度（30 km）內就是這個上限。**這一項列為人工驗收的必看項目**，
若專案負責人認為不可接受，選項是把 `FOG_COLOR` 調到天空與海之間的折衷值，
或退回方向相依的做法。

`FOG_DENSITY` **不動**（1.4e-5），它那三條門檻（5 km / 30 km / 250 km）
與本次無關。

## 5. 被推翻的既有裁定

`test/unit/fog.test.ts` 有一條：

```ts
it('霧色仍然比近處的海亮（深度感靠這個差）', () => {
  expect(lightness(FOG_COLOR)).toBeGreaterThan(lightness(new Color(SEA_COLOR)) + 0.05)
})
```

它的註解寫著「霧色若暗到接近海的基本色，遠處的海與近處的海就一樣暗 ——
霧的深度感整個不見」。**那正是專案負責人現在要的。** 這條測試連同它的
理由一起刪除。

同一組的 `霧色比**地平線上的**天空色暗` 與 `暗的幅度看得出來` 也一起走 ——
它們守的是「靠霧色與天空色的差撐出地平線」，而地平線現在由**海色**與天空色
的差撐起來。用 §6 的新斷言取代，守的是同一個需求（「要看得出地平線」），
只是換了正確的對象。

**這是護欄重新定值，而定值是專案負責人的決定。** 這份 spec 記錄的是那個
決定，不是實作者的判斷。

## 6. 測試

`test/unit/fog.test.ts`（本次動的都在這裡，另加 `sky` / `ocean` 的斷言）：

| 斷言 | 守的是哪一條要求 |
|---|---|
| **海色比地平線上的天空色暗，且差距 > 0.25** | 要求 2。取代原本比霧色的兩條 |
| **兩個海面材質的 `fog` 都是 `false`** | 要求 3。這是「霧不再讓海面近遠變色」唯一的來源。**兩個要分開斷言** —— 漏掉一個的症狀是 5 km 處出現一條色帶 |
| **天頂比地平線上的天空暗，且差距 > 0.10** | 要求 4。防止有人日後把漸層調反或壓平 |
| **地平線上的天空比改動前亮**（> 0.35）**且天頂也有下限**（> 0.20） | 要求 1。只釘地平線的話，有人可以把天頂調得更黑而仍然通過 —— 那就不是「整體淡一點」 |
| **`createSky()` 的 uniform 真的用了 `SKY_HORIZON` / `SKY_ZENITH`** | 上面四條測的都是 CPU 的 `skyColorAt`，而畫面是著色器畫的。這一條把兩份接起來（`sky.ts` 的「兩份必須一致」原本沒有任何測試） |
| **`FOG_COLOR` 逐分量等於 `skyColorAt(0)`** | 取代被刪掉的「霧色比天空暗」。**霧色必須跟著天空走**這個需求仍然成立，只是關係由「暗一階」變成「相等」；沒有這條的話 `FOG_COLOR` 可以被改成任意常數而不會紅 |
| 遠海的邊在上帝視角上限處落在幾何地平線以下 < 0.3° | §4.3。要用 `DEFAULT_GOD_CAMERA.maxAltitude` 與 `FAR_SEA_Y` 算，不可寫死；並斷言 `FAR_SEA_SIZE > 0`（負值會讓角度變負而假綠） |
| `CAMERA_FAR` 大於遠海的半對角線 | 既有，值改了要跟著動 |
| `SKY_HORIZON` 這個常數不出現在地平線上 | 既有，記錄一個歷史錯誤，繼續有效 |
| `fogFactor` 的三條密度門檻 | 既有，**一個字都不動** |
| `createFog` 用的是設計值、回傳複本 | 既有，不動。**注意它守不住 `FOG_COLOR` 的定義** —— 它只比 `createFog().color` 與 `FOG_COLOR`，兩邊一起改照樣綠。那是上面那條新斷言存在的理由 |

【刪掉 `遠海邊緣完全化進霧色（才不會看到硬邊）`】它守的是「遠海的邊要被霧
化掉」，而 §4.2 之後遠海不吃霧、§4.3 之後那條邊也不再需要被藏起來（它已經
在眼高上）。它的角色由上表的「遠海的邊在 12,000 m 處…」接手 —— 同一個需求，
換成直接量幾何而不是量霧。

## 7. 不做的事

- **不動 `SKY_GRADIENT_POWER`。** 天頂到地平線的落差本來就是 0.146，B 案是
  0.154，要求 4 已經滿足，沒有理由再多一個變數。
- **不動 `FOG_DENSITY` 與它的三條門檻。**
- **不動 `SEA_COLOR`。** 要求說的是「海面比天空深」，做法是把天空提亮，不是
  把海壓暗 —— 海再暗就只剩黑色。
- **不動燈光。** 海面的實際亮度是 `SEA_COLOR` 過一次 PBR 著色的結果，本次
  只改基本色與霧，不碰 `sun` / `HemisphereLight` / `AmbientLight`。
- **不做「天空球下半部塗成海色」。** 理由見 §4.3。
- **不改波形、`FAR_SEA_Y`、`renderOrder`。**
- **不處理 5 km 那道細浪面與遠海的接縫。** 它的差異來自 `flatShading` 與
  頂點位移，與霧無關（該處霧量只有 0.49%），是既有的事。
- **不做方向相依的霧色。** 見 §4.4 的已知代價。
- **不換成程序化／clip-space 的無限海面。** 見 §4.3。

## 8. Codex 對本 spec 與計畫的審查（11 條，9 條 Important）

三條指出的是**我的實質錯誤**，已直接改進上面的內文：

| # | 內容 | 處置 |
|---|---|---|
| E5 | 「海面恆為 `SEA_COLOR`、變化量 0.000」不成立 —— 那是 base color，實際像素還過一次 PBR，而且細浪面有 `flatShading`、遠海沒有 | §4.2 改寫成「**霧**造成的近遠色差為零」，並把 5 km 接縫明確排除在範圍外 |
| E8 | 計畫把 `vis-3-high.png` 當成地平線的主要證據 —— 但那張是上帝視角 −45° 俯角拍的，65° FOV 全部落在地平線以下，**根本拍不到** | 見 plan v2：改用座艙視角那張，並把 pitch 明確化 |
| E4 | 「物件絕大多數在天空背景上」在上帝視角俯視時不成立 —— 遠處飛機會在深海上化成亮藍色 | §4.4 加上這一段已知代價與 16% 的幅度，列為人工驗收必看項目 |

其餘採納的：E1（`atan(h / 半邊)` 是**上界**不是單一角度；高度要用
`相機高度 − FAR_SEA_Y`；「眼高」是世界仰角 0° 不是畫面中線）、E2（像素數要用
`(H/2)·tanθ/tan(FOV/2)`，3.4 px 不是 3.8 px；並明確寫出可接受的判準）、
E6 + E10（`createFog` 那條守不住 `FOG_COLOR` 的定義，補一條逐分量比對
`skyColorAt(0)`）、E7（天空提亮只釘地平線不夠，要加天頂下限；並補一條把
著色器 uniform 與 CPU 常數接起來的斷言）、E11（`fog.ts`、`scene.ts`、
`sky.ts`、e2e 裡描述舊值的註解要一併清掉）。

E3（WebGL 只保證 16-bit 深度緩衝，而所有精度計算都假設 24-bit）：**採納為
量測項目而非阻擋項** —— 那是遠平面拉到 800 km 時就存在的事，不是本次引入
的。e2e 加一行讀 `gl.getParameter(gl.DEPTH_BITS)` 記錄下來。
