# 魚雷投放的 HUD

2026-09-07

## 1. 要做的事

專案負責人的四條裁決：

1. **航跡線**：畫魚雷入水之後會跑到哪，**畫成平面的**（HUD 全都是平面的），
   線上加距離刻度。**只在投彈模式畫。**
2. **投放閘門**：說出是哪一條不過。放在畫面下方**與「裝填中」同一個位置**，
   兩者二擇一。
3. **攔截標記與目標殘影：不做。** 提前量由玩家自己評估。
4. **高度錶加一圈可投高度的弧**，範圍要**算出來**不是寫死 —— 日後每台飛機
   的包絡可能不同。

## 2. 為什麼現在的畫面對魚雷是錯的

`hud/widgets/bombsight.ts` 對兩種彈藥畫同一個圈。**圈是炸彈的語彙**：投彈時
落點就是傷害點，一個圈回答了全部問題。

魚雷不是。`world/torpedo.ts` 的入水點只是一條 **2,000 m 直線航跡的起點**
（`TORPEDO_RANGE`，22 m/s，跑滿就無聲自沉）。圈畫的那個位置對「會不會中」
幾乎不帶資訊。

三個具體的缺口：

| 缺口 | 後果 |
|---|---|
| 提前量沒有任何依據 | 雷 22 m/s、船 8 m/s。1,000 m 外正橫投放，水中跑 45 s，船走掉 364 m —— 提前角 20°。玩家無從估算 |
| `TORPEDO_RANGE` 是隱形的 | 跑滿是**無聲回收**（`world/torpedo.ts` §`stepWater`）：沒有爆炸、沒有水柱、沒有訊息。投遠了什麼都不會發生，而玩家學不到任何東西 |
| `releaseOk` 一個布林扛四個條件 | `TORPEDO_ENVELOPE` 是 12°／±6°／20…200 m，紅色是常態。紅告訴你「不行」，沒告訴你哪一根桿子拉錯 |

第三條 `hud/types.ts` 的 `releaseOk` 註解自己寫著「要告訴玩家是坡度還是高度
不對的話，那是另一個儀表的工作」—— 這一輪把那個儀表做出來。

## 3. 範圍

**只加畫面顯示，不動任何模擬。** 不碰彈道、不碰包絡的值、不碰命中判定、
不碰 AI。

不做的事：

- **不做攔截標記、不做目標殘影**（負責人裁決）。距離刻度是它的替代品：
  玩家要自己估提前量，就得有一把尺。
- **不做「現在投！」的提示音或閃燈。** 判準是玩起來合不合理 —— 自動投放
  提示把一個技術動作變成 QTE。
- **一般飛行不畫航跡線**（負責人裁決）。落點圈在一般飛行照舊畫。
- **炸彈不吃閘門讀數與高度弧。** `BOMB_ENVELOPE` 只擋退化狀態（倒飛、
  60 m），常態恆綠，畫出來是純噪音。
- **不顯示雷的航速與定深。** 不可操作。

## 4. 單一來源：閘門讀的必須是 `canRelease` 讀的那一份

這一節是整份 SPEC 最重要的一條。

**症狀先講**：閘門三格全綠而扳機沒有反應，或者反過來。這不會拋例外、不會
有錯誤訊息，玩家只會覺得「這遊戲的投彈壞了」。

現在有兩個現成的陷阱：

### 4.1 `HudFrame.altitude` 不是包絡吃的那個高度

```
  main.ts:1508  canRelease(..., agl, ...)   agl = renderPos.y − collisionHeightAt(x, z)
  main.ts:1734  hudFrame.altitude = renderPos.y                        ← 海拔
```

海上兩者相同（海的碰撞高度是 0），所以現在看不出來。飛過島上空就會分家。

**處置**：`HudFrame` 加 `releaseAgl`，由 `main.ts` 從**同一個 `agl` 區域
變數**填。閘門與高度弧只讀它，不得自己減地形。

### 4.2 門檻不得抄第二份

`envelopeFor(kind)` 今天回的是一個**依彈種分的模組常數，每一台飛機共用同
一份**。widget 自己去呼叫 `envelopeFor`，拿到的是「HUD 沒寫死」，但拿不到
「每台飛機不同」—— 哪天包絡真的變成逐機的（那是 `weapons/releaseEnvelope.ts`
與 `weapons/stores.ts` 的改動），widget 還得再改一次。

**處置**：`HudFrame` 加 `releaseEnv: ReleaseEnvelope | null`，由 `main.ts`
填**它餵給 `canRelease` 的那一個物件**。widget 只讀這一格。

它是模組常數的參考，不是複本 —— 不配置。

### 4.3 `canRelease` 要由三支述詞組成，不是各寫一份

閘門要逐軸的結果，而 `canRelease` 回一個布林。**兩邊各寫一份比較就會漂**。

`weapons/releaseEnvelope.ts` 轉出三支述詞，`canRelease` 改寫成它們的合取
（加上速度那一條）：

```ts
export function rollOk(env: ReleaseEnvelope, roll: number): boolean
export function pitchOk(env: ReleaseEnvelope, pitch: number): boolean
export function aglOk(env: ReleaseEnvelope, agl: number): boolean
```

`canRelease` 的**行為一個字都不能變**（既有測試全綠），只是換一種寫法。
護欄見 §8.1。

## 5. 航跡線

### 5.1 幾何

雷入水之後是**定深等速直線**，航向 = 入水速度的水平分量
（`world/torpedo.ts` 的 `stepAir`）。而 `ai/torpedoRun.ts` 已經證過：

> `stepBomb` 的阻力與速度反向、重力只動垂直分量，所以水平兩軸恆等比例
> 縮放 —— **方向在整個空中段守恆**。

所以航向可以直接由**當下的**速度算，不必等入水：

```
  hl  = hypot(vx, vz)
  dir = hl > 1e-9 ? (vx/hl, vz/hl) : 機首水平方向
  E   = BOMB_POINT                    solveImpact 已經解出來的入水點
  P_k = E + dir · (k · 500)           k = 0…4，P_4 是 2,000 m 的射程末端
```

`E` 就是落點圈的圓心。**圈是線的起點**，兩者自然組成一組。

**退化的門檻是 `hl > 1e-9` 才正規化，否則走機首** —— 逐字照 `stepAir`
（`world/torpedo.ts:306` 是 `if (hl > 1e-9)`，所以 `hl === 1e-9` 那一點是
**走機首**）。寫成 `hl < 1e-9 才退化` 的話等號那一點的行為就反了，而
`torpedoHeading` 會被 `stepAir` 呼叫 —— **那是改到模擬**。

### 5.2 畫的是散佈之前的**名義**中心線，不是那一枚的實際航跡

`World.dropTorpedo` 在投放時先改速度（`World.ts:788` 的 `spreadDirection`），
真雷的入水點與水中航向都是**散佈之後**的。線畫**散佈之前**的那一條，與落點
圈完全一致 —— 理由逐字沿用 `World.ts:785-787`：

> 把散佈也套進瞄具的話，散佈就變成免費的情報，等於沒有散佈。

**所以這條線是名義中心線，本文件不宣稱它與飛出去的那一枚同向。**
`torpedo-vs-ship.test.ts` 已經證過實際入水點必定偏離中心；垂直退化時散佈
甚至會生出水平速度，讓真雷不走機首備援而 HUD 走。這是**已知且刻意**的差異，
與落點圈的既有行為同一條。護欄因此只能斷言「HUD 的航向 = 未散佈速度的水平
分量」，**不得**斷言「與真雷逐位元相同」（見 §8.2）。

共用 `torpedoHeading` 買到的是「退化分支只有一份」，不是「與真雷同向」。

### 5.3 平面投影是精確的，不是近似

透視投影把直線映成直線（射影變換）。**投影兩個端點再連直線，就是那條 3D
線在畫面上的真實樣子** —— 不需要細分、不需要逐點投影。刻度點各自投影，
一樣精確。

### 5.4 端點跑到相機後面：唯一要自己擋的一件事

**畫到螢幕邊緣就停是免費的。** canvas 的 `moveTo` / `lineTo` 本來就只點陣
化畫布之內的部分，座標丟到界外它自己停在邊緣。落在畫面外的刻度直接不出現。
**不需要寫矩形裁剪。**

**但螢幕邊緣救不了相機後面的點。** `w ≤ 0` 的點投影出來是**穿過中心鏡射**
的：它不會跑到無限遠讓你發現，它會落在畫面上、方向剛好相反，canvas 再乾乾
淨淨地把它裁到邊緣。得到的是一條線條漂亮、方向錯 180° 的瞄準線。

**這正是不會報錯的那一種**，所以必須擋。

判準沿用這個 HUD 已經在用的那一條 —— `bombVisible` 與 `noseVisible` 都是
`project()` 之後看 `z < 1`（`main.ts:1718`）。**不新增一套視空間的近平面
裁剪**：

```
  逐點投影，front_k = (P_k.z < 1)
  畫「從 P_0 起連續為 front 的那一段」，遇到第一個非 front 就停
  P_0 自己不是 front → 整條不畫
```

**已知的近似**：線停在最後一個 front 取樣點，而不是精確停在近平面上，
誤差最多 500 m。它只在「入水點在前方、而 2 km 外的末端繞到身後」時出現 ——
那是大坡度機動中的幾何，那時候不在瞄準。**不值得為它寫一套線段裁剪。**

### 5.5 這條路徑在實戰幾何裡幾乎不會走到

包絡把玩家壓在 20…200 m 而且接近平飛。150 m 高、投彈模式下鏡頭盯著約
500 m 外的入水點（俯角 16.7°）。**2,000 m 是水中航程，離飛機是入水點再加
2,000 m**：

```
  入水點      離機   500 m   俯角 16.7°   畫面中心
  末端刻度    離機 2,500 m   俯角  3.4°   中心上方 13.3°
  垂直 FOV       65°                    半視角 32.5°
```

**射程上限那一格會在該看到的時候看得到**，正因為包絡逼你飛低飛平。

### 5.6 樣子

- 線寬與落點圈相同（`1 * L.scale`）。
- 顏色與圈相同，走 `bombsightColor(style, releaseOk)` —— 綠 = 這一幀投得
  出去。**兩者不得各判一次。**
- 刻度是垂直於線的短橫。中間三格短，**末端那一格長一截**，讀得出是「線到
  這裡為止」。
- **末端加一個 `2000` 的字**，其餘刻度不加字。玩家要自己估提前量就得知道
  一格是多少，但四個數字疊在低空畫面上是噪音 —— 給一個錨點就夠。

長度、字級是起始值，由試飛裁定。

### 5.7 什麼時候畫

```
  bombing === true            投彈模式（負責人裁決：一般飛行不畫）
  ordnance === 'torpedo'
  bombState === 'solved'
  入水點真的是水              見下面【落點是陸地就整條不畫】
  P_0 是 front
```

全部成立才畫。`bombVisible` **不進判準** —— 那一格額外要求圈在畫面內，而線
的起點滑出畫面時線本身還有一大段在畫面裡。

**【落點是陸地就整條不畫】`bombState === 'solved'` 不代表落在水上。**
`solveImpact` 撞到**任何**地面都回成功（它吃的是 `world.groundAt`），而真雷
在 `world/torpedo.ts:296` 遇到陸地或無水是**立刻結束**（`kind = 0` 撞岸），
根本沒有水中段。少了這一條，飛過島嶼或內陸農地時 HUD 會畫出一條不存在的
2 km 水中航跡 —— 而海上的 e2e 截圖抓不到它。

判準**逐字沿用 `stepAir` 的那一條**（`torpedo.ts:296`）：

```
  groundAt(E.x, E.z) > 0 || !Number.isFinite(waterAt(E.x, E.z))   →  不畫
```

`main.ts` 兩支都拿得到（`terrain.collisionHeightAt` 與 `terrain.waterAt`，
`main.ts:996-997` 就是把它們接到 `world` 上的）。**不得改用含浪的高度或
寫成 `> 雷體高度`** —— 那正是 `2026-09-06-aerial-torpedo` 那一輪列為全域
限制的兩個寫法。

## 6. 投放閘門

### 6.1 位置與二擇一

`hud/widgets/bombBay.ts` 現在在格子上方 `y − LABEL_RISE` 處畫「裝填中 12s」。
閘門畫在**同一個 baseline**、同樣置中。

```
  bombReloading === true   →  裝填中 12s
  否則                     →  閘門
```

### 6.2 顯示條件

```
  bombCapable && bombBayCapacity > 0 && ordnance === 'torpedo' && !bombReloading
```

**與彈艙格子一樣，不限投彈模式。** 它是儀表 —— 進場的姿態要在切投彈模式
**之前**就先擺好，只在投彈模式顯示的話它出現得太晚。理由與 `bombBay.ts`
自己的「釘在畫面下方而不是跟著準星走」逐字相同。

### 6.3 內容：顯示值，不是燈號

```
        坡度 18°    俯仰 −2°    高度 240 m
         紅           綠           紅
```

- `坡度` = `|roll|` 的度數，整數
- `俯仰` = `pitch` 的度數，帶正負號，整數
- `高度` = `releaseAgl` 的公尺數，整數

標籤與數值同色：過 `HUD_COLORS.primary`，不過 `HUD_COLORS.danger`。

**為什麼是數值不是燈號**：這個包絡緊（12°／±6°），「高度 240 m」告訴你要
下降多少、往哪個方向收斂；一個紅點只告訴你不行。值本身就是操作指令。

### 6.4 三格各自過不過由純函數答

`releaseGateColor(ok: boolean): string` 住在 widget 裡，三格的判定直接呼叫
§4.3 的 `rollOk` / `pitchOk` / `aglOk`。

**widget 不得自己寫 `Math.abs(roll) <= 12 * DEG`。**

## 7. 高度錶的可投高度弧

### 7.1 盤面

`hud/widgets/dials.ts` 的 `drawAltimeter` 是雙針：長針一圈 1,000 m、短針一圈
10,000 m。

20…200 m 對到長針的 **7.2°…72°**，佔盤面 18% —— 是一段讀得出來的弧。
弧畫在**長針那一圈**上。

`needle` / `tick` 的角度慣例是 **0 指 12 點、順時針為正**；canvas 的
`arc()` 是 0 指 3 點。**差 90°，而這個換算是整段最容易錯又最不會被抓到的
一行**：把 needle 慣例的 7.2°…72° 直接餵進 `ctx.arc()`，弧會從 12–2 點跑到
3–5 點，而 §8.5 的每一條純函數測試都還是綠的。

所以換算本身要被護欄看到 —— 見 §8.5：測的是 `ctx.arc()` **實際收到的引數**，
不是 `releaseBandArc` 的回傳值。

### 7.2 範圍是算的，不是寫死的

```
  ground = altitude − releaseAgl        地面高（海上是 0）
  lo     = ground + env.minAgl
  hi     = ground + env.maxAgl
  角度   = (lo / 1000 mod 1) · 360°  →  (hi / 1000 mod 1) · 360°
```

`env` 是 §4.2 那一格，所以包絡日後怎麼改、變不變成逐機的，這裡都不用動。

用 `altitude − releaseAgl` 反推地面高，弧才會畫在正確的海拔刻度上 —— 錶讀
的是海拔，帶是離地，飛過島上空不補這一項就錯位。

### 7.3 兩個退化情形

長針每 1,000 m 繞一圈，所以 1,020…1,200 m 時針也會落在弧裡 —— 玩家高了
十倍而錶面在說可以投。

```
  altitude 不在弧所屬的那一圈    →  不畫弧
  弧跨過 1,000 m 的整數邊界      →  不畫弧
```

第二條只有地面高在 800 m 以上時才成立，而魚雷是在海上投的；不畫比畫一段
繞回來的弧好。

### 7.4 顏色

`HUD_COLORS.primary` 就是綠（`#7dfba8`）—— **不新增顏色**。弧用 `dim`
或 `primary`，粗細與半徑是起始值，由試飛裁定；半徑要避開刻度（`r*0.78`
到 `r*0.94`）與刻度數字（`r*0.62`）。

### 7.5 什麼時候畫

```
  ordnance === 'torpedo' && releaseEnv !== null
```

與閘門同一條 —— 炸彈不畫（§3）。

## 8. 護欄

### 8.1 `canRelease` 是三支述詞的合取

掃一格網格（roll、pitch、agl 各取邊界內外若干點），逐點斷言

```
  canRelease(env, roll, pitch, agl, tas)
    === rollOk(env, roll) && pitchOk(env, pitch) && aglOk(env, agl) && tasOk
```

**這一條就是 §4 的整個症狀的守門員。** 變異測試：`rollOk` 的 `<=` 改成
`<` 之後必須紅。

既有的 **`test/unit/release-envelope.test.ts`**（15 條）一條都不能改、一條都
不能少 —— `canRelease` 是改寫不是改行為。

（`test/unit/envelope.test.ts` 是**飛行**包絡，與這一輪無關 —— 兩支同名的
理由見 `weapons/releaseEnvelope.ts` 檔頭。）

### 8.2 航跡線的取樣點

純函數，headless 可測：

- 取樣距離恰好是 `0, 500, 1000, 1500, TORPEDO_RANGE`，**最後一點精確落在
  射程上**（不是 `2000` 這個字面值，是 `TORPEDO_RANGE`）
- 航向：`hl > 1e-9` 時正規化，否則走機首。**`hl === 1e-9` 那一點要有一條
  測試**（§5.1：等號那一點走機首）—— 少了它，`>` 與 `>=` 的變異殺不掉，
  而 `stepAir` 也呼叫這一支，改錯就是改到模擬
- `Torpedoes.step` 的既有彈道斷言在重構前後**逐位元不變**

**不得斷言「HUD 的線與飛出去的那一枚同向」** —— 散佈在 HUD 這一側之外
（§5.2）。要斷言的是「HUD 的航向 = 未散佈速度的水平分量」。

### 8.3 相機後面的那一段

純函數 `runFrontCount(z: readonly number[]): number` —— 回傳「從 0 起連續
`z < 1` 的點數」。

- 全部 front → 5
- `z[0] >= 1` → 0
- 中間有一個非 front → 停在它之前
- **後面又變回 front 不得復活**（這一條是鏡射線的守門員）

變異測試：把 `>= 1` 改成 `> 1` 之後邊界那一條必須紅。

### 8.4 閘門要驗**畫出來的東西**，不只驗兩支純函數

只驗 `releaseGateVisible` 與 `releaseGateColor` 的話，下面每一種寫錯都全綠：

```
  坡度與俯仰兩格對調
  高度那一格讀 HudFrame.altitude 而不是 releaseAgl
  在繪圖函數裡重抄一份 12° 的比較
  裝填中的時候把閘門也一起畫上去
```

**用測試用的假 canvas context 直接呼叫 `drawBombBay`**，斷言：

- 三段文字的**內容與順序**（坡度／俯仰／高度）
- 三段各自的**顏色**，且各自只受自己那一軸影響 —— 只把 `pitch` 推出界時，
  只有「俯仰」那一格轉紅
- **高度那一格的值跟著 `releaseAgl` 走**：固定 `altitude`、只動 `releaseAgl`，
  文字要跟著變
- **門檻跟著 `releaseEnv` 走**：換一組包絡，同一組姿態的紅綠要跟著翻
- `bombReloading` 為真時**畫得出「裝填中」而且完全沒有閘門的三段文字**
- 掛炸彈 → 兩者都不畫（`bombReloading` 為真時仍畫「裝填中」，那是既有行為，
  不得回歸）

`test/unit/hud.test.ts` 已經有這種記錄式 context 的用法（比對
`texts.map(t => t.color)` 與 `t.text`）—— **沿用它，不要為了可測性在
production 端新增抽象。**

### 8.5 高度弧的可見性

純函數，回 `null` 或 `{ from, to }`（rad，`needle` 的慣例）：

- 海上（ground = 0）、`altitude` 在 0…1,000 → 回 7.2°…72° 的弧
- `altitude` 1,020 → 回 `null`（§7.3 第一條）
- ground = 900（弧跨 1,000 m 邊界）→ 回 `null`（§7.3 第二條）
- ground = 300、altitude 400 → 弧是 320…500 m 對應的角度（**證明它跟著地形
  走，不是寫死 20…200**）
- `env` 換一組值 → 弧跟著變（**證明沒有寫死**）

**再加一條看畫出來的**：用假 context 呼叫 `drawDials`，捕捉 `ctx.arc()`
**實際收到的起訖角**，斷言它等於 `releaseBandArc` 的值**減 90°**。少了這一條，
§7.1 那個 needle→canvas 的換算漏掉時上面每一條都還是綠的，而弧會整段轉到
盤面的另一側。

### 8.6 `HudFrame` 的新陣列

`hud.test.ts` 既有的「初始值不含 NaN」是
`for (const v of Object.values(f)) if (typeof v === 'number')` ——
**`Float64Array` 是物件，整個被跳過**。長度少一格或元素是 NaN 都不會紅，
而 typed array 越界寫入不拋例外，症狀是末段航跡與末端刻度**靜靜地消失**。

所以要明寫：

- `runX.length === runY.length === TORPEDO_RUN_SAMPLES`
- 兩條陣列的**每一個元素**都是有限值

### 8.7 逐位元護欄不得移動

這一輪不碰模擬。`spawn-baseline` 那一組校驗和、`rematch.test.ts`、
`perf-gate.test.ts` 全部不得變 —— 變了就是誤動了模擬。

## 9. 效能

HUD 每幀畫一次（60 Hz），不是 240 Hz 的熱路徑，但

- 五個取樣點的投影用**預先配置的暫存向量**，不得每幀 `new Vector3()`
  —— `main.ts` 的 `BOMB_NDC` 已經是這個做法，照抄
- `HudFrame` 上的取樣點用**固定長度的預先配置陣列** + 一個計數，
  與 `contacts` / `markers` 逐字同一個做法
- **投影出來的 z 也要有一條預先配置的緩衝（`RUN_Z`）。** `runFrontCount`
  要一次看完五個 z 才判得出「從 0 起連續在前面幾個」，而 `HudFrame` 上
  只有 `runX` / `runY`。沒有這一格的話，實作只剩兩條路：每幀生一個陣列
  （違反這一節），或在 `main.ts` 裡另寫一份判斷 —— 那會讓 §8.3 那支測過的
  純函數變成**沒有人呼叫的死護欄**。
  `runFrontCount` 因此收 `ArrayLike<number>` 加一個長度，不收 `number[]`。
- 閘門三格的字串每幀重組是可接受的（既有的「裝填中 12s」已經如此）

## 10. 開放項

- 刻度間隔 500 m、末端標 `2000`、閘門的字級與三格間距、弧的粗細與半徑
  —— 全部是**起始值，由試飛裁定**。
- 包絡的姿態上界由負責人在試飛中放寬到 **45°／±60°**（高度 20…200 m 不動）
  —— 理由是玩起來投得出去。`release-envelope.test.ts` 的斷言本來就寫成相對
  `TORPEDO_ENVELOPE.maxRoll`，所以一條都沒動；只有 HUD 閘門的測試原本拿
  `30°` 當「出界」而被吃掉，已改成同樣相對包絡寫。
- **AI 與玩家共用這一條包絡**（`ai/torpedoRun.ts` 的 `established()` 直接
  呼叫 `canRelease`），所以放寬也讓 AI 的雷擊更積極。那是刻意的：分家會
  出現「AI 投得出玩家投不出的雷」。
