# 破防的能量讓位 —— 讓閃躲動作本身帶能量管理

2026-08-13。專案負責人核可的設計,尚未實作。

---

## 1. 問題

AI 的高度**單向漂**:20v20、開局 2000 m、420 秒,高度中位是

```
 59s 2567　119s 3520　179s 3931　239s 4088　299s 4193　359s 4467　419s 4823
```

**七格全部單調上升,一次都沒有回落。** 開局 4000 m 的那一場漂到 5245 就卡住。

這件事會回頭放大另一個症狀。角落速度隨高度上升:

```
3000 m 426　4000 m 448　5000 m 473　6000 m 500　7000 m 528 km/h
```

而 `cornerRatio = TAS ÷ 角落速度` 是幾乎所有 AI 能量判準的分母。**飛得越高,同樣的空速越會被判定「沒能量」。** 實測:爬高 570 m,`extend`(放棄追擊去補能量)的佔時就由 20.3% 翻倍到 46.8%。

專案負責人回報的兩件事 ——「AI 很常放棄追擊」與「很常在 5000 m 以下就拉到 6000」—— 是同一個迴圈的兩端。

### 1.1 根因:只上不下的棘輪

高度歸戶(`climb-blame.probe.ts`,開局 2000 m、420 秒、全隊淨高度變化):

| 意圖 | 淨爬升 | 佔比 | 每秒 |
|---|---|---|---|
| approach | +31.5 km | 27% | 6.0 m/s |
| engage | +31.2 km | 27% | 17.9 m/s |
| extend | +28.7 km | 24% | 4.2 m/s |
| **defend** | **+27.6 km** | **23%** | 12.8 m/s |
| merge / rally | −1.2 km | — | 負 |

**每一種意圖都在爬。** 垂直旋鈕(高 yo-yo)94% 是中性的,不是它。

往上是拉桿轉彎的自然結果,**隨時做得到**;往下需要幾秒不被打擾,而一段 `extend` 中位只有 3.6 秒、56~58% 被 `defend` 插隊終止(`extend-payoff.probe.ts`)。換能量的兩個方向一個通一個塞。

### 1.2 為什麼先動 `defend`

`defend` 只佔爬升的 23%,**但它的爬升是唯一被「命令」出來的**。

`defendAim` 產生一個垂直於威脅視線的水平軸,再**固定往上抬 `defendTilt` = 20°**。其他三個意圖是拉桿轉彎的副產品。

而那 20° 是 2026-08-07 掃出來的,**當初的判準就是高度**(800 m 尾追、90 秒):

| 抬角 | 打得中 | 最低高度 |
|---|---|---|
| 0° | 2.0% | 2287(掉 1713 m) |
| **20°** | 2.4% | **4000(不掉)** |
| 40° | 8.3% | 4000 |

選 20° 是為了**止跌**。注意 0° 的「打得中」(2.0%)其實比 20°(2.4%)還低 —— **壓低抬角不會讓對方比較容易打中**,當初純粹是為了不掉高度。

**所以這不是漏做,是一個為單一場景校準的常數,在 20v20 裡過頭了。** 同一個固定抬角,在那個場景是「止跌」,在混戰裡變成「一路爬」。

### 1.3 已排除的做法

| 做過 | 結果 |
|---|---|
| 調 `extend` 的進出門檻(`cornerEnter`/`cornerExit`) | 安全層佔時衝到 65.6%(上限 5%),否決 |
| 換 `cornerRatio` 的分母(`manoeuvreGFraction`) | 指揮層一張命令都發不出來 + AI 撞海,否決 |
| 拆「速度過剩→爬升」的增益(`pitchSurplusGain`) | 關到 0 都沒差,完全無效,參數已收回 |
| 給 `extend` 保護期(禁止 `defend` 插隊) | **專案負責人否決** ——「被打就該閃」 |

前三次的共同錯誤:**一直在調「命令」,但問題在「執行」**。命令都是對的,飛機做不完。

## 2. 設計

### 2.1 機制

新增純函數:

```ts
/** 破防時的能量讓位偏置，rad。**恆 ≤ 0**（只壓不抬） */
export function defendPitchBias(cornerRatio: number, cfg: SteerConfig): number
```

```
bias = −defendEnergyGain × max(0, 1 − cornerRatio)
夾在 [−defendEnergyLimit, 0]
```

三個設計決定,各自有理由:

**一、恆 ≤ 0(只壓不抬)。**

系統已經只上不下,任何新機制都不該再加「上」。`cornerRatio ≥ 1` 時回傳 **0** —— `defendTilt` 的 20° 原封不動,速度充足時的閃躲行為完全不變。

`max(0, …)` 這個夾制是**必要的**,不是防禦性程式:少了它,`cornerRatio > 1` 時偏置會變正,等於再疊一份爬升 —— 那正是 `pitchSurplusGain` 那一輪證實沒有用、而且方向錯誤的東西。

**二、`defendEnergyGain` 的錨:脫離門檻。**

起始值取「`cornerRatio` 掉到 `DEFAULT_RULES.cornerEnter`(0.75,也就是該撤退的那條線)時,偏置剛好 −`defendTilt`(−20°),把防禦抬角**抵銷成平飛**」。

```
gain = defendTilt / (1 − cornerEnter) = 20° / 0.25 = 80°
```

這個錨讓兩層的交界有語意:**還撐得住就照原本閃,撐到該撤退了就先別再往上爬,再低才真的變成俯衝。** 定值由 §3 的掃描回填,這只是起始值。

**三、走既有的 `applyPitchBias`,不動 `defendAim`。**

`defendAim` 產生的幾何軸一個字不動 —— 2026-08-07 那張 `defendTilt` 掃描表因此繼續有效。

`applyPitchBias` 保證**世界水平方位不變**,所以閃躲的**方向**完全不受影響,只改航跡角。這與甜蜜區(`sweetSpotPitch`)是同一個手法、同一個函數。

`intent === 'defend'` 時把 `defendPitchBias` 的結果**加進既有那一次 `applyPitchBias` 呼叫**(與 `sit.sweetPitch` 相加),不新增第二次旋轉 —— 兩次旋轉會有次序相依,而且各自夾制會讓合成結果難以推理。

### 2.2 順序與既有各層的關係

`steerCommand` 的後處理順序不變:

```
意圖分支（defendAim，含 defendTilt 20°）
  ↓
shrinkTowardNose（拉桿紀律，方位不動）
  ↓
applyPitchBias（甜蜜區 + **本次新增的破防能量讓位**）
  ↓
applyFloor（離地底限，只抬不壓，離地 ≥ clearanceScale 時嚴格為 0）
```

**離地底限排在最後,所以它對本層有最後決定權。** 「我沒速度想壓機頭」不會贏過「快撞海了」—— 這是既有的位階,不必新增規則。

### 2.3 恆等基準

`defendEnergyGain = 0` → `defendPitchBias` 恆回傳 0 → **逐位元等於現況**。

這一點是硬要求,不是方便。本輪已經兩次靠恆等基準才驗得出「重構沒有偷偷改到別的東西」(`manoeuvreGFraction`、`pitchSurplusGain`)。

## 3. 判準與量測

### 3.1 主判準:高度不再單向漂

場景:20v20、`battleConfigFrom(DEFAULT_SKIRMISH)`(**VETERAN**,玩家實際玩到的配置,不是護欄用的 `ACE`)、420 秒。

**兩個開局**(誤差棒。種子不進物理路徑,只用來取飛行員名字,所以改種子得不到獨立樣本):

- `2000 m / 200 m/s` —— 低開局,「往上飄」的訊號最大,**主場景**
- `4000 m / 200 m/s` —— 出貨開局

| 量 | 基準（2000 開局） | 基準（4000 開局） | 要求 |
|---|---|---|---|
| 結束高度 − 開局高度 | **+2823 m** | **+1245 m** | 見下方門檻 |
| 高度中位的**最大回落** | **0 m** | **0 m** | **> 0**（兩個開局都要） |

基準數字取自 `altitude-drift.probe.ts`（t=419 s 的高度中位:2000 開局 4823 m、4000 開局 5245 m）。`surplus-gain.probe.ts` 用「最後 60 秒的中位」量同一件事,給 4854 / 5247 —— 兩者差 31 / 2 m,遠小於 393 m 的開局間雜訊,但**新的探針必須明講用哪一個定義**,不可混用。

第二個才是「單向」的直接判準。只看第一個會被「爬得慢一點但仍然只上不下」騙過去。

**「最大回落」的定義**:每 60 秒取一次全隊存活者的高度中位,取相鄰兩點差值中最負的那一個的絕對值;全程單調上升時為 0。

**第一個量的門檻在任務 0 之後才訂**,不在這裡拍板。理由是雜訊底線已知但改動的量級未知:同一組設定下兩個開局的結束高度差 **393 m**,所以任何小於 393 m 的改善都不算數。任務 0 的消融會給出「這根槓桿最多能推多少」,門檻取它的一個保守比例,寫進計畫。

### 3.2 副判準（只報,不當紅綠）

`extend` 佔時、`engage` 佔時、傷害、存活數。

**它們不設門檻。** 若高度降下來而它們沒動,那就證明 §1 的「高度 → 角落速度 → `extend`」因果鏈是錯的 —— **那個資訊本身就是這次要買的東西**,而只有把它們放在副判準的位置才問得出來。

### 3.3 否決條件（任一成立就退回）

- `ai-manoeuvre` 的 `safetyShare` 或 `belowStall` 上升(前兩次失敗都栽在這裡)
- `ai-defence`、`ai-visible-evasion` 由綠轉紅
- 全套出現新的紅燈

護欄若只是**數值移動而未破門檻**,照專案紀律列表交專案負責人裁定,不自行重新定值。

### 3.4 一條寫死的紀律:觀察窗 ≥ 120 秒

`steer.ts` 記載的既有教訓:

> 受控場景的 30 秒觀察窗**看不到高度問題**。它是為「反應快不快、挨不挨打」設計的,那兩件事在 30 秒內就定案;「會不會把自己飛到地上」則需要 120 秒以上。日後任何動到 `defend` 的改動,都要在拉長的窗上再看一次。

本次所有新增量測一律 ≥ 120 秒。

## 4. 任務順序

**第一個任務是消融,不是實作。**

| # | 任務 | 產出 |
|---|---|---|
| **0** | **止損閘門**:把現有 `defendTilt` 直接掃 `20° / 10° / 0° / −10°`,量 §3.1 的兩個高度指標 | 有反應 → 繼續;沒反應 → **當場結案** |
| 1 | `defendPitchBias` 純函數 + 單元測試(含 `gain = 0` 恆回傳 0、`cornerRatio ≥ 1` 回傳 0、連續性) | 純函數 |
| 2 | 接進 `steerCommand`,`gain` 出貨值先設 **0**,跑全套確認**逐位元恆等** | 接線 |
| 3 | 掃描 `defendEnergyGain` 與 `defendEnergyLimit`,含**低開局**(見 §5 風險三) | 定值 |
| 4 | 全套回歸 + 護欄逐條比較,交專案負責人裁定 | 報告 |

任務 0 **不寫任何新程式,也不改任何出貨值** —— `defendTilt` 已經是 `SteerConfig` 的欄位,探針在跑之前改它、跑完還原(與 `extend-threshold.probe.ts` 同一個手法)。這與 §2.1「不動 `defendAim` 的幾何軸」不衝突:任務 0 是**量測**,不是改動。

止損閘門的理由:`pitchSurplusGain` 那一輪蓋完整套才發現「關到底都沒差」,白燒一輪。這次先問「這根槓桿接得上嗎」。

## 5. 已知風險

**一、`defend` 這條路徑很敏感。** 動過三次都被否決(破防力道連續化、異平面破防、反轉),其中異平面那次讓 AI 在 1000 m 開局下**整場 72.9% 被撞地護欄接管**。

**二、天花板是四分之一。** 就算完全成功,approach / engage / extend 那三份爬升(77%)還在。主判準會改善但不會歸零 —— **這不是失敗判準**,§3.1 的門檻要照這個現實訂。

**三、壓機頭在低空是危險的,而那個組合沒被測過。** `applyFloor` 在離地 500 m 以下會把航跡角抬回來,理論上守得住 —— 但那一層從來沒有在「破防 + 低空 + 低速」三者同時成立時被壓力測試過。任務 3 的掃描必須含低開局。

## 6. 明確不做

- **不動優先序。** 不給 `extend` 保護期、不限制 `defend` 插隊 —— 專案負責人裁定「被打就該閃」。
- **不動 `defendAim` 的幾何軸。** 保住 2026-08-07 的掃描表。
- **不給 AI 一個偏好高度。** 那是硬把症狀壓住,飄上去的機制還在。
- **不修 approach / engage / extend 的爬升。** 那是另外三份,本次只做 `defend`。

## 7. 實作結果(2026-08-15):**否決**

出貨值維持 `defendEnergyGain = 0`。機制、旗標與九條單元測試保留 —— 否決的是**定值**,不是這條路的存在。

### 7.1 Task 0:止損閘門 —— 通過

`defendTilt` 由 20° 掃到 −10°(20v20、420 秒、VETERAN、兩個開局):

| 抬角 | 2000 開局 | 回落 | 4000 開局 | 回落 |
|---|---|---|---|---|
| 20°(出貨) | 4823 m | 151 | 5245 m | 531 |
| 10° | 4147 m | 243 | **5652 m** | 262 |
| 0° | 3889 m | 299 | 4740 m | 672 |
| −10° | 3644 m | 346 | 4464 m | 1053 |

三條判準逐條判定:

- **方向** —— 端點方向正確,兩個開局都降。**但 4000 開局的 10° 那一點非單調**(比 20° 高 407 m,僅超出 393 m 雜訊底線 14 m)。專案負責人裁定為雜訊。
- **一致性** —— 通過,兩個開局同向。
- **效果量** —— 通過,端點差 1179 m 與 781 m,遠超雜訊。回落亦同向變大。

地板佔時全程 0.00%、安全層 0.11~0.44% —— 這一輪的高度差異與那兩層無關,量測乾淨。

### 7.2 Task 3:掃描 —— 主判準達成

高空(每欄與同開局的 `0.0×錨` 比):

| 增益 | 結束高度 2000／4000 | 回落 2000／4000 |
|---|---|---|
| 0.0×(基準) | 4823 ／ 5245 | 151 ／ 531 |
| 0.5× | 4132 ／ **5721 ↑** | 315 ／ **414 ↓** |
| 1.0× | 4152 ／ 4991 | 213 ／ 605 |
| 1.5× | 3898 ／ **5251 ＝** | 276 ／ **422 ↓** |
| 2.0× | 4007 ／ 4773 | 283 ／ 774 |

**只有 2.0× 的兩個開局各自都超過 393 m 雜訊底線**(−816、−472),回落亦兩邊同向變大。§3.1 的主判準達成。

低空(1000 m / 600 m 開局)四項安全指標全部沒有惡化,安全層佔時反而由 0.35% 降到 0.13%。

### 7.3 Task 4:護欄 —— **否決**

| | 2.0× | 1.0× | 門檻 |
|---|---|---|---|
| `ai-reaction-delay` 低空飛進海裡 | **13292** | 0 | = 0 |
| `ai-visible-evasion` 墜海場次 | 紅 | **1 場** | 0 場 |
| `ai-defence` 正後方 250 m | **0.96** | **0.887** | < 0.85 |
| `ai-defence` 後下方 400 m | **0.87** | 綠 | < 0.85 |
| `ai-targeting` 產出 | **1.30** | **1.40** | ≥ 1.5 |
| `ai-withdraw-anchor` 半徑 | **5839** | 綠 | ≤ 3574 |

§3.3 把「`ai-defence` 轉紅」列為否決條件。它在**兩個劑量**都轉紅。

**這不是劑量問題。** `ai-defence` 的場景在 **4000 m**(`ALT`),地面遠在天邊 —— 也就是說**壓機頭讓閃躲變差,與低空無關**。原本設想的退路「加一道離地餘裕的閘門」(比照 `extendPitchAngle`)因此救不了它。

**兩端都不通:** 更小的劑量連效果都沒有(0.5× 讓 4000 開局爬更高、1.5× 等於沒動),有效果的劑量會踩護欄。

**結論:這一層在用閃躲品質換能量,而閃躲正是 `defend` 存在的理由。**

### 7.4 副判準:因果鏈被否證

原本的推論是「高度降 → 角落速度降 → `extend` 減少 → `engage` 增加」。

兩輪獨立量測(Task 0 消融、Task 3 掃描)都**不支持**:2.0× 讓平均高度降了 644 m,而 `extend` 佔時在 2000 開局降(40.6→34.8%)、在 4000 開局**反而升**(37.1→40.9%)。

**「AI 常放棄追擊去補能量」不是飛太高造成的。** 這是本輪買到最有價值的資訊 —— 它把下一輪的方向從「治高度」轉開。

### 7.5 方法上的教訓

**自訂量測不能取代護欄。**

本輪的低空壓力測試(600 m / 1000 m 開局)四項全過、安全層甚至下降,但看窗中位序列就知道 **AI 一分鐘內就爬到 3000 m 以上、整場平均 4312 m** —— 它根本沒待在低空,所以量不到低空的危險。真正把飛機按在低空打的是 `ai-reaction-delay`,它一跑就抓到 13292。

這是本專案第三次「自訂量測全過、護欄一跑就死」:

| 輪次 | 自訂量測 | 護欄實際抓到 |
|---|---|---|
| `cornerEnter` 放寬 | `belowStall` 漂亮 | 安全層佔時 87% |
| `manoeuvreGFraction` | 傷害 +69% | 低空飛進海裡 0 → 5566;而那個 +69% 本身是指揮層被關掉的假象 |
| 本輪 | 低空四項全過 | 低空飛進海裡 0 → 13292 |

### 7.6 全套回歸

出貨值收回 0 之後:**4 條紅,與基準逐條相同**(`ai-command-channel` 編隊收攏、`ai-command-channel` 命令佔時、`ai-command-tactics` 側翼方位角、`ai-withdraw-anchor` 半徑),2490 綠。`perf-gate` 在全套並行下假紅,單獨跑 4/4 綠。

**沒有護欄移動需要裁定** —— 出貨值是 0,行為與本輪之前逐位元相同。

### 7.7 若要重啟這條路

否決的是「在**閃躲動作**上壓機頭」。仍未嘗試的方向:

- 只在**脫離**動作上壓,不動閃躲本身(需要先定義「脫離」與 `defend` 的分界)
- 直接重掃 `defendTilt`(那會作廢 2026-08-07 的掃描表,要重做那一輪)
- 承認 `defend` 的爬升是必要代價,改去治另外 77%(approach / engage / extend)

`defendEnergyGain` / `defendEnergyLimit` 兩個欄位、`defendPitchBias` 與 `defendTilted` 旗標、以及十六條單元測試都留著 —— 重啟時是現成的。
