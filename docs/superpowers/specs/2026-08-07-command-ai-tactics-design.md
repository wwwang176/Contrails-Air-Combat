# 指揮 AI 第二份：戰術庫（側翼與集火）

**日期**：2026-08-07
**前置**：`2026-08-07-command-ai-orders-design.md`（第一份，已實作並驗收）。
指令通道、集合點、命令生命週期、戰機端的兩行覆寫都已經在線上。

---

## 1. 範圍

### 1.1 只做兩個戰術，不是四個

第一份的 §1.1 把戰術庫列成四個：側翼、慢速脫離、火力壓制、集火。實作完
第一份之後回頭看，這四個**對戰場的作用方向相反**：

| 戰術 | 作用 | 這一份 |
|---|---|---|
| 側翼 | **增加**輸出 —— 小隊還在打，只是換角度 | **做** |
| 集火 | **增加**輸出 —— 同一個目標被多架咬 | **做** |
| 慢速脫離 | **減少**交戰 —— 又一種撤離 | 不做 |
| 火力壓制 | **減少**輸出（明確「不求擊落」） | 不做 |

**排除後兩個的理由不是懶，是各自有具體的問題：**

**慢速脫離幾乎已經做完了。** 第一份的那條規則就是「集合點放到戰鬥範圍
外」。差別只在觸發條件（能量見底 vs 別的理由），不在機制 —— 它屬於第三份
（什麼時候該下哪一個），不屬於戰術庫。

**火力壓制目前沒有受益者。** 它在史實裡的用途是「把敵人壓在守勢，好讓別人
去打轟炸機」。這個專案的護航／攔截任務在 `src/ui/missions.ts` 裡**全是資料、
全部停用**。沒有要保護的對象時，「維持接觸、不求擊落」量得出來（敵人待在
`defend` 的時間）但**沒有目的** —— 那是一個為了自己而存在的戰術。等任務模式
上線再做，屆時它的驗收判準才有意義（被護送的單位活下來了嗎）。

**而且後兩個都會撞到第一份那條只剩 4.6% 餘裕的傷害護欄**（第一份 §9.4）。
在同一份 spec 裡同時動機制與動護欄，出事時分不出是哪一個的錯。

### 1.2 本份不做的

慢速脫離、火力壓制（見上）；**指揮決策的多樣化**（第三份 —— 見 §2）；
玩家收命令與 HUD 呈現；跨小隊協同（例如「A 隊側翼、B 隊正面」的配合）；
非戰鬥機單位。

## 2. 最重要的一條紀律：驗收與觸發分開

第一份 §1.1 寫過三份分開的理由：

> 混在一起的話，「第三份挑錯戰術」與「第二份戰術寫壞」在數據上分不出來，
> 而兩者的修法完全不同。

但**沒有觸發條件，兩個新戰術就一次都不會發生，驗收全部空洞地通過。**
而只要開始寫「什麼時候該側翼」，第三份就跑進來了。

裁定（專案負責人 2026-08-07）：**強制注入驗收 + 一條最笨的預設觸發。**

- **驗收全部用「把戰術直接塞給分隊」跑。** 量的是「這個戰術執行得對不對」，
  與「該不該選它」完全分開。這是 §7.1 與 §7.2 那兩層存在的前提。
- **生產端各配一條笨到不需要辯護的觸發**（§3），第三份整條換掉。
- 觸發的參數**不掃描**。掃描它等於在調第三份的東西 —— 掃的是 §6 那四個
  **執行**參數。

## 3. 觸發階梯（刻意笨，第三份整條換掉）

```
見底                                   → 撤退      （第一份，已有）
健康 + 敵分隊已經被別人纏住 + 有距離   → 側翼切入
健康 + 近                              → 集火
其餘                                   → 自由交戰
```

「見底」的定義沿用第一份 §2.4（小隊裡最低的那一架持續 T 秒低於門檻）。
撤退**優先於**兩個新戰術：打不動的小隊不該被派去執行任何進攻戰術。

### 3.1 側翼那條為什麼要加「已經被別人纏住」

少了它，**開場五個分隊對五個分隊全都健康又全都很遠，所有人同時側翼** ——
而側翼途中不交戰（§4.4），開局會變成兩隊互相繞圈、一槍不開。更糟的是它會
自我維持：雙方都在繞，「已經接戰」永遠不成立。

加上這道閘門之後，側翼在語意上就是史實的「從側面加入別人已經打起來的仗」，
而且**結構上不可能在接敵前觸發**。

判定：目標敵分隊裡至少有一架，它的 `cornerRatio` 低於 `ENGAGED_RATIO`
（0.9）—— 也就是有人正在讓它拉桿。**這與見底判定用同一個量，不新增概念**：
0.9 高於指揮層的 `spentRatio`（0.6，「已經打不動」）而低於自由巡航。

### 3.2 側翼與集火互斥，靠距離分開

遠（> `FLANK_RANGE`，2500 m）→ 側翼切入；近 → 集火。兩者永遠不會同時成立，
所以**命令不需要組合**，`OrderKind` 是一個聯集而不是一組旗標（§6.1）。
2500 介於 `THREAT_RANGE`（900）與 `withdrawRange`（3000）之間。

### 3.3 這兩個數字**不進** `CommandConfig`，也不掃描

`ENGAGED_RATIO` 與 `FLANK_RANGE` 是**觸發**參數，而 §2 的裁定是觸發整條由
第三份換掉。把它們放進 `CommandConfig` 會讓人以為它們與 §8 那些執行參數
同一個地位，於是被一起掃描 —— 那就是在調第三份的東西。

寫成 `command.ts` 裡的模組層級常數，註解明寫「暫時的觸發，第三份整條換掉，
**不要掃描它**」。

## 4. 側翼

### 4.1 對象是敵**分隊**，不是整個敵隊

2026-08-07 的實測（20v20、120 秒、每 0.5 秒取樣）：

```
敵「隊」質心的漂移        中位數    最大
  10 秒                    393 m   1854 m
  30 秒                    720 m   4971 m
  50 秒                   1009 m   4945 m

敵「分隊」質心 @30 秒     五個分隊的中位數
                     2040 / 2071 / 2587 / 2712 / 4663 m
```

整隊的質心很穩 —— 20 架在纏鬥，繞來繞去互相抵銷。**但抵銷效應只在架數多時
成立**，四架的分隊就是一團一起動的東西，30 秒飄 2~4.6 km。

對象取分隊（戰術上才鋒利：包一個小隊的側翼，而不是「往戰區的側面移動」），
**代價是集合點不能凍結** —— 這是第一份 §4.1 刻意迴避掉的決定，現在必須面對。

### 4.2 點每步重算，到達改用幾何判定

**命令凍結的是「決定」，不是「座標」**：`side`（從左舷還是右舷切進去）與
`targetFlight`（切誰）一旦發出就不再變；飛行點每步由**當下**的敵分隊質心
推出來。

到達判定**不能**再用「距離小於 `arriveRadius`」—— 那個判準在追一個移動目標
時可能永遠不成立，正是第一份 §4.1 記載的病。改用**幾何**：

```
到達 ⇔  我方分隊質心在敵分隊的後側方扇區內
   且  我方分隊質心離敵分隊質心進入交戰距離
```

「後側方扇區」的定義：令 `u` = 敵分隊平均速度的水平單位向量，
`d` = 由敵分隊質心指向我方分隊質心的水平單位向量，則

```
到位 ⇔ d · u < cos(flankSector)     （我在他們的後半邊）
```

**幾何判準不會過期。** 它同時就是驗收要量的東西（§7.3）—— 判準與想量的
東西是同一個，不需要第二個近似。

### 4.3 側翼點的算法與危險評估

```
u   = 敵分隊平均速度的水平單位向量（退化 → 敵分隊機首平均；再退化 → −Z）
r   = u 的右手側水平法向量 = (−u.z, 0, u.x)
候選 = 敵分隊質心 − u × flankTrail ± r × flankOffset
高度 = 敵分隊質心的高度 + flankClimb，夾在 clearanceScale 與最低升限之間
```

`−u × flankTrail` 把點放到他們**後方**而不是正側方：正側方是一個過渡位置，
後側方才是能開始追蹤射擊的位置。

**危險評估**（專案負責人 2026-08-07 追加）：側翼點有可能正好落在另一場交火
中間。對左右兩個候選點各算一個危險分數，取安全的那一邊；**兩邊都超過門檻
就不發令**。

```
danger(p) = Σ  1 / (1 + (|p − e| / dangerScale)²)     e ∈ 不屬於目標分隊的敵機
```

- **為什麼是平方反比而不是計數**：計數需要一個半徑門檻，而門檻會讓分數在
  邊界上跳。連續核在相鄰輸入上連續 —— 與 `targetScore` 的三個折扣項、
  `floorPitchAngle` 的連續斜坡同一條紀律（§7.5 的否決條件之一）。
- **為什麼排除目標分隊自己**：側翼點本來就該靠近它。把它算進去等於懲罰
  「靠近要打的人」。
- **為什麼不算友機**：友機不危險。這裡問的是「這個點會不會被打」。

### 4.4 途中不交戰

與第一份 §2.3「命令絕對」一致：側翼期間不交戰，閃躲依舊絕對優先
（第一份 §2.2）。

**理由不是史實的「保持突襲」** —— 這個專案的 AI 是全知的，沒有突襲可言。
是機械上的：不交戰就不用轉彎瞄準，到位快很多，而**到位後的優勢才是側翼的
目的**。

代價是轉場期間輸出為零，直接往傷害護欄撞 —— 見 §7.4。

## 5. 集火

### 5.1 只覆寫長機的目標，僚機靠既有機制收斂

`wingman.ts` 的 `LEVEL_FOCUS`（第 3 級）語意已經是「打參考機正在打的那一
架」，而且帶著兩道測過的閘門（離站位太遠不出擊、目標離參考機超過
`THREAT_RANGE` 不跟）。它同時是**最低的一級** —— 自衛與掩護都插得了隊。

所以指揮層**只覆寫長機的 `target`**，僚機透過既有的 `LEVEL_FOCUS` 自動
收斂過去。**與集合點同一個手法：只操縱長機，編隊靠既有機制跟上**，不新增
任何協調、不動 `wingman.ts` 一個字。

### 5.2 硬覆寫，但規劃端只准指定「追得到」的

專案負責人 2026-08-07 裁定：硬覆寫（與「命令絕對」一致），風險改在**規劃
端**防。

風險是具體的：`targetScore` 有距離折扣與轉彎成本兩項，它們存在的理由就是
防止 AI 飛去打一架追不到的敵機。硬覆寫繞過整個 `selectTarget`，那兩道防護
一起消失。

所以 `planFocusTarget` 只從通過**可及性閘門**的敵機裡挑：

```
可及 ⇔ |e − 小隊質心| < focusRange
   且 由小隊質心指向 e 的方向，與小隊平均速度的夾角 < focusCone
```

**為什麼不用 `assess.ts` 的 `turnTime`**：它吃兩架 `Aircraft`（要包絡查詢與
姿態），而規劃層只吃快照 —— 收 `Aircraft` 會毀掉「純函數，能直接餵字面物件
出考題」這個性質，那是 §7.1 那一層存在的前提。在 `command.ts` 裡重寫一個
`turnTime` 的近似更糟：那就是**對同一個問題有兩個答案**，正是第一份反覆避開
的錯誤。

夾角不是 `turnTime` 的近似，**它是另一個問題的精確答案**：「這架敵機在不在
我們正在去的方向上」。它只需要 position 與 velocity，兩者快照都有。

**沒有任何一架可及 → 不發令。** 這與 §4.3「兩邊都危險就不發令」是同一條
紀律：**規劃層寧可不發，也不發一張執行不了的命令。**

### 5.3 挑哪一架：血最少的

從可及的敵機裡取 **`hpFraction` 最低**的那一架；同值時取近的。

**為什麼不重用 `targetScore`**：同 §5.2 —— 它吃 `Aircraft`（要 orientation
算機首、要 `threatFactor`）。用速度方向代替機首是一個近似，而近似會製造
第二個「誰好打」的答案。

**為什麼「血最少」是對的判準而不是將就**：集火的整個賣點是**讓目標更快掉
下來**（§7.3 的第 30 條就是量這個）。已經受創的那一架離掉下來最近 —— 這是
史實的「打落單、打受傷」，也是這個戰術唯一能買到的東西。`targetScore` 回答
的是另一個問題（「誰對我最有價值」，含威脅項與機會項），那是**單機**選目標
的問題，不是**小隊集火**的問題。

`CommandUnit` 因此要加一個 `hpFraction`（0..1，1 = 毫髮無傷）。它與
`cornerRatio`、`alive` 一樣是每步被 `setup.ts` 改寫的快照欄位。

### 5.4 集火期間**要**交戰

這是它與另外兩種命令最大的差別，也是 `OrderKind` 必須存在的理由。

## 6. 架構

### 6.1 命令長出種類

```ts
export type OrderKind = 'rally' | 'flank' | 'focus'

export interface FlightOrder {
  readonly kind: OrderKind
  /**
   * 飛行點。`rally` 發令後凍結；`flank` **每步由 `stepCommand` 重寫**
   * （§4.2）；`focus` 不使用。
   */
  point: Vector3
  /** 到達判定半徑，m。只有 `rally` 使用 */
  readonly radius: number
  /** `flank`：切誰。全域分隊索引。其餘為 −1 */
  readonly targetFlight: number
  /** `flank`：從哪一邊切。+1 = 敵航向的右舷，−1 = 左舷。其餘為 0 */
  readonly side: number
  /** `focus`：打哪一架。`units` 的全域索引。其餘為 −1 */
  readonly focusIndex: number
}
```

`point` 對 `flank` 而言不再是 `readonly` —— **這是刻意的，而且只有這一種
命令如此**。註解要寫明凍結的是 `side` 與 `targetFlight`。

### 6.2 `stepCommand` 的簽名要改（同時修掉第一份的一個浪費）

第一份的 `stepCommand` 收 `flights`（**全部**分隊，含敵方）與一個攤平的
`enemies` 陣列，於是它**替敵方分隊也規劃了一遍**，結果從來不被讀。正確但
浪費一半的規劃工作，而且讀起來會讓人以為藍方指揮官在指揮紅方。

側翼要挑「某一個敵分隊」，本來就需要敵方的**分隊結構**而不是攤平的名單。
一併改成：

```ts
export function stepCommand(
  s: CommandState,
  flights: readonly CommandFlight[],   // 全部分隊，全域索引
  own: readonly number[],              // 這個指揮官管的分隊索引
  foe: readonly number[],              // 敵方的分隊索引
  units: readonly CommandUnit[],       // 全域索引，與 CommandFlight.members 對應
  skipFlight: number,
  dt: number,
  cfg?: CommandConfig,
): void
```

攤平的 `enemies` 不再需要（由 `foe` + `flights` + `units` 推得）。
`setup.ts` 的 `BLUE_UNITS` / `RED_UNITS` 兩個暫存陣列因此可以刪掉，換成
兩組**分隊索引**（在 `createBattle` 時算一次就好，分隊的隊伍歸屬不會變）。

### 6.3 規劃拆成三個純函數

```ts
/** 撤退。第一份既有，簽名不變 */
export function planFlightOrder(...): FlightOrder | null

/** 側翼。`null` = 兩邊都太危險，或目標分隊沒在交戰 */
export function planFlankOrder(
  members: readonly CommandUnit[],
  target: readonly CommandUnit[],      // 目標敵分隊
  others: readonly CommandUnit[],      // 其餘敵機，算危險分數用
  targetFlight: number,
  cfg?: CommandConfig,
): FlightOrder | null

/** 集火。`null` = 沒有任何一架可及 */
export function planFocusTarget(
  members: readonly CommandUnit[],
  candidates: readonly CommandUnit[],
  candidateIndices: readonly number[], // 與 candidates 平行，給 focusIndex 用
  cfg?: CommandConfig,
): FlightOrder | null
```

**三個都是純函數**，理由與第一份 §3 相同：混戰的結果太吵，從結果反推判斷
品質驗不出東西，必須能直接餵快照出考題（§7.1）。

三個都**只讀 `CommandUnit`**，不 import `Aircraft`、不 import `assess.ts`
的任何東西 —— 見 §5.2 與 §5.3 兩處對「為什麼不重用 `turnTime` 與
`targetScore`」的說明。這是這一層能出考題的前提。

### 6.4 戰機端

`AiController` 的優先序：

```
defend  >  rally|flank → 'rally' 意圖  >  focus → 只換 target  >  arbitrate
```

具體改動只有三處：

1. 現行的兩行覆寫加一個條件 —— `focus` **不碰意圖**：

```ts
if (this.order !== null && this.order.kind !== 'focus') {
  this.intent = this.rules.defendLatch ? 'defend' : 'rally'
}
```

2. 現行的僚機限制（「停止出擊」）加同一個條件 —— `focus` 時僚機**不能**被
   清掉目標，它要靠 `LEVEL_FOCUS` 跟上長機：

```ts
if (this.order !== null && this.order.kind !== 'focus'
    && reference && this.wingmanState.level > LEVEL_SELF_DEFENCE) {
  this.target = null
}
```

3. 新增 `focusTarget: Aircraft | null`，由 `setup.ts` 每步寫入（與
   `stationReference` 同一個手法 —— 索引在規劃層，解析成 `Aircraft` 在
   `battle` 層）。長機在**選完目標之後**（`if (this.board)` 那一段的尾巴，
   與既有的僚機限制相鄰）套用：

```ts
if (this.focusTarget !== null && !reference) this.target = this.focusTarget
```

**`!reference` 是重點**：只有長機被覆寫。僚機走 `LEVEL_FOCUS`，那一級本來
就有自衛與掩護插隊 —— 「有人正在打我」不會被集火命令擋住。

**陣亡的那一格由 `setup.ts` 負責**：解析索引時若那一架已經 `!alive`，寫入
`null`。理由是層次 —— `AiController` 不該知道「命令裡的索引可能過期」這回
事，而 `setup.ts` 本來就在做索引解析。`stepCommand` 同一步也會把命令解除
（§7.1 考題 22），所以這只是同一件事的兩道保險：**命令層的解除是慢的
（下一次規劃），索引解析是每步的。**

## 7. 驗收

### 7.1 純函數的考題（不跑模擬）

**這一層是唯一能抓到「指揮 AI 想錯了」的地方。** 混戰的結果太吵。

`planFlankOrder`：

1. 目標分隊在 +Z、朝 −Z 飛 → 側翼點在他們**後方**（Z 比質心大）
2. 側翼點在敵航向的側方，橫向偏置約等於 `flankOffset`
3. 我方在目標分隊的左邊 → 選左舷（就近，也就是轉場最短）
4. 右邊塞滿其他敵機 → 選左舷（**危險評估壓過就近**）
5. 左右都塞滿其他敵機 → `null`
6. 目標分隊沒有任何一架在交戰（全部 `cornerRatio` 高） → `null`
7. 敵分隊速度退化為零 → 用機首平均，不產生 NaN
8. 敵分隊速度與機首都退化 → 取固定方向，不產生 NaN
9. 高度夾在 `clearanceScale` 與最低升限之間
10. **決定性**：同一個快照算兩次逐位元相同
11. **連續性**：其他敵機位置微擾 ±20 m，側翼點的位移有界
12. **連續性**：危險分數對敵機位置連續（不因為跨過某個半徑而跳）

`planFocusTarget`：

13. 兩架等距、一架受創 → 挑受創的（§5.3 的主判準）
14. 兩架血量相同、一近一遠 → 挑近的（同值時的破平手）
15. 唯一的敵機在 `focusRange` 外 → `null`
16. 唯一的敵機在射程內但偏離小隊航向超過 `focusCone` → `null`
17. 受創但不可及、健康但可及 → 挑**健康那架**（可及性是閘門不是加權項，
    一個追不到的目標再好打也沒用）
18. **決定性**：同一個快照算兩次回同一個索引

`stepCommand` 的生命週期：

19. `flank` 的 `point` 每步跟著敵分隊質心移動
20. `flank` 的 `side` 與 `targetFlight` 發令後**不再變**（凍結的是決定）
21. `flank` 到位（進入後側方扇區且距離夠近）→ 命令解除
22. `focus` 的目標陣亡 → 命令解除
23. 撤退優先於兩個新戰術：見底的分隊拿到的是 `rally` 而不是 `flank`/`focus`

### 7.2 強制注入的執行驗收（20v20）

**把戰術直接塞給分隊，不經過觸發階梯。** 量的是「執行得對不對」。

24. 強制 `flank` → 該分隊的質心確實進入敵分隊的後側方扇區（多數命令成立，
    判準形狀與第一份 §9.3 的「編隊收攏」相同，理由也相同：混戰是混沌的，
    個別一張被打斷是正常的）
25. 強制 `flank` → 轉場期間該分隊的開火取樣數為 0（§4.4）
26. 強制 `flank` → 命令期間不動用安全層的撞地接管（與第一份同一條線）
27. 強制 `focus` → 該分隊成員鎖定同一架的比例，顯著高於不下令的對照
28. 強制 `focus` → 僚機**不會**被清掉目標（`target !== null` 的比例不低於
    對照）—— 這一條守著 §6.4 的第 2 點，那是最容易寫錯的地方

### 7.3 效果驗收：品質，不是量

專案負責人 2026-08-07 裁定：**主判準改成品質，量的判準降成地板。**

理由：側翼與集火要買的是**從更好的角度發起攻擊**與**同一個目標被更多架
咬**。用總傷害量去驗品質的改動，方向本來就不對 —— 而且側翼必然減少交戰
時間，量的判準會把一個成功的側翼判成失敗。

29. **側翼的品質**：開火那一刻的**方位角**分布往後側方移動。
    定義：開火時 `敵機首 · 由敵指向我` 的中位數 —— 值越接近 −1 代表越是從
    他背後打。開戰術 vs 關戰術對照，開的那一路中位數必須更低。
30. **集火的品質**：**每單位開火時間的擊墜數**上升。集火的整個賣點就是
    「同一架被多人咬 → 更快掉下來」；若它沒有變快，這個戰術沒有意義。
31. **量的地板**：總傷害不得低於關戰術的某個比例。**這個數字等 §7.2 與
    §7.3 實測完再定**，而且要與專案負責人確認 —— 它是護欄不是參數。
    第一份 §9.4 已經記過：一條撤退規則就讓總傷害掉 48%，遠高於命令佔時
    比例，因為撤離的小隊同時停止挨打與停止輸出。側翼會再加一段。

### 7.4 回歸

全套；`perf-gate` 與 `rematch` 依慣例單獨複測。

**`perf-gate` 特別要看**：側翼的點每步重算，那是新的每步工作。它必須不
配置（走既有的 `makeScratch` 暫存池）。

**第一份的通道驗收五條必須全綠** —— 撤退的行為不得因為這一份而改變。

### 7.5 否決條件

任何一條成立，整份撤回而不是調參數：

- 規劃的**決定性**或**連續性**不成立（考題 10、11、12、18）
- 命令期間動用了安全層的撞地接管（考題 26）
- 側翼**到不了** —— 多數強制注入的側翼命令進不了後側方扇區（考題 24），
  而 §6 的掃描找不到任何一組參數救得回來
- 集火**沒有變快**（考題 30）—— 那代表這個戰術不存在價值

**護欄重新定值是專案負責人的決定，不是實作者的。** 紅了先量、先報告、先問。

## 10. 實作後的實測回填（2026-08-07）

八個任務全部實作完成，commit `367d8eb`..`ade4fd8`。這一節記載實測到的
東西 —— 包含**三件推翻了本文設計的事**與**三條留紅的判準**。

### 10.1 先更正 spec 已知的三處

**一、§4.3 的退化階梯寫「敵分隊機首平均」，但 `CommandUnit` 沒有
`orientation`。** 那是從 `stationPoint` 抄形狀時漏掉的 —— 那個函式收
`Aircraft`，有機首可以退。實作的階梯是：

```
目標分隊平均速度 → 由我方質心指向目標質心 → 世界 −Z
```

第二階把敵人當成「正在遠離我們」，於是點落在**我們與他們之間**，可及而且
安全。原文保留供追溯。

**二、§6.2 沒說集火命令什麼時候解除（只說了目標陣亡）。** 目標活著就永遠
不解除的話集火會變成永久狀態，那正是第一份 §4.1 記載的病。實作加了「跑到
`FLANK_RANGE`（2500）之外」，與發令條件 `focusRange`（1500）構成遲滯 ——
兩個**既有**的數字，不新增參數。

**三、§7.1 的考題條數。** 實際寫出來的是 Task 2 十八條、Task 3 九條、
Task 4 十條，加上 Task 1 兩條，共三十九條，全部綠。

### 10.2 實作中發現的四個洞（三個在既有程式碼裡）

**一、命令期間照樣開火。** 意圖覆寫有生效（`intent === 'rally'`），但
`raw.firing = shouldFire(...)` 根本不看意圖。`rally.ts` 的 `rallyCommand`
確實寫了 `firing = false`，可是它只在「沒有目標」那條分支跑 —— **有目標的
長機走的是另一行**。這個洞第一份就在，只是沒有測試問過。閘門加在意圖上。

**二、「沒有目標 → 飛集合點」那一格不看 `kind`。** 集火令的 `point` 是零
向量，於是集火令的長機在目標剛陣亡的那一瞬會往**世界原點的海平面**俯衝。
Task 4 量到的撞地接管 34,175、掉到 clearance 以下 8,460、傷害崩到
R311:B182，全部是這一個成因的全域版本。

**三、`stepCommand` 掃全部分隊。** 藍方指揮官替紅方分隊也規劃了一遍、結果
從來不被讀。§6.2 換簽名時一併修掉。

**四、「撤退優先於兩個進攻戰術」只寫在規劃那一格是不夠的。** 持有命令時
規劃根本不跑，於是一張已經發出的側翼令會把小隊釘在那裡直到它到位，期間
就算打不動了也換不到撤退令 —— 而「打不動的小隊被派出去切側翼」正是這條
優先序要防的事。實作把優先序同時做成一條**解除條件**。

### 10.3 §7.2 強制注入的執行驗收：九條全綠

```
側翼   注入 6 張、到位解除 6 張、命令期間開火 0/43460、
       撞地接管 0、沒有飛機掉到 clearance 以下
集火   注入 5155 張、鎖同一架的比例 0.476、
       僚機持有目標 33.9%（側翼 1.3%、自由交戰 31.1%）、撞地接管 0
```

**寫這一層時抓到三個量測本身的錯誤，每一個都會讓驗收量到不存在的東西：**

1. **強制注入跟真實指揮官搶同一格。** 原本只在「這一格是空的」時補一張，
   而指揮官會替同一個分隊發自己的命令 —— 實測 120 秒裡只有 4 張是注入的，
   其餘時間量到的是指揮官自己發的集火令（開火取樣 5828 個全部是
   `kind === 'focus'`）。改成用**物件同一性**每步補位。
2. **側翼注入的目標挑「最近的敵分隊」。** 混戰中最近的分隊本來就在
   `FLANK_RANGE` 內、常常已經在它的後方扇區 —— 命令在發出的同一步就被
   `flankArrived` 判定到位（17,701 張注入、17,700 張立刻解除，飛機一張都
   沒真的收到）。那是真實觸發器**永遠不會產生**的狀態。改成只挑超過
   `FLANK_RANGE` 的，並把該常數 export 出來（與「不進 `CommandConfig`、
   不掃描」不衝突）。
3. **到位就立刻補下一張，受命分隊整整 120 秒一槍不開**（方位角取樣 0 個）。
   側翼要買的是「切進去**之後**開的那幾槍角度更好」，效果的發生時機被量測
   整個切掉。加了 10 秒冷卻期，品質只在 `order === null` 的自由狀態量。

**兩個門檻由專案負責人依實測裁定：**

- 「鎖同一架的比例」：實測 0.476，裁定 **> 0.30**（約 1.6 倍餘裕）。
- 「集火期間僚機仍然有目標」：計畫寫的 **> 50% 不可能滿足** —— 自由交戰的
  僚機本來就只有 31.1% 的時間握著目標。改成對照式「集火 > 側翼的十倍」
  （實測 33.9% vs 1.3%，26 倍）。那問的才是 §6.4 第 2 點真正的問題：
  **限制對 `focus` 有沒有關掉**。同一場、同一批飛機，抵銷選擇效應。
  這個專案踩過三次同一個坑（task #136 的 `minAlt > 500`、第一份的
  `strayUnderOrder === 0`、這一條）。

### 10.4 §7.3 的兩個品質判準：**量不出來，留紅**

```
方位角     側翼 0.938  對照 0.919   （n = 66 對 446）
每單位開火時間的擊墜   0.000  對照 0.000  （兩邊都是零擊墜）
```

- **`killsPerFiring` 在這個場景沒有解析度**：120 秒的 20v20 一架都沒掉
  （總傷害 2,764 對上 40 架的血量），兩邊都是 0.000。
- **方位角沒有往後側方移動**，而且 n 只有 66，不足以論證任何事。受命分隊
  在命令期間本來就不開火，自由窗口的取樣量因此天然很小。

這兩條是 §7.5 的**否決條件**。**沒有調門檻、沒有改判準** —— 它們留紅，
等專案負責人裁定要換量測方式（更長的場、更多場、或改量「側翼到位後第一次
開火的方位角」）還是視為戰術本身沒有買到東西。

**量的地板同樣留白**：實測比值 0.628（側翼 1,736、對照 2,764）。`FLOOR`
是護欄不是參數，暫留 0（那條測試現在只擋「總傷害歸零」，註解裡寫明它還
不是 §7.3 要的那條護欄）。

### 10.5 §8 的八個參數：**沒有掃描**

掃描的選值判準（§8）就是 §7.3 的那兩個品質指標，而它們現在量不出來。
拿一個量不出來的判準去掃 30 組會產生一張**看起來有來歷、其實沒有**的表
—— 這個專案在第一份的掃描表註解裡剛寫過「不要拿這張表去論證 0.6 比 0.5
好」。八個值維持起始值，來歷寫在 `DEFAULT_COMMAND` 的註解裡（每一個都
對應一個既有的量）。**品質判準定案之後再掃。**

### 10.6 對既有驗收的影響：四條紅，成因全部量到

| 測試 | 判準 | 實測 | 成因 |
|---|---|---|---|
| `ai-command-channel` | 離場佔時 < 25% | 36.67% | 見下 |
| `ai-command-channel` | 命令期間撞地接管 = 0 | 134 | 見下 |
| `multi-battle` | 開局巡航編隊 < 100 m | 365 m | 相位偵測失效 |
| `multi-battle` | 傷害比 ≤ 1258 | 1503 | 戰局形狀改變 |
| `ai-duel-matrix` | ≤ 0.35 | 0.388 | 1v1 的分隊只有一架 |

**通道驗收的兩條判準先依裁定改成只算「離場」的命令**（`rally` + `flank`，
`focus` 不算）：上界 25% 的理由逐字是「場上有四分之一的飛機在離場 —— 那
不是空戰」，而 `focus` 是「打那一架」，一秒都沒有離場；收攏量的是僚機的
站位誤差，而它會縮小是因為僚機被清掉目標，`focus` 刻意不清。改完之後收攏
**7:1 綠**（rally 4:1、flank 3:0；未拆之前是 7:12，鬆脫的 11 張全部是
`focus`）。

**剩下兩條是真紅，而且成因已經證實：** 把兩個新戰術暫時關掉重跑，數字
**逐字回到第一份**（5 發 5 到、17.79%、撞地 0）。所以退化完全來自新戰術
改變了戰局的走向 —— `rally` 的程式碼一個字都沒動，這一份加的開火閘門對
這組數字的影響是零。

機制：被派去側翼／集火的分隊之後更常見底，而且是在更高、更慢、更深入的
位置見底，於是撤退令發得更多（5 → 11）、到得更少（5/5 → 5/11）。134 次
撞地接管全部發生在 **5,345 m、TAS 50 m/s** —— 一支見底的小隊被叫去爬
600 m 之後掛住，被 `safety.ts` 的撞地分支吞掉的**失速**（該檔 233 行的
註解記過同一個病：低速時 `nMax` 崩掉，`recoveryAltitude` 會讓撞地分支在
任何高度接管）。

**`multi-battle` 的兩條與 `ai-duel-matrix` 的一條同源，而且指向觸發階梯
而不是戰術執行：**

實測接敵瞬間（t = 24.0 s）**八個分隊同時拿到集火令** —— §3.2 的階梯是
「近就集火」，而接敵後每個分隊都在 `FLANK_RANGE` 內。於是整場戰鬥幾乎
都在集火令之下（佔時 32.6%，而 `rally` 33.5%、`flank` 只有 3.2%）。

後果之一是兩隊質心**在 150 秒內從來沒有靠近到 900 m 以內**，而
`multi-battle` 的「巡航相位」正是用那個距離判定結束的 —— 相位偵測因此
整場為真，那條判準量到的是整場戰鬥的站位誤差而不是巡航的。**判準沒有
壞，是它依賴的相位偵測被新行為破壞了。**

§3 已經明寫這個階梯是暫時的、第三份會整條換掉。這三條紅要不要在第三份
之前處理，是專案負責人的決定。

### 10.7 效能

`perf-gate` 與 `rematch` 單獨複測全綠。側翼點每步重算（`flankPoint`）與
幾何到位判定（`flankArrived`）都不配置，走既有的 `makeScratch` 暫存池。

## 11. 品質判準的第二輪量測（2026-08-07 稍晚）

§10.4 記載的「兩個品質判準量不出來」交專案負責人裁定後，改了量法重跑。
**門檻在跑之前先定死** —— 看到結果再定門檻等於量到綠為止，這一輪的目的
正是要讓判準**有可能失敗**。

### 11.1 三個改動

| | 舊 | 新 | 理由 |
|---|---|---|---|
| 集火 | 每單位開火時間的**擊墜** | 被指名那架的**掉血速率** ÷ 同場同隊其他敵機 | 擊墜是傷害的門檻版，而 120 秒零擊墜 → 分母是零 |
| 側翼 | 一場、n=66 | **九個受命分隊各一場**合併 | 換 seed 沒用（只影響飛行員名字） |
| 地板 | 未定 | **0.55**（實測 0.628） | 留約 13% 餘裕 |

過程中又修掉兩個量測錯誤：

1. **冷卻期根本不自由。** 只是不注入是不夠的 —— 真實指揮官會在下一個規劃
   週期補上自己的命令（接敵後每個分隊都在 `FLANK_RANGE` 內，補的幾乎必然
   是集火）。九場合併的自由開火取樣因此**只有 66 個，與單場一樣多**。改成
   冷卻期每步清掉那一格，取樣變成 **3854 個**。
2. **「命令期間一槍都不開」量的是全部。** 閃躲永遠優先是既有裁定：破防閂上
   時那些格**不受命令管**，而正在閃躲的飛機偶爾會打到一槍。要求零等於順帶
   要求「閃躲時不准開槍」—— 這個專案第四次踩到「對一個基線非零的量要求零」。
   改成量意圖為 `rally` 的那些格，實測 **0**。

### 11.2 結果

```
集火掉血速率      3.681 對 0.767 = 4.80 倍   （門檻 1.5）    過
總傷害            2273 對 2764 = 0.822        （地板 0.55）   過
鎖同一架的比例    0.537                       （門檻 0.30）   過
側翼方位角        −0.214 對照 −0.243、n=3854  （要低 0.05）   不過
僚機持有目標      0.566 對側翼 0.064 = 8.9 倍 （門檻 10）     不過
```

**集火成立，而且是強成立。** 掉血速率 4.8 倍遠高於門檻，機制（僚機靠
`LEVEL_FOCUS` 收斂到長機的目標）也直接量到了。

### 11.3 側翼：11.2 那一列是**錯的**，已更正

原本這裡寫「側翼乾淨地不成立，方位角 −0.214 對照 −0.243，方向是反的」。
**那個結論來自一個量測 bug**，2026-08-07 稍晚由 `flankSector` 的掃描發現：

`ai-command-tactics.test.ts` 的判準印出的 `n` 用的是 `aspectCountOwn`
（受命分隊、自由狀態），但比較的**值**誤用了 `aspectSum`（**全場所有飛機、
含命令期間**）。兩個母體差很多 —— 獨立探針量到同一場仗的三個值：

```
全部開火        −0.243   n = 18747
自由狀態（無命令） +0.769   n =  1562
命令期間        −0.335   n = 17185
```

修正後的比較是 **側翼 0.061 對照 0.769**（n = 3854），也就是側翼之後
自由開火的方位角**明顯往後側方移動**，方向與設計主張一致，而且通過了
預先登記的門檻（要低 0.05 以上，實際低 0.708）。

### 11.4 但這一條**還不能算證明** —— 對照沒有時間對齊

方位角受**戰局階段**支配的程度遠超過戰術本身。同一批受命分隊、**不下任何
命令**的對照：

```
整場        +0.858   n = 1060
後半場（60 秒之後） −0.600   n =   58
```

開場是對頭接面（正面、正值），後期變成咬尾（背後、負值）。**任何把開火
時機往後推的處理都會讓這個指標變好看**，而側翼恰恰就會把開火往後推
（繞路途中不開槍）。

側翼實測 0.061 落在對照的整場（0.858）與後半場（−0.600）之間，所以
「是戰術還是時機」目前分不出來。要分出來必須**時間對齊**：拿側翼的每一段
自由窗口 `[t, t+10]`，只取對照組在同一批時間窗內、同一批分隊的取樣來比。

### 11.5 到位判定與點位置的掃描：**不可用**

同一批量測跑了 `flankSector`（60/90/120/135/150）與 `flankTrail`
（1700/2500/3500）共八組。**那張表不能拿來選值**，兩個理由：

1. 各組的方位角取樣數差到 **40 倍**（165 到 7223）。到位判定越嚴，小隊待在
   命令裡越久、自由窗口越短，而且那些槍落在戰局的不同階段 —— 每一組平均的
   **母體根本不是同一群**。
2. 上面 11.4 的階段混淆對每一組的影響不同。

所以「哪一個到位角度比較好」目前**沒有答案**。表留在這裡當紀錄：

```
flankSector  60 → −0.127  n=2818   注入 14 到位 12
             90 → −0.646  n=7223   注入 16 到位 14
            120 → −0.338  n=3791   注入 13 到位 11
            135 → −0.139  n=4379   注入 11 到位  9
            150 → −0.503  n= 165   注入 12 到位 10
flankTrail 1700 → +0.323  n=2153   注入 11 到位 11
           2500 → −0.336  n=3190   注入 12 到位 10
           3500 → −0.468  n=1825   注入 13 到位 10
```

值得記的一件事：**八組的撞地接管全部是 0，`firingRally` 全部是 0**。
到位判定收到 150°（正後方 30° 以內）時命令仍然到得了（12 發 10 到）——
所以「收緊到位判定會讓命令完不成」這個當初的顧慮，實測**不成立**。

### 11.6 一個設計層的觀察（來自專案負責人的提問）

現在的到位判定是 `d·u < cos(flankSector)`，`flankSector` = 60° 表示
「我方在敵機首 60° 以外」—— **正側面（90°）就算到位**。而點放在敵分隊
後方 800 m、側向 1200 m，也就是尾軸外 `atan(1200/800)` = **56°**。

二戰空戰裡 90° 正側面是**最難打的位置**（最大偏角射擊）；要的是六點鐘
方向，偏角接近零。「側翼」指的是**繞過去的路線**，不是最後要停的位置。
就這個推理而言，現行的兩個值都偏側面。

另一個被提出的定義是「以我方航向的 45° 側邊」。不建議：它只描述我們轉了
多少，**沒有描述與敵人的相對位置** —— 兩隊對頭接近時往自己的 45° 飛出去，
會落在敵人的側面甚至前方。參考系掛在敵人的速度向量上才有意義，這點現行
實作是對的。

### 11.7 僚機那條門檻的一個誠實註記

10 倍是依「側翼 1.3%、集火 33.9%（26 倍）」定的，而那組數字來自**修好
冷卻期之前**的量測。修好之後兩個數字都動了（0.064 / 0.566），比值 8.9 倍。

所以這一條**不是**一次乾淨的預先登記：門檻定下來之後，量測工具本身又改了。
它要不要算不過，是專案負責人的決定。就機制而言 8.9 倍與 26 倍講的是同一
件事 —— 限制對 `focus` 確實關掉了。

## 12. 側翼的最終量測：**時間對齊之後，它讓角度變差**（2026-08-07 最後一輪）

§11.3 更正了一次（「反效果」是量測 bug），§11.4 指出對照沒有時間對齊。
這一節是把對齊做完之後的結論，**它推翻 §11.3 的樂觀更正**。

### 12.1 對齊怎麼做

戰局是完全決定性的，所以對照跑一次就夠：把**每一步、每一個分隊**的開火
方位角存成逐步索引。側翼那九場記下每一段「到位之後的自由窗口」落在哪些
步，只拿對照在**同一批步、同一個分隊**的取樣來比。這樣「打得比較晚所以
角度比較好」在兩邊完全一樣，相減就消掉。

### 12.2 結果

```
沒對齊    側翼  0.061   對照  0.769   delta −0.708   （看起來是大勝）
對齊後    側翼  0.170   對照 −0.558   delta +0.728   （方向相反）

n = 3425 對 7566，九個受命分隊合併
```

**那個「大勝」完全是時間效應。** 同一批時刻，不繞路的那一支已經咬在
人家尾後（−0.558），繞完路的那一支落在正側面附近（+0.170）。

側翼不只沒買到位置 —— 它把**已經到手的尾後位置丟掉了**：為了執行命令
放棄現有的咬尾，飛 2.5 km 過去，結果落在一場新的接面。

順帶：總傷害 2273 對 2764（0.822），所以它同時也花掉了 18% 的輸出。

### 12.3 參數救不回來

到位判定與點位置各掃了幾組，對照同樣時間對齊：

```
knob          值     側翼     同窗對照   delta      n
flankSector    60   −0.004   −0.517    +0.513    2389
               90   −0.646   −0.521    −0.125    7203
              120   −0.333   −0.332    −0.000    3539
              135   −0.152   −0.368    +0.215    4322
              150   −0.503   −0.305    −0.198     165
flankTrail   1700   +0.199   −0.604    +0.803    1746
             2500   −0.390   −0.544    +0.154    2913
             3500   −0.468   −0.413    −0.055    1825
```

`delta` 在 +0.803 到 −0.198 之間亂跳，隨 `flankSector` 完全非單調
（60 正、90 負、120 零、135 正、150 負）—— **那是雜訊不是結構**。五列
平均 +0.08，方向偏壞。到位角度從 60° 收到 150°、後方距離從 800 拉到
3500，沒有任何一組給出一致的負 delta。

**所以這不是參數問題。**

### 12.4 一個副產品：收緊到位判定沒有代價

八組**全部**：撞地接管 0、`rally` 期間開火 0。而且到位判定收到 150°
（正後方 30° 以內）時命令仍然到得了（12 發 10 到）。當初「收緊到位判定
會讓命令完不成」的顧慮，**實測不成立**。這個結論本身仍然有用 —— 若之後
重新設計側翼，到位可以放心要求真的在後方。

### 12.5 現況與建議

| 戰術 | 狀態 |
|---|---|
| **集火** | **成立，而且強**。被指名那架掉血 3.68/s 對同隊其他敵機 0.77/s = **4.8 倍**。僚機被鎖在長機指定的那一架上（56.6%，自由交戰 31.1%、側翼 6.4%）。 |
| **側翼** | **未通過 §7.5**。時間對齊後角度變差（delta +0.73），總傷害 −18%，八組參數都救不回來。 |

**建議把兩者分開處理**：集火可以留，側翼在重新設計之前不該當成「有效
的戰術」計入。領先的重新設計方向（未驗證）是**命令解除時交接目標** ——
現在解除的那一瞬，小隊回頭走既有的自由選目標，而 `targetScore` 完全不
知道「我們剛繞到這一群的後面」，於是它可能挑一個正在對衝的新目標，把
繞路的成果丟掉。若那個假設成立，修法在交接而不在幾何。

**這一節的判準留紅**，不調門檻。
