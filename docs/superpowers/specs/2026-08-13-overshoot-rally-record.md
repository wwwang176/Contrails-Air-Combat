# 2026-08-13 兩個既有缺陷的修正紀錄

**不是設計 spec。** 專案負責人在讀完根因分析後直接指定改法並豁免
SPEC → PLAN（「你可以直接改，我人工驗收」），所以這一份記錄的是**做了
什麼、量到什麼、還剩什麼風險**，不是設計推導。

兩個缺陷都**早於 `feat/turn-radius-trial`**，由玩家實機回報：長機在高空
無限垂直繞圈，5300 m / 250 km/h ↔ 4900 m / 350 km/h，一圈 15~20 秒，AoA
始終 16°。

---

## 1. 缺陷甲：`overshoot` 的能量手段沒有能量守衛

### 1.1 病灶

`geometryGate` 最高優先的那一支：

```
range < overshootRange(120) && closureRate > 0  →  'overshoot'
```

**純幾何，一個字都沒問「我還有速度嗎」。** 而 `steerCommand` 收到這個
mode 之後無條件三管齊下：瞄準點後置 + 高 yo-yo（幾何）、油門收到
`THROTTLE_FLOOR`、減速板全開（能量）。

因為它優先序最高，同一個態勢下「我沒速度了該壓機頭」的 `speedRecover`
**永遠輪不到**。`stall-loop-trace.probe.ts` 抓到的一段：525 km/h 掉到
149 km/h 同時爬升 700 m，安全層在壓機頭而瞄準點層還在拉 —— 兩層互打。

進入 `overshoot` 的取樣有 66~74% **本來就已經低於角落速度**。也就是它
專挑最不該減速的時候減速。

### 1.2 改法

拿掉 `mode === 'overshoot'` 那一支的油門與減速，讓它落到既有的角落速度
判準：`cornerRatio > brakeCornerRatio(1.8)` 才減速，低於角落速度一點都
不減。**幾何手段（後置與高 yo-yo）原封不動。**

依據：「衝過頭」在低速時本來就不成立 —— 低速的飛機追不上任何人。所以
用速度當減速的判準不會削弱這個閘門要解決的問題。

---

## 2. 缺陷乙：集合令的到達判定判錯了對象

### 2.1 病灶

兩層各自都對，合起來永遠不成立：

- `AiController` **只把集合點給長機**（「只操縱長機，編隊靠既有機制跟
  上」）。僚機拿到的是「別打了」+ 站位保持。
- `stepCommand` 的解除條件判的是**小隊質心**（`command.ts:1115`）。

質心被落在站位偏置上的僚機拖著，長機飛過點的那一瞬，質心離點還有一整個
編隊尺度。而 `rallyAim` 是對固定點的**純追擊、沒有抵達行為** —— 命令不
解除就等於長機繞著那個點無限盤旋；轉彎要升力、升力要迎角，於是它一路吃
CLmax，正是回報的 AoA 16°。

實機 log（seed 297534859、座位 #8）：`命令 rally` 連握 200 秒以上，高度
鎖在 5258~5306 m、速度 319~333 km/h、mode 恆為 `unload`。

### 2.2 改法

解除條件由 `centroidDistance` 換成新的 `leaderDistance` —— 分隊裡**第一個
存活成員**離集合點的距離。

掃「第一個存活的」而不是寫死 `members[0]`：這一層吃的是快照，壓縮與
`stepCommand` 的先後是呼叫端的事，寫死索引會在「長機剛陣亡、還沒重壓」
的那一格算到屍體座標，命令從此解除不了。保序壓縮下兩者是同一架。

## 3. 量測

`test/tools/rally-hold.probe.ts`（新增）。**跑玩家實際玩到的
`battleConfigFrom(DEFAULT_SKIRMISH)`（`VETERAN`）**，20v20、900 秒。

> 【為什麼不用 `stall-loop.probe.ts`】那一支跑 `DEFAULT_BATTLE`（`ACE`，
> 反應延遲 0），該配置下指揮層幾乎不發命令，`rally` 佔時 0~3.8% ——
> 缺陷乙在那裡結構上不可見。這就是缺陷丙（護欄跑在玩家玩不到的配置上）。

| 量 | 基準（88030ff） | 改後 |
|---|---|---|
| **甲** 進入 `overshoot` 後 2 s 的掉速 | 中位 33、p90 98、最多 **152** km/h | 中位 4、p90 49、最多 **81** |
| **甲** 進入時 `cornerRatio < 1` 的比例 | 74.3% | 66.5% |
| **乙** `rally` 命令壽命 | 中位 **37.5**、p90 57.2、最長 57.2 s | 中位 **13.6**、p90 33.4、最長 41.8 s |
| **乙** 跑到結束仍未解除 | 0 | 0 |

**兩個種子給出逐位元相同的數字** —— 種子不進物理路徑（只用來取飛行員
名字），這一點在 2026-08-12 已經確認過。誤差棒要靠改開局，不是改種子。

### 3.1 沒有重現到的部分

實機看到的是握 200 秒以上；無頭 900 秒最長只有 57.2 s（基準）。也就是
**極端案例沒有重現**，這一份能證明的是分佈往對的方向移動，不是「那個
200 秒的個案已經不會發生」。原因仍然指向缺陷丙（無頭少了地形、
`crashPolicy`、重生）。

### 3.2 `stall-loop.probe.ts` 三個場景不一致

繞圈視窗比例 3.9%→5.8%、5.9%→4.5%、4.3%→8.2%。**方向不一致，不能當
證據。** 它跑 `ACE`，量到的幾乎全是甲的副作用，而 n≈320 個視窗、差異
5~12 個，落在雜訊裡。記錄下來是為了避免下次有人拿它當結論。

## 4. 護欄的移動（**裁定留給專案負責人**）

基準（88030ff）在這幾支上本來就有紅燈。逐條比較：

| 護欄 | 基準 | 改後 | 歸因 |
|---|---|---|---|
| `ai-command-channel` 編隊收攏 | **綠** | **紅** 257 → 534/701 | **甲**（單獨套甲即紅 534；單獨套乙仍綠） |
| `ai-command-channel` 命令佔時 | 紅 0.0168 | 紅 0.0035 | 甲 0.0084、乙 0.0082，兩者都往下壓 |
| `ai-command-tactics` 側翼方位角 | 紅 −0.447 / −0.554 | 紅 −0.243 / −0.507 | 舊有紅燈，續變差 |
| `ai-withdraw-anchor` 半徑 | 紅 4148 / 3410 | 紅 5199 / 3367 | **甲**（單獨套甲 4316；單獨套乙**逐位元相同**） |

其餘全套綠（2454 passed）。

**「單獨套乙、`ai-withdraw-anchor` 逐位元相同」本身就是缺陷丙的又一個
證據**：那一支跑 `ACE`，命令層根本沒發命令，所以改命令層的解除條件對它
毫無影響。

### 4.1 一個新紅燈的解讀

`編隊收攏` 量的是同一張離場命令在**發令當下**與**解除當下**的平均站位
誤差。甲拿掉減速板之後，長機在受命期間保住能量，僚機追不上 —— 誤差由
257 m 長到 534 m。這是甲的真實代價，不是量具壞掉。

要不要為此付這個代價、或是否該讓 `rallyCommand` 的油門也連續化（讓長機
在僚機落後時等一下），是**重新定值／新設計**的層級，依專案紀律留給負責人。

## 5. 還沒補的洞

**乙只拿掉了「質心被拖住」這一項，沒有加抵達行為。** `rallyAim` 仍然是
對固定點的純追擊。若長機的迴轉半徑大於 `arriveRadius`（300 m），它仍然
可能在 300 m 外繞著點盤旋而永遠判不到達 —— 實機回報的 15~20 秒一圈換算
半徑約 220~290 m，離 300 m 只差一點。

而且 `rally` **豁免** `spentSeconds` 的逾時（`command.ts` 的
`order.kind !== 'rally' && ...`），所以它結構上沒有任何上限。

兩個候選補法（都沒做，等裁定）：

1. `rallyAim` 加抵達行為 —— 進到某個半徑內改成平飛／盤旋，而不是繼續
   對點純追擊。治本，但要新設計。
2. 給 `rally` 一個絕對逾時。便宜，但是遮蔽症狀，與 2026-08-12「不要阻尼
   解法」的裁定同一個性質。
