# M5 多機 設計

前置里程碑：M0 + M1（`2026-07-31-m0-m1-flight-model-design.md`）、M2（`2026-08-02-m2-weapons-design.md`）、M4（`2026-08-03-m4-enemy-ai-design.md`）、低速操控權（`2026-08-03-low-speed-control-authority-design.md`）

---

## 1. 概述

M4 交付了一個會經營能量的對手，但**只有一個**。M5 把戰場從 1v1 拉到 **20v20**。

核心命題：**讓玩家置身於一場真正的空戰，而不是一場決鬥。** 1v1 的每一個決定都只跟一個人有關；20v20 裡「打誰」本身就是一個決定，而且會錯。

**含**：命中判定的空間分割、AI 目標選擇、死亡退場、陣營生成與戰鬥重置。

**不含**（各有理由，不是遺漏）：

| 不做 | 理由 |
|---|---|
| 編隊與僚機協同 | 另一份 spec。1–4 是「多機能不能跑」，編隊是「多機好不好看」，前者是後者的前提 |
| 飛機互撞 | 沒有需求驅動它。40 架的出生點與 AI 行為都不會刻意製造碰撞 |
| 爆炸火焰與殘骸模型 | 專案負責人明確延後至後續里程碑。M5 的陣亡是**直接消失** |
| 難度調整 | 專案負責人明確延後。`DifficultyProfile` 兩個欄位維持 M4 的天花板（皆為 0） |
| 視野盲區 | M4 spec §2 已延後：它需要「最後已知位置 + 搜索行為」，是一整套行為而不是一個參數 |
| 主選單與規模選擇 | 專案負責人裁決：M5 固定 20v20，規模選擇等主選單存在時再做 |

### 1.1 M5 付掉的兩筆舊帳

**一、`resolveHits` 是 O(N²)。** M2 把彈丸池按「M5 的 40 架」抓到 4,000 發，但命中判定的雙層迴圈從來沒有為 40 架量過。實測見 §5：40 架時整步 7,778 µs，每幀 31 ms —— 是整個 60 FPS 幀預算的兩倍。

**二、`isCrashed` 只對玩家做。** `main.ts` 的註解寫得很誠實：「M2 的靶機在固定高度巡航，不會撞海」。M4 的 AI 有安全層，但安全層不是保證 —— 40 架裡總有人會被打到失控。不補的話會出現在海面下繼續飛的飛機。

## 2. 已定案的裁決

| 項目 | 決策 | 出處 |
|---|---|---|
| **戰場規模** | 固定 **20v20**（40 架）。玩家在藍隊，其餘 39 架皆為 AI | 專案負責人裁決 |
| **陣亡表現** | **直接消失**。爆炸火焰與殘骸模型延後 | 專案負責人裁決 |
| **一方全滅** | 整場自動重置（與 `R` 同一條路徑） | 專案負責人裁決 |
| **友軍火力** | **彈丸直接穿過友機**。命中判定跳過同隊 | 專案負責人裁決 |
| **AI 態勢感知** | **全知**：看得到場上所有存活敵機 | 本文 §6.1 |
| **目標選擇** | 評分 + 遲滯 + 隊內分攤 | 專案負責人裁決 |
| **空間分割** | 沿 X 軸的排序掃描，不用網格 | 本文 §5，量測結果 |

### 2.1 為什麼態勢感知是「全知」而不是一個半徑

`DifficultyProfile` 只有 `reactionDelay` 與 `aimError` 兩個欄位，沒有態勢感知半徑。M4 交付的是**天花板**（兩者皆為 0），理由記在 `profile.ts`：不可能從一個沒量過的天花板往下調難度。

態勢感知半徑若在 M5 引進，它會是**第三個難度旋鈕**，而專案負責人已明確延後難度調整。所以 M5 維持天花板紀律：全知。

這與「視野盲區」不是同一件事。盲區需要「最後已知位置 + 搜索行為」，是一整套行為；半徑則只是一個門檻。兩者都不在 M5。

## 4. 架構

```
src/world/World.ts       ← 排序掃描的粗篩、存活旗標、撞地退場的注入點
src/world/cull.ts        ← 新增：排序掃描的純資料結構與掃描函數
src/ai/target.ts         ← 新增：目標評分、遲滯、分攤（純函數）
src/ai/AiController.ts   ← 接上目標選擇；決策相位錯開
src/battle/setup.ts      ← 新增：20v20 的生成、存活統計、重置
src/main.ts              ← 改用 battle/setup 建場；撞地檢查擴及全部
src/hud/…                ← 雙方存活數與重置倒數
```

**為什麼另開 `src/battle/`**：`World` 管的是「一步怎麼推進」，`battle/` 管的是「這一場怎麼開始與結束」。兩者的變更理由不同 —— 未來的任務模式、主選單、勝負條件只會讓後者長大，而 `World` 應該原地不動。

**為什麼 `cull.ts` 不塞進 `World.ts`**：`World.ts` 已經 254 行，而排序掃描是一組有自己的不變量（依 X 遞增、與 `combatants` 索引對齊）的資料結構。抽出來才測得到 —— §3.1 條件 1 的等價測試需要能單獨呼叫掃描。

**`src/ai/` 不依賴 `src/world/`**：`target.ts` 定義自己需要的最小介面 `TargetCandidate`，`Combatant` 在結構上滿足它。這維持 M4 建立的邊界：`ai/` 管「要幹嘛」，不知道世界是怎麼組裝的。

## 5. 命中判定：沿 X 軸的排序掃描

### 5.1 量測：問題在哪裡

40 架 × 滿載 4,000 發的 `World.step`（同一台機器、同一組條件、取五批的最小值）：

| 架數 | 無彈丸 | 滿載 4,000 發 | 60 FPS 每幀 4 步 |
|---|---|---|---|
| 2 | 100 µs | 323 µs | 1.3 ms |
| 8 | 115 µs | 1,263 µs | 5.1 ms |
| 16 | 217 µs | 3,084 µs | 12.3 ms |
| 40 | **602 µs** | **7,778 µs** | **31.1 ms** |

**AI 與物理不是瓶頸**：40 架的無彈丸成本只有 602 µs。爆掉的是 `resolveHits`，它是 `O(彈丸數 × 架數)`，而彈丸存量本身又正比於架數 —— 真實成長是 `O(N²)`。

只量粗篩迴圈本身（40 架 × 4,000 發，不含命中盒與物理）：

| 寫法 | 耗時 |
|---|---|
| A 現況：內迴圈穿 `Combatant → Aircraft → state → Vector3` 四層指標 | 7,408 µs |
| B 每步把位置與半徑攤平進 `Float32Array` | 6,892 µs |
| C 攤平 + 沿 X 軸排序後的滑動視窗 | **202 µs** |

**A 的 7,408 µs 對上整步的 7,778 µs —— 粗篩佔了 95%。**

**B 幾乎沒省（7%），這推翻了「成本在指標穿越」的假設。** 成本就是那 160,000 次距離計算本身；攤平只讓每次便宜一點點。要贏只能**不做那些計算**。這一條記在這裡，是因為它是先做了才知道的 —— 憑直覺會先去改資料布局，然後發現白改。

### 5.2 做法

每個物理步，在 `resolveHits` 之前重填一組並排的預配置陣列，只收**存活**的飛機：

| 陣列 | 內容 |
|---|---|
| `x` / `y` / `z` | 重心位置，**依 x 遞增排序** |
| `r2` | `hitRadius²` |
| `index` | 對應的 `combatants` 索引 |
| `team` | 陣營，供同隊跳過 |

**容量沒有魔術數字**：陣列在 `combatants` 增長時才重新配置（`add` 不是熱路徑），穩態下每步零配置。

排序用**插入排序**：飛機數是數十的量級，而且幀間的排列幾乎已經是排好的（240 Hz 下一步只移動幾公尺），實際比較次數接近 `O(N)`。不配置、不遞迴。

每一發彈丸：

```
lo = min(ax, bx) − rMax
hi = max(ax, bx) + rMax
二分找到第一個 x ≥ lo 的槽位，往上掃到 x > hi 為止
```

### 5.3 窗寬的推導 —— 沒有魔術數字

一架飛機的包圍球是「球心 `px`、半徑 `r`」。線段要碰得到它，**必要條件**是兩者的 X 區間重疊：

```
[px − r, px + r]  ∩  [min(ax,bx), max(ax,bx)]  ≠ ∅
⟺  px ∈ [min(ax,bx) − r, max(ax,bx) + r]
```

取 `rMax` = 本步所有存活機的最大 `hitRadius`，窗就對所有飛機都成立。

**`rMax` 每步算，不是常數** —— 換機種會變（P-51D 與 Bf 109 的包圍球不同），寫死一個值會在換裝時漏掉命中。

**窗外的飛機不可能被命中**，所以窗內取到的最小 `t` 就是全場的最小 `t`。這是等價性的證明；§3.1 條件 1 是它的實證。

### 5.4 同隊跳過

專案負責人裁決「彈丸直接穿過友機」，所以粗篩在 `team` 相同時直接 `continue`。20v20 下這再砍掉約一半的工作量。

**它取代不了「打不到自己」那一條**：射手一定與自己同隊，所以同隊跳過已經涵蓋自傷 —— 但保留原本的 `c.index === owner` 判斷，因為 §3.1 條件 8 要求的是「同隊零傷害」這條規則本身可測，而不是「碰巧被另一條規則擋掉」。

### 5.5 預期成效

粗篩 7,408 → 202 µs，整步約 570 µs，每幀 4 步 = **2.3 ms**，佔 16.7 ms 幀預算的 14%。

M1 spec §「M5 有 40 架時可降至 120 Hz 或加入子步進」預留的退路**不必動用**。240 Hz 維持不變。

## 6. 目標選擇（`src/ai/target.ts`）

純函數 + 一個共享的指派板，與 `assess` / `rules` / `steer` / `fire` 同一紀律。

### 6.1 候選集合

全部**存活的敵隊**飛機。全知，沒有距離門檻（理由見 §2.1）。

`target.ts` 定義自己需要的最小介面：

```ts
export interface TargetCandidate {
  readonly index: number
  readonly aircraft: Aircraft
  readonly team: Team
  alive: boolean
}
```

`Combatant` 在結構上滿足它。`ai/` 因此不 import `world/World`。

### 6.2 評分

三項都只用位置、速度、姿態算得出來 —— **不需要跨格狀態**，所以候選目標不必各自持有一份 `Situation`（那會是 40 × 39 份）：

| 項 | 定義 | 意義 |
|---|---|---|
| 機會 | `0.5 × (1 + cos(angleOffTail))` | 我在他尾後的程度。1 = 純尾追，0 = 純對頭 |
| 威脅 | `0.5 × (1 + cos(aspectAngleOfHim))` | 他機首指著我的程度。1 = 他正咬著我 |
| 距離 | `1 / (1 + range / rangeScale)` | 遠的打折 |

```
score = (opportunityWeight × 機會 + threatWeight × 威脅) × 距離 − crowdPenalty × 已鎖定他的隊友數
```

**機會與威脅用同一個式子的兩個方向**，與 `steer.ts` 的 `pursuit` 是同一個量 —— 不引進第二套會漂掉的幾何定義。

**威脅項是加分不是扣分**：咬著我的那一架最該被處理。這條規則的可觀察後果寫在 §3.2 條件 14。

### 6.3 分攤：一塊共享的指派板

```ts
export interface TargetBoard {
  readonly candidates: TargetCandidate[]
  /** assignments[i] = 第 i 架正在鎖定的候選索引；−1 = 無 */
  readonly assignments: Int32Array
}
```

每架 AI 選完就寫 `assignments[selfIndex] = chosen`。「已鎖定他的隊友數」則是**每次選擇時重新掃一遍 `assignments`** 得到的 —— 只數**同隊**的（敵隊也鎖定同一架敵機是不可能的，但這條規則要寫明，因為 `assignments` 是全場共用一份）。

**為什麼是重算而不是增減計數器**：增減計數器要求每一次「放棄目標」都配一次遞減 —— 陣亡、退場、重置、換目標各是一條路徑，漏掉任何一條就留下一個永遠不會消失的幽靈鎖定，而且**症狀（大家都不打那一架）離成因很遠**。重掃一遍是 `O(N)`，40 架 × 10 Hz = 每秒 16,000 次整數比較，可忽略，而且**自我修復**：任何錯誤的指派都會在下一拍被沖掉。

退場的飛機其 `assignments` 槽位歸 −1，且掃描時跳過。

### 6.4 決策相位錯開

`AiController` 的 10 Hz 節拍目前從 `decisionTimer = 0` 起算 —— 40 架會**在同一個物理步一起做昂貴的包絡查詢**，產生每 100 ms 一次的週期性尖峰（§3.2 條件 12 就是在看這個）。

生成時把第 i 架的初始 `decisionTimer` 設為 `(i / N) × 週期`，成本攤平成連續的。§3.2 條件 12 是它的人工驗收。

**它不解決分攤的順序相依，只是讓那件事變小 —— 這一點必須講清楚，不要在實作時被當成已解決的問題。** 分攤是「誰先選誰佔位」，所以總得有人先挑；相位錯開之後第 0 架仍然**每一拍都**比第 1 架早 `週期/N`（20v20 下是 2.5 ms）決策 —— 那是系統性的，不是隨機的。

不解決它的理由是：**它不是一個可以消除的東西，只能換一種形式。** 讓所有人同拍決策並讀同一份快照，順序相依確實消失，但代價是同一拍裡每個人都看到「沒人鎖定他」，於是全隊撲同一架 —— 那正是分攤要防的事，而且會在下一拍過度散開，變成 10 Hz 的震盪。相較之下「早 2.5 ms 挑」在一場 60 秒、目標不斷退場、幾何不斷改變的戰鬥裡不是有意義的優勢。

實際要保證的是**決定性**：同一組出生點與同一份設定，重跑得到一模一樣的結果（§3.1 條件 7）。這是測試能不能寫的前提，也是這一節真正的驗收對象。

### 6.5 遲滯與重選

| 規則 | 內容 |
|---|---|
| 換目標門檻 | 新目標的分數要 **好過現任 × (1 + switchMargin)** 才換 |
| 最小停留 | 換過之後 `minDwell` 秒內不再換 |
| 立即重選 | 目標退場（陣亡或撞地）時**不受最小停留約束**，下一拍就重選 |

沿用 `rules.ts` 的遲滯紀律。M4 在這裡踩過一個坑（`latch` 的 OR 結果被寫回它自己的記憶，遲滯因此失效），教訓是：**遲滯的記憶只能由遲滯自己寫**。目標選擇的「現任」同理 —— 它是遲滯的記憶，除了換目標與立即重選之外沒有任何路徑可以動它。

### 6.6 與 M4 的相容

`AiController.board` 為 `null` 時，行為與 M4 完全相同（`target` 由外部指派，不做選擇）。M4 的全部測試與 `bench/ai-load.ts` 因此一個字都不用改。

## 7. 死亡與退場

`Combatant` 新增存活旗標。**不可從 `combatants` 陣列移除** —— `index` 是彈丸記錄射手用的，`splice` 會讓所有在飛的彈丸認錯主人。所以是標記，不是刪除。

退場的飛機：

| 面向 | 行為 |
|---|---|
| 控制器 | 不呼叫 |
| 物理 | 不推進 |
| 開火 | 不開火 |
| 命中判定 | 不進粗篩陣列，打不中 |
| 目標選擇 | 不進候選集合，`assignments` 槽位歸 −1 |
| 渲染 | 模型隱藏 |

**兩個觸發**：

1. `hp ≤ 0`
2. 撞地 —— 現在擴及所有飛機，不只玩家

撞地檢查由 `World` 呼叫一個**注入的判斷式**（預設 `position.y ≤ 0`；`main.ts` 注入與海面著色器共用波參數的 `isCrashed`）。一個呼叫點、一條政策，headless 測試拿平海面的預設值，玩家拿看得到的浪頭 —— 不是兩套會漂掉的判斷。

`respawnOnDestroy` 保留（M2 的靶機與 bench 在用），但 M5 的戰場一律為 false。

## 8. 陣營生成與戰鬥重置（`src/battle/setup.ts`）

### 8.1 生成

20 藍（玩家 + 19 AI）對 20 紅（全 AI），面對面，相距 `entryRange`，同一高度層帶散布：

| 參數 | 意義 |
|---|---|
| `entryRange` | 兩隊重心的初始距離 |
| `lateralSpacing` | 同隊相鄰兩架的橫向間距 |
| `altitudeSpread` | 高度散布的半幅 |

出生點是**分布，不是編隊飛行** —— 沒有隊形保持邏輯，生成之後每架各自為戰。

玩家固定在藍隊的中央位置，這樣開局視野裡兩側都是友機，敵機在正前方 —— 與 M2「靶機擺正前方 400 m」的理由同一條：看得到才算存在。

### 8.2 重置

任一隊存活數歸零 → 倒數 `resetCountdown` 秒 → 整場重建為滿編。

與 `R` 鍵共用同一條重建路徑 —— **不是第二套初始化**。這是 M2「零選單、零狀態機」紀律能延續的方式：唯一的新狀態是一個倒數計時器。

## 10. 效能

**負載定義照 M1/M2/M4 的「單一替換點」設計**：門檻測試與 `npm run bench` 呼叫同一份負載，改一處、兩邊量到同一份工作量。

**兩個數字各有用途**（與 M2 §、M4 §12 同一個理由）：

- **設計預算**由 `npm run bench` 獨立驗證，量的是程式真正的成本
- **斷言門檻**留 2–3 倍餘裕。vitest 把測試檔分散到多個 worker 並行跑，門檻壓在預算線上會**時紅時綠**，而會飄的效能門檻比沒有門檻更糟 —— 它訓練所有人重跑一次當作沒看到，真的迴歸時也就沒人信了

兩個數字都在實作時由量測回填（§13）。預估：整步約 570 µs。

門檻要抓的是**數量級的迴歸**，具體而言就是「有人把排序掃描改回全掃描」—— 那會從 570 µs 變成 7,800 µs，十四倍。

## 12. 風險

| 風險 | 對策 |
|---|---|
| 排序掃描漏掉命中 | §3.1 條件 1 的逐發等價測試。窗寬有代數推導（§5.3），不是配出來的 |
| 分攤讓 AI 追一個沒道理的目標 | `crowdPenalty` 由 §3.1 條件 3 的最大同時鎖定數反推，不憑感覺 |
| 遲滯讓 AI 死抱一個跑掉的目標 | §3.1 條件 10 量換目標次數；距離項會隨著目標遠離自然壓低分數 |
| 20v20 的行為只在 20v20 才錯 | 整合測試以 20v20 為預設規模跑，不是拿 2v2 測完就外推 |
| 相位錯開讓決策落後 | 錯開的是相位不是頻率，每架仍然是 10 Hz。最壞情況的落後量與 M4 相同（一拍 = 100 ms） |
| 分攤的順序相依被誤以為已解決 | §6.4 明寫它**沒有**被解決，只是變小。要保證的是決定性（§3.1 條件 7），不是順序無關 |
| 40 架的 AI 成本被低估 | §5.1 已量：40 架無彈丸 602 µs。目標選擇再加每秒 16,000 次評分，量過再說 |
