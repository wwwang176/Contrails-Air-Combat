# 繪製呼叫與每幀上傳的優化設計

> 專案負責人裁定：做「飛機合併」「上傳的閘」「天空最後畫」三項，**地面著色器
> 的距離 LOD 不做** —— 那一項一定會改畫面，這一輪要的是不改畫面的。

## 一、病灶

農地・代飛纏鬥・1707×960 @ DPR 1.5・解鎖 vsync：

```
   項目          整幀      這一項    佔全幀
   全開         30.70 ms
   關飛機       16.80      13.90     45.3%
   關曳光彈     25.30       5.40     17.6%
   關渦流       29.40       1.30      4.2%
   全部不畫      6.30      24.40     79.5%
```

**模擬（40 架 AI ＋ 6 子步物理 ＋ HUD）只有 6.30 ms。** 其餘 24.4 ms 全在繪製
那一側 —— 而定格（`__still` 會暫停模擬，逐幀的更新函式因此不跑）同一張圖只有
**2.90 ms**。

三個數字放在一起只有一個解釋：`__gfx` 把一層藏起來時，three 不但不畫它，
**也不會上傳它的緩衝**。所以那 24.4 ms 大半不是「畫」，是**每幀把實例緩衝
打上去**與**每架飛機三十個 draw call** 兩件事。

### 飛機的實際結構

```
   機種      總 mesh   靜態 mesh  靜態材質   會動 mesh   合併後 draw call
   p51d          30         25         4          5             9
   bf109k4       31         27         4          4             8
   he111         46         38         6          8            14
   b17g          52         36         6         16            22
```

20v20 的戰鬥機對戰是 **40 × 30 ≈ 1,220 個 draw call**，合併後約 **340**。

**只有螺旋槳會動。** `setPropSpin` 只碰槳轂的 `rotation.z` 與槳葉／圓盤的
`visible`；砲塔管是獨立的 `InstancedMesh`（`turretBarrels`），不在飛機的
group 裡。這一點是實測的：呼叫 `setPropSpin` 前後比對每一個節點的
`rotation.z` 與 `visible`，變了的就是會動的。

### 每幀無條件上傳的池

```
   模組           實例／頂點   每幀上傳    有閘   縮 count
   tracers.ts          4,000    256.0 KB    無      無
   vortex.ts          20,480    327.7 KB    有      —     ← 有閘但整條全傳
   sparks.ts             512     38.0 KB    無      無
   muzzle 槍口           320     23.8 KB    無      無
   muzzle 砲塔           320     23.8 KB    無      無
   splash.ts             256     16.0 KB    無      無
   合計                          685.3 KB / 幀
```

**沒有任何一個池會縮 `object.count`** —— 死掉的實例是「縮放成 0」藏起來的，
所以頂點著色器每幀照樣跑滿整個容量。`vegetation.ts` 有做（`mesh.count = used`），
這幾個沒有。

`tracers` 最誇張：`PROJECTILE_CAPACITY = 4000`，每幀無條件跑滿四千次
`M.compose` ＋ `setMatrixAt` 再傳 256 KB —— 而空戰大部分時間場上不到十發子彈。

**重點不是 685 KB 的頻寬。** 2026-08-26 查證過貴的是那個動作本身：對正在被
GPU 讀的緩衝呼叫 `bufferSubData` 會強迫管線同步。`debris`（90 KB）與
`turretBarrels`（40 KB）修掉之後解鎖 p50 由 11.5 掉到 2.6 ms —— 那兩條的量
遠小於這裡。

## 二、目標與非目標

**目標**：把 24.4 ms 的繪製側成本壓下來，而**畫面一個像素都不動**。

**非目標**：
- 地面著色器的距離 LOD（會改遠處的像素，另案）。
- 降低 DPR（畫質取捨，不在這裡）。
- 模擬那 6.3 ms。

**判準**：逐像素比對。做不到逐像素相同的改動不進這一版。

## 三、三項改動

### 一、飛機的靜態零件按材質合併

`buildAircraft` 回的 `group` 目前是三十幾個 `Mesh`。改成：**建完之後把不會動
的那些按材質合併成一個 `Mesh`**，會動的（槳轂子樹）原樣留著。

```
   合併前   group ├─ 25 個靜態 Mesh（4 顆材質）
                  └─ 5 個槳葉／圓盤 Mesh
   合併後   group ├─ 4 個合併後的 Mesh（一顆材質一個）
                  └─ 5 個槳葉／圓盤 Mesh（原樣）
```

**怎麼認出「會動的」**：不用名字比對（會漏），用行為 —— 建完之後呼叫
`setPropSpin` 兩次不同的參數，把 `rotation` 或 `visible` 變過的節點連同它的
子樹標成會動。這一段只在建模時跑一次。

**合併要把子物件的變換烘進頂點**。`mergeGeometries` 只吃幾何，所以每一個
要併的 mesh 得先 `geometry.clone().applyMatrix4(mesh.matrixWorld)`。
**非等比縮放的法線要用法線矩陣**，`applyMatrix4` 對 `normal` 屬性做的正是
這件事 —— 但前提是 `updateMatrixWorld` 先跑過。

**材質不能跨組併**。座艙內裝是「朝內的殼」（`side` 不同），機身、玻璃、
金屬各有各的參數。按材質分組就自動保住這一點 —— 判準是材質物件的身分，
不是它的參數。

**視錐剔除會由逐 mesh 變成逐合併塊**。半出畫面的飛機會整塊畫 —— 那是**多畫**
不是少畫，畫面不變。而一架戰鬥機也才 2,700 個三角形。

**`dispose` 要跟著改**：合併出來的幾何是新配的，要進 `disposables`；被併掉的
原始幾何在合併後立刻釋放。

### 二、逐池的上傳閘與 `count`

對 `tracers` / `sparks` / `splash` / `muzzle`（兩個池）套 `debris.ts` 已經驗證
過的那一招：

```
   touched   這一幀有沒有動到任何一格。沒動就不設 needsUpdate
   hi        高水位。只上傳 addUpdateRange(0, hi × stride)
   count     object.count = 活著的格數，死掉的不進頂點著色器
```

**`count` 要活著的實例壓在前面。** 現在死掉的格散在中間（縮放成 0）。有兩條路：

- **高水位**：`count = hi + 1`，不搬動。省得少，但完全不動槽位。
- **壓實**：每幀把活著的搬到前面。省得多，但槽位會變 —— 而槽位在
  `sparks`／`splash` 是「粒子的身分」（`age` 等平行陣列按槽位索引）。

**取高水位。** 壓實要同步搬動四五條平行陣列，而收益是「頂點著色器少跑幾個
退化三角形」—— 那本來就會被早期剔除掉。真正貴的是上傳，而上傳靠 `touched`
與 `addUpdateRange` 就解決了。

**`vortex` 只缺 `addUpdateRange`。** 它已經有 `touched`，但一旦有任何一條尾跡
動過就整條 327 KB 全傳。它自己有 `dirty[t]` 逐尾跡的旗標，可以由那個算出要傳
的區間 —— 尾跡在緩衝裡是連續配置的（`slotOf(t, k)`）。

**`tracers` 還要順手修一件事**：它每幀 `for (let i = 0; i < n; i++)` 跑滿
`min(capacity, p.capacity)` = 4,000 格，即使場上只有幾發。`Projectiles` 有沒有
「活著的最大索引」要先查；沒有的話用高水位自己記。

### 三、天空最後畫

現在 `renderOrder = -1000`、`depthWrite: false` —— **先畫，整個螢幕被著色一次
再被地面蓋掉**。改成最後畫（`renderOrder` 設成一個大值、`depthTest` 維持開、
`depthWrite` 維持關），只有真正看得到的天空像素才付錢。

**它仍然要在不透明那一批裡。** three 先畫 opaque（按 renderOrder 再前到後）
再畫 transparent。天空的材質不是 transparent，所以給它一個大的 `renderOrder`
就會排在不透明的最後、粒子與曳光彈之前 —— 那正是要的位置。

天空的片段著色器很便宜（一個 `pow` 加一個 `mix`），所以這一項省得不多；
它進來是因為**風險接近零而且順手**。

## 四、驗收

### 逐像素

`test/e2e/pixel-identical.e2e.ts` 現在把飛機關掉，所以它守得到第三項但守不到
第一項。要補一個 fixture：**在固定姿態渲染單獨一架飛機**，合併前後各拍一輪
比像素 —— 就像 `card-probe.ts` 對點做的那樣。

```
   四個機種 × 六個方位（0/60/120/180/240/300°）× 兩個俯角（0/−30°）
   螺旋槳兩種狀態（轉動／模糊圓盤）都要拍
```

判準是**逐像素相同**，不是「看起來一樣」。

### 單元

| 測試 | 位置 | 變異 |
| --- | --- | --- |
| 合併後 draw call 數逐機種釘死 | `aircraft-merge.test.ts` | 不合併 → 紅 |
| 合併不改頂點集合（位置與法線的多重集） | 同上 | 忘了烘變換 → 紅 |
| 會動的零件仍然獨立、`setPropSpin` 仍然有效 | 同上 | 把槳葉也併進去 → 紅 |
| 每一個池「整池全死時不上傳」 | `pools.test.ts` | 拿掉 `touched` → 紅 |
| 每一個池「有東西動時一定上傳」 | 同上 | `touched` 恆假 → 紅 |
| 天空的 `renderOrder` 在所有不透明物之後、透明物之前 | `scene.test.ts` | 改回 −1000 → 紅 |

「有東西動時一定上傳」那一條特別重要 —— 漏標 `touched` 的症狀是**那一層停在
上一幀**（曳光彈不動、火花凍住），而那個缺陷在靜態截圖上看不出來。

### 幀時間

農地與群島各量一次，代飛纏鬥、鎖 vsync 與解鎖各一組。逐項提交，每一項自己
量一次 —— 三項一起進場的話出問題無法歸因。

## 五、風險

**合併之後 `dispose` 漏掉會漏記憶體。** 每一架被打下來都會 `dispose`，四十架
一場。測試要數 `dispose` 事件。

**`mergeGeometries` 要求所有幾何有相同的屬性集合。** 有的零件可能沒有
`uv` 或 `color`。合併前要先檢查，缺的那一種要嘛補上要嘛不併（自成一組）。

**`touched` 漏標。** 見上。守它的是「飛過一段之後每個池的內容都是最新的」
那一類測試 —— `vegetation.test.ts` 有一條可以照抄。

**天空的 `renderOrder` 與別人相撞。** 目前場上用到 renderOrder 的有天空
（−1000）、遠海（1）、螺旋槳圓盤（`PROP_DISC_RENDER_ORDER`）。新的值要比
所有不透明物大、而且不能踩到既有的常數。
